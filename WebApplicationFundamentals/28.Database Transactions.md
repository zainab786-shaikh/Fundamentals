# Topic 30: Database Transactions, Concurrency Control, and Data Consistency

Transactions keep related database operations consistent when requests run concurrently or failures occur partway through an operation.

## 1. ACID Properties

| Property | Meaning |
|---|---|
| Atomicity | All operations succeed, or none take effect |
| Consistency | Constraints remain valid after the transaction |
| Isolation | Concurrent transactions do not improperly interfere |
| Durability | Committed changes survive failures |

Application validation is useful, but database transactions and constraints provide the final protection against concurrent writes.

---

## 2. Define a Transaction Boundary

A transaction should represent one complete business operation.

```text name=transaction-boundary.txt
Create order:
1. Validate product and quantity
2. Reserve inventory
3. Create order
4. Create outbox event
5. Commit everything together
```

Avoid committing separately after every repository call. Otherwise, later failures can leave partially completed operations.

---

## 3. Commit or Roll Back

```python name=app/services/profile_service.py
from sqlalchemy.exc import SQLAlchemyError
from sqlalchemy.orm import Session

from app.models.user import User


def update_display_name(
    db: Session,
    user: User,
    display_name: str,
) -> User:
    try:
        user.display_name = display_name
        db.commit()
        db.refresh(user)
        return user
    except SQLAlchemyError:
        db.rollback()
        raise
```

After a failed transaction, call `rollback()` before reusing the session.

Return generic database errors to clients while logging technical details securely on the server.

---

## 4. Use a Transaction Context Manager

SQLAlchemy can commit successful work and roll back failures automatically.

```python name=app/services/order_service.py
from sqlalchemy.orm import Session

from app.models.order import Order
from app.models.outbox_event import OutboxEvent


def create_order(
    db: Session,
    order: Order,
    event: OutboxEvent,
) -> Order:
    with db.begin():
        db.add(order)
        db.flush()

        event.payload = {
            "order_id": str(order.id),
        }
        db.add(event)

    db.refresh(order)
    return order
```

`flush()` sends pending SQL to the database without committing, making generated identifiers available inside the same transaction.

Do not call `commit()` inside repository methods when the service owns the transaction.

## 5. Database Session Dependency

Use one session per request and always close it.

```python name=app/dependencies/database.py
from collections.abc import Iterator

from sqlalchemy.orm import Session

from app.database import SessionFactory


def get_db() -> Iterator[Session]:
    db = SessionFactory()

    try:
        yield db
    finally:
        db.close()
```

The service layer should explicitly define whether an operation commits or rolls back.

Do not share one SQLAlchemy `Session` across concurrent requests or threads.

## 6. Database Constraints Are Essential

Application checks alone are vulnerable to races.

Unsafe sequence:

```text name=uniqueness-race.txt
Request A checks whether email exists → No
Request B checks whether email exists → No
Request A inserts email              → Success
Request B inserts same email         → Duplicate
```

Enforce uniqueness in the database:

```python name=app/models/user.py
from sqlalchemy import String, UniqueConstraint
from sqlalchemy.orm import Mapped, mapped_column

from app.database import Base


class User(Base):
    __tablename__ = "users"
    __table_args__ = (
        UniqueConstraint(
            "normalized_email",
            name="uq_users_normalized_email",
        ),
    )

    id: Mapped[int] = mapped_column(primary_key=True)
    normalized_email: Mapped[str] = mapped_column(
        String(320),
        nullable=False,
    )
```

The unique constraint prevents duplicates even when requests execute concurrently.

## 7. Translate Constraint Violations Safely

```python name=app/services/user_service.py
from sqlalchemy.exc import IntegrityError
from sqlalchemy.orm import Session

from app.exceptions import ApplicationError
from app.models.user import User


def create_user(
    db: Session,
    normalized_email: str,
) -> User:
    user = User(normalized_email=normalized_email)

    try:
        db.add(user)
        db.commit()
        db.refresh(user)
        return user
    except IntegrityError:
        db.rollback()

        raise ApplicationError(
            code="email_conflict",
            message="An account cannot be created with that email",
            status_code=409,
        ) from None
```

In larger applications, inspect the database constraint name before translating an `IntegrityError`; not every integrity violation means an email conflict.

Avoid exposing raw SQL or constraint details to clients.

## 8. Check Constraints

Database checks protect invariants independently of the API.

```python name=app/models/order_item.py
from decimal import Decimal

from sqlalchemy import CheckConstraint, Numeric
from sqlalchemy.orm import Mapped, mapped_column

from app.database import Base


class OrderItem(Base):
    __tablename__ = "order_items"
    __table_args__ = (
        CheckConstraint(
            "quantity > 0",
            name="ck_order_items_positive_quantity",
        ),
        CheckConstraint(
            "unit_price >= 0",
            name="ck_order_items_nonnegative_price",
        ),
    )

    id: Mapped[int] = mapped_column(primary_key=True)
    quantity: Mapped[int] = mapped_column(nullable=False)
    unit_price: Mapped[Decimal] = mapped_column(
        Numeric(12, 2),
        nullable=False,
    )
```

Retain request validation as well so clients receive useful errors before a database operation is attempted.

## 9. The Lost-Update Problem

Two requests may read the same value and overwrite one another.

```text name=lost-update.txt
Stock starts at 10

Request A reads 10
Request B reads 10
Request A writes 9
Request B writes 9

Expected stock: 8
Actual stock:   9
```

Use atomic updates, optimistic concurrency, or row locks to prevent lost updates.

## 10. Prefer Atomic Updates

A single conditional statement can safely reserve inventory.

```python name=app/repositories/inventory_repository.py
from sqlalchemy import update
from sqlalchemy.orm import Session

from app.models.inventory import Inventory


def reserve_inventory(
    db: Session,
    product_id: int,
    quantity: int,
) -> bool:
    if quantity < 1:
        raise ValueError("quantity must be positive")

    result = db.execute(
        update(Inventory)
        .where(
            Inventory.product_id == product_id,
            Inventory.available_quantity >= quantity,
        )
        .values(
            available_quantity=(
                Inventory.available_quantity - quantity
            )
        )
    )

    return result.rowcount == 1
```

Use it inside a service-owned transaction:

```python name=app/services/order_service.py
from sqlalchemy.orm import Session

from app.exceptions import ApplicationError
from app.repositories.inventory_repository import reserve_inventory


def reserve_and_create_order(
    db: Session,
    product_id: int,
    quantity: int,
) -> None:
    with db.begin():
        reserved = reserve_inventory(
            db=db,
            product_id=product_id,
            quantity=quantity,
        )

        if not reserved:
            raise ApplicationError(
                code="insufficient_inventory",
                message="Insufficient inventory",
                status_code=409,
            )

        # Add the order in the same transaction.
```

The condition and decrement execute atomically in the database.

## 11. Optimistic Concurrency Control

Optimistic concurrency assumes conflicts are uncommon and detects them using a version number.

```python name=app/models/document.py
from sqlalchemy import Integer, String
from sqlalchemy.orm import Mapped, mapped_column

from app.database import Base


class Document(Base):
    __tablename__ = "documents"

    id: Mapped[int] = mapped_column(primary_key=True)
    owner_id: Mapped[int] = mapped_column(index=True)
    title: Mapped[str] = mapped_column(String(200))
    version: Mapped[int] = mapped_column(
        Integer,
        nullable=False,
        default=1,
    )
```

Update only if the expected version still matches:

```python name=app/repositories/document_repository.py
from sqlalchemy import update
from sqlalchemy.orm import Session

from app.models.document import Document


def update_document_title(
    db: Session,
    document_id: int,
    owner_id: int,
    expected_version: int,
    title: str,
) -> bool:
    result = db.execute(
        update(Document)
        .where(
            Document.id == document_id,
            Document.owner_id == owner_id,
            Document.version == expected_version,
        )
        .values(
            title=title,
            version=Document.version + 1,
        )
    )

    return result.rowcount == 1
```

If no row is updated, the record may be missing, unauthorized, or modified since the client retrieved it.

## 12. Return a Conflict for Stale Writes

```python name=app/services/document_service.py
from sqlalchemy.orm import Session

from app.exceptions import ApplicationError
from app.repositories.document_repository import (
    update_document_title,
)


def change_document_title(
    db: Session,
    document_id: int,
    owner_id: int,
    expected_version: int,
    title: str,
) -> None:
    with db.begin():
        updated = update_document_title(
            db=db,
            document_id=document_id,
            owner_id=owner_id,
            expected_version=expected_version,
            title=title,
        )

        if not updated:
            raise ApplicationError(
                code="document_update_conflict",
                message=(
                    "The document was modified. "
                    "Reload it and try again."
                ),
                status_code=409,
            )
```

Do not automatically overwrite a newer change unless the business rules explicitly permit last-write-wins behavior.

## 13. Pessimistic Row Locking

A row lock prevents competing transactions from modifying a selected row until the current transaction ends.

```python name=app/services/account_service.py
from decimal import Decimal

from sqlalchemy import select
from sqlalchemy.orm import Session

from app.exceptions import ApplicationError
from app.models.account import Account


def withdraw(
    db: Session,
    account_id: int,
    owner_id: int,
    amount: Decimal,
) -> None:
    if amount <= 0:
        raise ValueError("amount must be positive")

    with db.begin():
        account = db.scalar(
            select(Account)
            .where(
                Account.id == account_id,
                Account.owner_id == owner_id,
            )
            .with_for_update()
        )

        if account is None:
            raise ApplicationError(
                code="account_not_found",
                message="Account not found",
                status_code=404,
            )

        if account.balance < amount:
            raise ApplicationError(
                code="insufficient_funds",
                message="Insufficient funds",
                status_code=409,
            )

        account.balance -= amount
```

Use row locks only when required. Long transactions can block other requests and increase deadlock risk.

Never hold a database transaction open while waiting for user input or making a slow external network call.

## 14. Lock Rows in a Stable Order

Transfers may lock two accounts. Always lock them in a deterministic order.

```python name=app/services/transfer_service.py
from decimal import Decimal

from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models.account import Account


def transfer(
    db: Session,
    owner_id: int,
    source_id: int,
    destination_id: int,
    amount: Decimal,
) -> None:
    if source_id == destination_id:
        raise ValueError("Accounts must be different")

    if amount <= 0:
        raise ValueError("Amount must be positive")

    ordered_ids = sorted([source_id, destination_id])

    with db.begin():
        accounts = list(
            db.scalars(
                select(Account)
                .where(
                    Account.id.in_(ordered_ids),
                    Account.owner_id == owner_id,
                )
                .order_by(Account.id)
                .with_for_update()
            )
        )

        if len(accounts) != 2:
            raise ValueError("Account not found")

        accounts_by_id = {
            account.id: account
            for account in accounts
        }

        source = accounts_by_id[source_id]
        destination = accounts_by_id[destination_id]

        if source.balance < amount:
            raise ValueError("Insufficient funds")

        source.balance -= amount
        destination.balance += amount
```

Stable lock ordering reduces the chance of deadlocks.

Production code should translate these errors into safe application exceptions.

## 15. Isolation Levels

Common transaction isolation levels are:

| Level | Main behavior |
|---|---|
| Read committed | Prevents dirty reads; common default |
| Repeatable read | Repeated reads remain stable within the transaction |
| Serializable | Transactions behave as though run sequentially |

Higher isolation can reduce concurrency and may cause transactions to fail and require retries.

Choose isolation based on actual invariants—not merely the strictest available setting.

## 16. Serializable Transactions

Highly sensitive operations may require serializable isolation.

```python name=app/database.py
from sqlalchemy import create_engine

engine = create_engine(
    DATABASE_URL,
    isolation_level="SERIALIZABLE",
    pool_pre_ping=True,
)
```

Applying serializable isolation globally may be unnecessarily expensive. Prefer operation-specific configuration where supported.

Serializable transactions can still fail due to serialization conflicts. The complete transaction may need to be retried.

## 17. Retry Transient Transaction Failures

Only retry errors known to be transient, such as a serialization failure or deadlock.

```python name=app/database_retry.py
import random
import time
from collections.abc import Callable
from typing import TypeVar

from sqlalchemy.exc import OperationalError

T = TypeVar("T")


def run_transaction_with_retry(
    operation: Callable[[], T],
    maximum_attempts: int = 3,
) -> T:
    for attempt in range(1, maximum_attempts + 1):
        try:
            return operation()
        except OperationalError as error:
            if (
                not is_transient_transaction_error(error)
                or attempt == maximum_attempts
            ):
                raise

            delay = (0.05 * (2 ** (attempt - 1))) + random.uniform(
                0,
                0.05,
            )
            time.sleep(delay)

    raise RuntimeError("Transaction retry loop exited unexpectedly")
```

`is_transient_transaction_error()` must inspect database-specific error codes, not error-message text.

Retry the entire transaction from the beginning. Ensure the transaction does not perform non-idempotent external side effects.

## 18. Do Not Make External Calls Inside Transactions

Unsafe flow:

```text name=external-call-in-transaction.txt
Begin transaction
Lock account row
Call payment provider for 10 seconds
Update account
Commit
```

Problems:

- Locks remain held during network delays.
- External failures prolong transactions.
- Database rollback cannot undo the external call.
- Retrying may duplicate the external effect.

Safer designs include:

- Reserve state in one short transaction.
- Commit an outbox event.
- Process the external operation asynchronously.
- Apply the result idempotently in another transaction.

## 19. Idempotency for Database Writes

A retry of a `POST` request must not create duplicate records.

```python name=app/models/idempotency_record.py
from sqlalchemy import JSON, String, UniqueConstraint
from sqlalchemy.orm import Mapped, mapped_column

from app.database import Base


class IdempotencyRecord(Base):
    __tablename__ = "idempotency_records"
    __table_args__ = (
        UniqueConstraint(
            "owner_id",
            "operation",
            "key",
            name="uq_idempotency_owner_operation_key",
        ),
    )

    id: Mapped[int] = mapped_column(primary_key=True)
    owner_id: Mapped[int] = mapped_column(index=True)
    operation: Mapped[str] = mapped_column(String(100))
    key: Mapped[str] = mapped_column(String(128))
    request_hash: Mapped[str] = mapped_column(String(64))
    response_body: Mapped[dict[str, object] | None] = mapped_column(
        JSON,
    )
```

Associate the key with:

- The authenticated owner
- A specific operation
- A hash of the normalized request
- The stored result or resulting resource

Reject reuse of the same key with a different request payload.

## 21. Avoid Read-Modify-Write for Counters

Unsafe:

```python name=app/services/unsafe_counter.py
counter.value = counter.value + 1
db.commit()
```

Concurrent transactions may overwrite each other.

Use an atomic statement:

```python name=app/repositories/counter_repository.py
from sqlalchemy import update
from sqlalchemy.orm import Session

from app.models.counter import Counter


def increment_counter(
    db: Session,
    counter_id: int,
) -> None:
    db.execute(
        update(Counter)
        .where(Counter.id == counter_id)
        .values(value=Counter.value + 1)
    )
```

Commit it as part of the surrounding business transaction.

## 22. Prevent Double Processing with State Transitions

Update a record only from an expected state.

```python name=app/repositories/job_repository.py
from sqlalchemy import update
from sqlalchemy.orm import Session

from app.models.job import Job, JobStatus


def claim_pending_job(
    db: Session,
    job_id: int,
) -> bool:
    result = db.execute(
        update(Job)
        .where(
            Job.id == job_id,
            Job.status == JobStatus.PENDING,
        )
        .values(status=JobStatus.RUNNING)
    )

    return result.rowcount == 1
```

Only one worker can successfully change the job from `pending` to `running`.

Model valid transitions explicitly:

```text name=valid-job-transitions.txt
pending → running
running → completed
running → failed
```

Reject transitions such as `completed → running` unless an explicit replay workflow permits them.

## 23. Work Queues with `SKIP LOCKED`

Multiple database workers can claim different rows without waiting for one another.

```python name=app/repositories/job_queue.py
from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models.job import Job, JobStatus


def claim_jobs(
    db: Session,
    batch_size: int = 10,
) -> list[Job]:
    jobs = list(
        db.scalars(
            select(Job)
            .where(Job.status == JobStatus.PENDING)
            .order_by(Job.created_at)
            .limit(batch_size)
            .with_for_update(skip_locked=True)
        )
    )

    for job in jobs:
        job.status = JobStatus.RUNNING

    return jobs
```

Call this within a short transaction.

`SKIP LOCKED` behavior and support vary by database. Verify compatibility with the selected database version.

## 24. Transactional Outbox

When a state change must produce an event, store both in one transaction.

```python name=app/services/order_completion.py
from datetime import UTC, datetime

from sqlalchemy.orm import Session

from app.models.order import Order
from app.models.outbox_event import OutboxEvent


def complete_order(
    db: Session,
    order: Order,
) -> None:
    with db.begin():
        order.status = "completed"

        db.add(
            OutboxEvent(
                event_type="order.completed",
                payload={"order_id": str(order.id)},
                created_at=datetime.now(UTC),
            )
        )
```

A separate publisher sends the outbox event. Consumers must remain idempotent because publication may happen more than once.

## 25. Avoid Long Transactions

Long-running transactions can cause:

- Lock contention
- Deadlocks
- Connection-pool exhaustion
- Larger database logs
- Delayed cleanup of old row versions
- Reduced throughput

Keep transactions short:

```text name=short-transaction.txt
Validate request outside transaction
        ↓
Begin transaction
        ↓
Read and lock only required rows
        ↓
Apply database changes
        ↓
Commit
        ↓
Perform non-transactional follow-up work
```

Do not perform large file processing, user interaction, or slow network calls while holding a transaction open.

## 26. Multi-Tenant Transaction Safety

Every tenant-scoped query must include the authenticated tenant identifier.

```python name=app/repositories/invoice_repository.py
from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models.invoice import Invoice


def get_invoice_for_update(
    db: Session,
    invoice_id: int,
    tenant_id: int,
) -> Invoice | None:
    return db.scalar(
        select(Invoice)
        .where(
            Invoice.id == invoice_id,
            Invoice.tenant_id == tenant_id,
        )
        .with_for_update()
    )
```

Obtain `tenant_id` from the validated identity or server-side session—not from an unrestricted request field.

Where supported, database row-level security can provide an additional tenant-isolation layer.

## 27. Migration Consistency

Schema migrations must account for concurrent application versions.

Safe expansion:

```text name=safe-migration.txt
1. Add a nullable column
2. Deploy code that supports old and new schemas
3. Backfill data in bounded batches
4. Add validation or constraints
5. Switch reads to the new column
6. Remove the old column in a later release
```

Before destructive migration:

- Back up critical data.
- Test restoration.
- Confirm old application versions are no longer running.
- Measure lock duration.
- Define a rollback strategy.

Large table changes may require online migration techniques supported by the selected database.

## 28. Test Concurrent Inventory Reservation

```python name=tests/integration/test_inventory_concurrency.py
from concurrent.futures import ThreadPoolExecutor


def test_inventory_cannot_be_oversold(
    session_factory,
    product_id: int,
) -> None:
    def reserve() -> bool:
        with session_factory() as db:
            try:
                with db.begin():
                    return reserve_inventory(
                        db=db,
                        product_id=product_id,
                        quantity=1,
                    )
            finally:
                db.close()

    with ThreadPoolExecutor(max_workers=2) as executor:
        results = list(
            executor.map(
                lambda _: reserve(),
                range(2),
            )
        )

    assert results.count(True) == 1
    assert results.count(False) == 1
```

Use a real test database with the same concurrency semantics as production. SQLite may not reproduce PostgreSQL or SQL Server locking behavior.

## 30. Data Consistency Checklist

- Define one transaction boundary per business operation.
- Commit only after all required database changes succeed.
- Roll back failed transactions before reusing the session.
- Use database constraints for critical invariants.
- Prefer atomic conditional updates for counters and inventory.
- Use optimistic concurrency for ordinary editable resources.
- Use row locks only when conflicts require serialization.
- Lock multiple rows in a deterministic order.
- Keep transactions short.
- Retry only known transient database failures.
- Make retried transactions idempotent.
- Keep external calls outside database transactions.
- Use the transactional outbox for reliable event publication.
- Use `Decimal` and database `NUMERIC` types for money.
- Include authenticated tenant or owner criteria in every scoped query.
- Test concurrency against the production database engine.

## Key Points

- Transactions prevent partial database changes but cannot automatically undo external side effects.
- Database constraints are the final defense against concurrent invalid state.
- Atomic updates prevent many lost-update and overselling problems with minimal complexity.
- Optimistic concurrency detects stale writes without long-lived locks.
- Pessimistic locking is useful for high-contention invariants but must remain short.
- Deadlocks and serialization failures require bounded, whole-transaction retries.
- Idempotency and explicit state transitions prevent duplicate effects.
- Reliable database-and-message coordination usually requires a transactional outbox.
