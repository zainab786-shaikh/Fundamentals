# Topic 25: CI/CD Pipelines and Secure Software Supply Chains

A CI/CD pipeline automatically validates, packages, and deploys software. A secure supply chain protects source code, dependencies, build systems, artifacts, and deployment credentials.

## 1. Typical Pipeline

```text name=pipeline-flow.txt
Commit or pull request
        ↓
Lint and type-check
        ↓
Unit and integration tests
        ↓
Security scans
        ↓
Build immutable artifact
        ↓
Sign artifact and generate provenance
        ↓
Deploy to staging
        ↓
Smoke tests and approval
        ↓
Deploy to production
        ↓
Monitor and roll back if necessary
```

Build an artifact once and promote that exact artifact between environments. Rebuilding for production can produce different, unverified output.

---

## 2. Start with Minimal Workflow Permissions

GitHub Actions workflows should deny write access by default:

```yaml name=.github/workflows/ci.yml
name: CI

on:
  pull_request:
  push:
    branches:
      - main

permissions:
  contents: read
```

Grant additional permissions only to the job that requires them.

Avoid repository-wide `write-all` permission.

---

## 3. Basic Validation Job

```yaml name=.github/workflows/ci.yml
name: CI

on:
  pull_request:
  push:
    branches:
      - main

permissions:
  contents: read

jobs:
  validate:
    name: Validate
    runs-on: ubuntu-latest
    timeout-minutes: 15

    steps:
      - name: Check out source
        uses: actions/checkout@v4
        with:
          persist-credentials: false

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.13"
          cache: pip

      - name: Install dependencies
        run: |
          python -m pip install --requirement requirements.txt
          python -m pip install --requirement requirements-dev.txt

      - name: Lint
        run: ruff check .

      - name: Check formatting
        run: ruff format --check .

      - name: Type-check
        run: mypy app

      - name: Run tests
        run: pytest --strict-markers
```

Use timeouts so stalled or compromised jobs cannot consume runners indefinitely.

## 4. Pin Dependencies Reproducibly

Direct dependency declarations alone may not produce identical builds over time.

```text name=requirements.in
fastapi
pydantic-settings
sqlalchemy
uvicorn[standard]
```

Generate a locked dependency file containing exact versions and hashes:

```bash name=scripts/lock-dependencies.sh
set -euo pipefail

python -m pip install pip-tools

pip-compile \
  --generate-hashes \
  --output-file requirements.txt \
  requirements.in
```

Install only the locked packages:

```bash name=scripts/install-dependencies.sh
set -euo pipefail

python -m pip install \
  --require-hashes \
  --requirement requirements.txt
```

Review dependency updates like source-code changes. Do not update lock files blindly.

## 5. Audit Dependencies

```yaml name=.github/workflows/security.yml
name: Security

on:
  pull_request:
  push:
    branches:
      - main
  schedule:
    - cron: "17 3 * * 1"

permissions:
  contents: read

jobs:
  dependency-audit:
    runs-on: ubuntu-latest
    timeout-minutes: 10

    steps:
      - name: Check out source
        uses: actions/checkout@v4
        with:
          persist-credentials: false

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.13"

      - name: Install audit tool
        run: python -m pip install pip-audit

      - name: Audit locked dependencies
        run: pip-audit --requirement requirements.txt
```

Run scans both when code changes and on a schedule because new vulnerabilities may be disclosed without a repository change.

## 6. Scan for Committed Secrets

Secrets may accidentally appear in source code, configuration, or test fixtures.

```yaml name=.github/workflows/security.yml
jobs:
  secret-scan:
    runs-on: ubuntu-latest
    timeout-minutes: 10

    steps:
      - name: Check out full history
        uses: actions/checkout@v4
        with:
          fetch-depth: 0
          persist-credentials: false

      - name: Scan repository
        uses: gitleaks/gitleaks-action@v2
```

If a secret is committed:

1. Revoke or rotate it immediately.
2. Remove it from current source.
3. Assess whether history must be rewritten.
4. Review access logs for misuse.
5. Add preventive scanning and secret-management controls.

Deleting a secret in a later commit does not make the original secret safe.

## 7. Static Application Security Testing

Static analysis can detect insecure code patterns without executing the application.

```yaml name=.github/workflows/security.yml
jobs:
  static-analysis:
    runs-on: ubuntu-latest
    timeout-minutes: 15

    steps:
      - name: Check out source
        uses: actions/checkout@v4
        with:
          persist-credentials: false

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.13"

      - name: Install Bandit
        run: python -m pip install bandit

      - name: Run static security analysis
        run: bandit --recursive app
```

Static analysis supplements review and testing. It does not prove that an application is secure.

## 8. Build an Immutable Container

```yaml name=.github/workflows/build.yml
name: Build

on:
  push:
    branches:
      - main

permissions:
  contents: read
  packages: write

jobs:
  container:
    runs-on: ubuntu-latest
    timeout-minutes: 30

    steps:
      - name: Check out source
        uses: actions/checkout@v4
        with:
          persist-credentials: false

      - name: Set image name
        id: image
        shell: bash
        run: |
          set -euo pipefail
          echo "name=ghcr.io/${GITHUB_REPOSITORY,,}" >> "$GITHUB_OUTPUT"

      - name: Log in to container registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build container
        run: |
          set -euo pipefail
          docker build \
            --tag "${{ steps.image.outputs.name }}:${{ github.sha }}" \
            .

      - name: Push container
        run: |
          set -euo pipefail
          docker push \
            "${{ steps.image.outputs.name }}:${{ github.sha }}"
```

Use the commit SHA or image digest as the immutable release identifier. Do not rely exclusively on mutable tags such as `latest`.

## 9. Scan Before Publishing or Deploying

```yaml name=.github/workflows/build.yml
      - name: Scan container
        uses: aquasecurity/trivy-action@0.30.0
        with:
          image-ref: ${{ steps.image.outputs.name }}:${{ github.sha }}
          severity: HIGH,CRITICAL
          ignore-unfixed: true
          exit-code: "1"

      - name: Push container
        run: |
          set -euo pipefail
          docker push \
            "${{ steps.image.outputs.name }}:${{ github.sha }}"
```

The scan must run before deployment. Define a documented process for time-limited exceptions rather than permanently suppressing findings.

## 10. Generate an SBOM

A Software Bill of Materials lists the components included in a release.

```yaml name=.github/workflows/build.yml
      - name: Generate SBOM
        uses: anchore/sbom-action@v0
        with:
          image: ${{ steps.image.outputs.name }}:${{ github.sha }}
          format: cyclonedx-json
          output-file: sbom.cdx.json

      - name: Upload SBOM
        uses: actions/upload-artifact@v4
        with:
          name: sbom-${{ github.sha }}
          path: sbom.cdx.json
          if-no-files-found: error
          retention-days: 30
```

An SBOM helps determine whether a deployed artifact includes a newly vulnerable dependency.

Do not place secrets or sensitive configuration in build artifacts.

---

## 11. Sign Artifacts

Artifact signing lets deployment systems verify who produced an image and whether it was modified.

```text name=artifact-verification.txt
Source commit
    ↓ trusted CI build
Container image
    ↓ signature and provenance
Registry
    ↓ verification policy
Deployment
```

Prefer keyless signing with short-lived workload identity when supported. If signing keys are required, keep them in a dedicated key-management service—not repository secrets or source files.

Deployment should fail closed when a required signature or provenance record cannot be verified.

---

## 12. Avoid Long-Lived Cloud Credentials

Do not store permanent cloud access keys in CI secrets when workload identity federation is available.

```yaml name=.github/workflows/deploy.yml
permissions:
  contents: read
  id-token: write
```

The `id-token: write` permission allows the job to request a short-lived identity token. The cloud provider should exchange it for narrowly scoped, temporary credentials.

Restrict trust by:

- Repository
- Branch or tag
- Workflow
- Deployment environment
- Organization
- Expected audience

A pull-request workflow should not receive production deployment access.

## 13. Separate Build and Deployment Jobs

```yaml name=.github/workflows/deploy.yml
name: Deploy

on:
  workflow_dispatch:
    inputs:
      image_digest:
        description: Immutable image digest
        required: true
        type: string

permissions:
  contents: read

jobs:
  deploy-staging:
    environment: staging
    runs-on: ubuntu-latest
    timeout-minutes: 15

    steps:
      - name: Validate digest format
        env:
          IMAGE_DIGEST: ${{ inputs.image_digest }}
        shell: bash
        run: |
          set -euo pipefail

          if [[ ! "$IMAGE_DIGEST" =~ ^sha256:[a-f0-9]{64}$ ]]; then
            echo "Invalid image digest" >&2
            exit 1
          fi

      - name: Deploy approved artifact
        env:
          IMAGE_DIGEST: ${{ inputs.image_digest }}
        run: |
          ./scripts/deploy.sh staging "$IMAGE_DIGEST"
```

The deployment accepts only an immutable digest and validates its format before use.

Production deployments should use a separate protected environment.

## 14. Protect Deployment Environments

Configure production environments with:

- Required reviewers
- Restricted deployment branches or tags
- Separate environment secrets
- Deployment history
- Approval gates
- Short-lived cloud credentials

```yaml name=.github/workflows/deploy.yml
jobs:
  deploy-production:
    environment: production
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write
```

Environment protection belongs in repository settings as well as workflow code.

---

## 15. Treat Pull Requests as Untrusted

Pull-request code can modify scripts and workflow behavior.

For workflows triggered from forks:

- Do not expose privileged secrets.
- Do not provide production credentials.
- Do not automatically publish trusted artifacts.
- Do not run untrusted code on persistent self-hosted runners.
- Review changes to workflows and build scripts carefully.

Avoid using `pull_request_target` to check out and execute untrusted pull-request code with privileged permissions.

---

## 16. Protect Self-Hosted Runners

A compromised job may persist on a reusable runner and affect later jobs.

Prefer ephemeral, isolated runners for untrusted builds.

Self-hosted runners should:

- Be recreated after each job.
- Have no inbound network access.
- Use least-privileged identities.
- Have restricted outbound access.
- Never mount the host Docker socket unnecessarily.
- Avoid sharing credentials or workspaces.
- Be separated by trust level.

Do not run public fork code on sensitive internal runners.

---

## 17. Pin Third-Party Actions

A version tag can move. Pinning to a full commit SHA provides stronger immutability.

```yaml name=.github/workflows/ci.yml
steps:
  - name: Check out source
    uses: actions/checkout@<reviewed-full-commit-sha>
```

When pinning:

1. Select the official action repository.
2. Verify the intended release.
3. Resolve it to its full commit SHA.
4. Record the release version in a comment.
5. Use automated updates to propose reviewed SHA changes.

Never copy an unverified SHA from an untrusted source.

## 18. Prevent Command Injection in Workflows

Do not insert untrusted event data directly into shell scripts.

**Unsafe:**

```yaml name=.github/workflows/unsafe.yml
- name: Print pull-request title
  run: echo "${{ github.event.pull_request.title }}"
```

A malicious title could contain shell syntax.

**Safer:**

```yaml name=.github/workflows/safe.yml
- name: Print pull-request title
  env:
    PULL_REQUEST_TITLE: ${{ github.event.pull_request.title }}
  shell: bash
  run: |
    set -euo pipefail
    printf '%s\n' "$PULL_REQUEST_TITLE"
```

Pass untrusted expressions through environment variables and quote them correctly.

Do not use untrusted input to construct commands, paths, registry names, or deployment targets without strict validation.

---

## 19. Masking Is Not Secret Management

GitHub attempts to mask registered secrets in logs, but applications can still transform or leak values.

Do not:

- Print environment variables indiscriminately.
- Enable shell tracing around secret-handling commands.
- Upload directories containing credentials.
- Include tokens in URLs.
- Pass secrets as command-line arguments when safer alternatives exist.

Use standard input, protected files with restrictive permissions, or platform-specific secret injection where appropriate.

---

## 20. Branch Protection

Protect the default and release branches with:

- Pull requests required
- Required approving reviews
- Required status checks
- Conversation resolution
- Restricted direct pushes
- Protection against force pushes and deletion
- Code-owner review for security-sensitive paths

```text name=security-sensitive-paths.txt
.github/workflows/
Dockerfile
scripts/deploy.sh
infrastructure/
app/security/
requirements.txt
```

Changes to these paths deserve additional review because they affect the trust boundary.

## 21. Deployment Smoke Tests

```bash name=scripts/smoke-test.sh
set -euo pipefail

environment="${1:?Environment is required}"

case "$environment" in
  staging)
    base_url="https://staging.example.com"
    ;;
  production)
    base_url="https://api.example.com"
    ;;
  *)
    echo "Unsupported environment" >&2
    exit 1
    ;;
esac

curl \
  --fail \
  --silent \
  --show-error \
  --max-time 10 \
  "${base_url}/health/live"
```

The script derives the URL from an allow-listed environment instead of accepting an arbitrary URL.

Smoke tests should validate only synthetic or non-destructive operations unless explicitly designed with idempotency and cleanup.

## 22. Deployment Concurrency

Prevent overlapping production deployments:

```yaml name=.github/workflows/deploy.yml
concurrency:
  group: production-deployment
  cancel-in-progress: false
```

Allowing only one production deployment at a time avoids conflicting migrations and uncertain release state.

Do not cancel an active production deployment unless the deployment process is designed for interruption.

---

## 23. Rollback Strategy

Record the previously deployed immutable digest before each deployment.

```text name=rollback-process.txt
1. Detect a failed health check or alert threshold
2. Stop further rollout
3. Restore the previous verified image digest
4. Confirm readiness and critical workflows
5. Preserve logs and evidence
6. Investigate the incident
```

Database migrations must be backward-compatible because reverting the application does not automatically reverse schema or data changes.

---

## 24. Pipeline Auditability

Record:

- Source commit
- Workflow identity and version
- Dependency lock-file hash
- Artifact digest
- SBOM
- Security scan results
- Signature and provenance
- Deployment environment
- Approver
- Deployment timestamp
- Rollback events

Keep production deployment records protected from ordinary application accounts.

---

## 25. Secure Pipeline Checklist

- Use minimal workflow permissions.
- Pin dependencies and verify hashes.
- Pin third-party actions to reviewed commit SHAs.
- Scan dependencies, source code, secrets, and images.
- Build once and promote the same immutable artifact.
- Generate an SBOM and provenance.
- Sign artifacts and verify them before deployment.
- Use short-lived federated deployment credentials.
- Protect production environments with approval gates.
- Treat pull-request code as untrusted.
- Use ephemeral isolated runners where possible.
- Validate all workflow inputs.
- Protect workflow, deployment, and security configuration files.
- Test rollback procedures before an incident.
- Monitor deployments and fail closed when verification fails.
