
# Topic 14: CSRF and XSS

**CSRF** abuses a user’s authenticated browser session.  
**XSS** injects malicious script into a trusted web page.

---

## 1. CSRF Explained

Browsers automatically send cookies with matching requests. An attacker may exploit this behavior to submit an unwanted action.

```text name=csrf-flow.txt
User logs in to bank.example
        ↓
Browser stores session cookie
        ↓
User visits malicious.example
        ↓
Malicious page submits a request to bank.example
        ↓
Browser automatically attaches the session cookie
```

CSRF mainly affects applications that authenticate requests with cookies.

---

## 2. Unsafe State-Changing Request

```html name=malicious-page.html
<form action="https://bank.example/transfers" method="post">
  <input name="amount" value="1000">
  <input name="recipient" value="attacker">
</form>

<script>
  document.forms[0].submit();
</script>
```

The browser may attach the user’s bank session cookie automatically. The API must not trust the cookie alone.

---

## 3. Use Safe HTTP Methods Correctly

Never modify data through `GET`.

```python name=app/routers/accounts.py
from fastapi import APIRouter, status

router = APIRouter(prefix="/accounts")


@router.post(
    "/{account_id}/deactivate",
    status_code=status.HTTP_204_NO_CONTENT,
)
def deactivate_account(account_id: int) -> None:
    # Authenticate, authorize, and validate CSRF before changing data.
    return None
```

Use `POST`, `PUT`, `PATCH`, or `DELETE` for state changes and protect them against CSRF.

---

## 4. Secure Session Cookies

```python name=app/security/cookies.py
from fastapi import Response


def set_session_cookie(
    response: Response,
    session_id: str,
) -> None:
    response.set_cookie(
        key="__Host-session",
        value=session_id,
        secure=True,
        httponly=True,
        samesite="strict",
        path="/",
        max_age=900,
    )
```

- `Secure`: Sends the cookie only over HTTPS.
- `HttpOnly`: Prevents JavaScript from reading it.
- `SameSite=Strict`: Strongly limits cross-site cookie submission.
- `__Host-`: Prevents a domain attribute and requires `Path=/`.

Use `SameSite=Lax` only when legitimate cross-site navigation is required.

## 5. CSRF Token Pattern

The server generates an unpredictable CSRF token and associates it with the authenticated session.

```python name=app/security/csrf.py
import secrets


def generate_csrf_token() -> str:
    return secrets.token_urlsafe(32)
```

The frontend sends it in a custom header:

```javascript name=frontend/update-profile.js
await fetch("https://api.example.com/profile", {
  method: "PATCH",
  credentials: "include",
  headers: {
    "Content-Type": "application/json",
    "X-CSRF-Token": csrfToken,
  },
  body: JSON.stringify({ displayName: "Alice" }),
});
```

A malicious site generally cannot read the valid token due to the Same-Origin Policy.

---

## 6. Validate the CSRF Token

```python name=app/security/csrf.py
import secrets
from typing import Annotated

from fastapi import Header, HTTPException, status


def verify_csrf_token(
    expected_token: str,
    supplied_token: Annotated[
        str | None,
        Header(alias="X-CSRF-Token"),
    ] = None,
) -> None:
    if supplied_token is None or not secrets.compare_digest(
        supplied_token,
        expected_token,
    ):
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="Invalid CSRF token",
        )
```

Compare the supplied token with the server-side session token. Reject missing or incorrect values.

---

## 7. Validate the Request Origin

```python name=app/security/origin.py
from typing import Annotated

from fastapi import Header, HTTPException, status

ALLOWED_ORIGINS = {"https://app.example.com"}


def verify_origin(
    origin: Annotated[str | None, Header()] = None,
) -> None:
    if origin not in ALLOWED_ORIGINS:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="Untrusted request origin",
        )
```

For sensitive cookie-authenticated operations, validate the exact `Origin` in addition to using a CSRF token.

Do not use substring checks such as `endswith("example.com")`.

---

## 8. CSRF and Bearer Tokens

```javascript name=frontend/profile.js
await fetch("https://api.example.com/profile", {
  headers: {
    Authorization: `Bearer ${accessToken}`,
  },
});
```

Bearer tokens manually added to `Authorization` headers are generally less vulnerable to CSRF because browsers do not attach them automatically.

However, stolen tokens remain vulnerable to misuse. Protect them from XSS and never place them in URLs.

---

## 9. CORS Does Not Replace CSRF Protection

```python name=app/main.py
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.example.com"],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PATCH", "DELETE"],
    allow_headers=["Content-Type", "X-CSRF-Token"],
)
```

CORS controls whether browser JavaScript can read responses. CSRF protection verifies that a state-changing request was intentionally made by the trusted application.

Use both when cross-origin cookies are required.

# XSS

## 10. XSS Explained

XSS occurs when untrusted content is interpreted as executable HTML or JavaScript.

Common types:

- **Stored XSS:** Malicious content is saved and shown later.
- **Reflected XSS:** Malicious input is immediately returned in a page.
- **DOM-based XSS:** Frontend JavaScript inserts unsafe content into the page.

---

## 11. Stored XSS Example

A malicious comment might contain:

```html name=malicious-comment.html
<img src="invalid" onerror="alert('XSS')">
```

If the frontend inserts this as HTML, the browser may execute the event handler.

The API should treat user-generated content as untrusted text.

---

## 12. Prefer `textContent`

Unsafe:

```javascript name=frontend/unsafe-comment.js
commentElement.innerHTML = apiResponse.comment;
```

Secure:

```javascript name=frontend/comment.js
commentElement.textContent = apiResponse.comment;
```

`textContent` displays the value as text instead of interpreting it as HTML.

---

## 13. Use Framework Escaping

Most modern frontend frameworks escape text by default.

```tsx name=frontend/Comment.tsx
type CommentProps = {
  message: string;
};

export function Comment({ message }: CommentProps) {
  return <p>{message}</p>;
}
```

React escapes `message` when rendered normally. Avoid bypass mechanisms such as `dangerouslySetInnerHTML` with untrusted content.

---

## 14. Validate Input, but Encode Output

```python name=app/schemas/comment.py
from pydantic import BaseModel, ConfigDict, Field


class CommentCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    message: str = Field(min_length=1, max_length=2_000)
```

Input validation limits malformed or oversized content, but it does not fully prevent XSS.

The final protection is **context-aware output encoding** in the frontend:

- HTML context: HTML encoding
- JavaScript context: JavaScript-safe encoding
- URL context: URL encoding
- Attribute context: Attribute encoding

---

## 15. Sanitize HTML When HTML Is Required

If users must submit formatted HTML, use a proven HTML sanitizer with a strict allow-list.

```javascript name=frontend/sanitized-content.js
import DOMPurify from "dompurify";

const sanitizedHtml = DOMPurify.sanitize(untrustedHtml, {
  ALLOWED_TAGS: ["p", "strong", "em", "ul", "li"],
  ALLOWED_ATTR: [],
});

contentElement.innerHTML = sanitizedHtml;
```

Prefer plain text or Markdown when possible. Keep the sanitizer updated and forbid scripts, event handlers, iframes, and dangerous URLs.

## 16. Content Security Policy

CSP limits which scripts and resources a browser may execute.

```python name=app/middleware/security_headers.py
from fastapi import Request, Response


async def add_security_headers(
    request: Request,
    call_next,
) -> Response:
    response = await call_next(request)

    response.headers["Content-Security-Policy"] = (
        "default-src 'self'; "
        "script-src 'self'; "
        "object-src 'none'; "
        "base-uri 'none'; "
        "frame-ancestors 'none'"
    )
    response.headers["X-Content-Type-Options"] = "nosniff"

    return response
```

Avoid `'unsafe-inline'` and `'unsafe-eval'` where possible. Test CSP in report-only mode before enforcing it on an existing application.

---

## 17. Protect Tokens from XSS

Avoid storing long-lived tokens in `localStorage`:

```javascript name=frontend/unsafe-token-storage.js
localStorage.setItem("refresh_token", refreshToken);
```

Injected JavaScript can read `localStorage`.

A safer browser design is:

- Keep short-lived access tokens in memory.
- Keep refresh or session tokens in `HttpOnly`, `Secure` cookies.
- Protect cookie-authenticated operations against CSRF.

`HttpOnly` reduces token theft through JavaScript, although XSS may still perform actions through the victim’s browser.

## CSRF vs XSS Summary

| Risk | Main cause | Main protections |
|---|---|---|
| CSRF | Browser automatically sends authentication cookies | CSRF tokens, `SameSite`, origin checks |
| XSS | Untrusted content is executed as code | Output encoding, safe DOM APIs, sanitization, CSP |

## Key Security Rules

- Use CSRF protection for cookie-authenticated state changes.
- Use the strictest practical `SameSite` cookie policy.
- Validate exact request origins.
- Never use `GET` to modify data.
- Treat all user-generated content as untrusted.
- Prefer `textContent` and normal framework rendering.
- Sanitize HTML only when formatted HTML is necessary.
- Apply a restrictive Content Security Policy.
- Keep sensitive tokens out of URLs and browser-readable persistent storage.
