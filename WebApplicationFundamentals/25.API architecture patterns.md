# Topic 27: API Architecture Patterns and Project Structure

A clear architecture separates HTTP handling, business rules, data access, security, and infrastructure. This improves testing and maintainability without requiring unnecessary abstraction.

## 1. Start with a Simple Layered Architecture

```text name=architecture-layers.txt
HTTP request
    ↓
Router / controller
    ↓
Service / business logic
    ↓
Repository / data access
    ↓
Database or external service
```

Responsibilities:

| Layer | Responsibility |
|---|---|
| Router | HTTP parsing, dependencies, status codes, response models |
| Service | Business rules, authorization decisions, transactions |
| Repository | Parameterized database operations |
| Model | Persistence representation |
| Schema | Validated API request and response contracts |
| Infrastructure | Database, messaging, storage, and external clients |

Start with these layers and add more only when complexity justifies them.

## 3. Application Entry Point

Keep application construction centralized.

```python name=app/main.py
from fastapi import FastAPI

from app.middleware.security_headers import security_headers_middleware
from app.routers import health, orders


def create_app() -> FastAPI:
    application = FastAPI(
        title="Order API",
        version="1.0.0",
        debug=False,
    )

    application.middleware("http")(security_headers_middleware)

    application.include_router(health.router)
    application.include_router(orders.router, prefix="/v1")

    return application


app = create_app()
```

An application factory makes configuration and integration testing easier.

## 4. API Schemas

API schemas define the public contract and validate untrusted input.

```python name=app/schemas/order.py
from decimal import Decimal

from pydantic import BaseModel, ConfigDict, Field


class OrderCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    product_id: int = Field(ge=1)
    quantity: int = Field(ge=1, le=100)


class OrderResponse(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    product_id: int
    quantity: int
    total: Decimal
    status: str
```

Do not reuse database models as request schemas. Request models should exclude fields such as:

- `owner_id`
- `tenant_id`
- `is_admin`
- Internal status flags
- Audit fields

The server derives those values from trusted context.

## 5. Database Model

```python name=app/models/order.py
from decimal import Decimal

from sqlalchemy import ForeignKey, Numeric, String
from sqlalchemy.orm import Mapped, mapped_column

from app.database import Base


class Order(Base):
    __tablename__ = "orders"

    id: Mapped[int] = mapped_column(primary_key=True)
    owner_id: Mapped[int] = mapped_column(
        ForeignKey("users.id", ondelete="RESTRICT"),
        index=True,
        nullable=False,
    )
    product_id: Mapped[int] = mapped_column(
        ForeignKey("products.id", ondelete="RESTRICT"),
        index=True,
        nullable=False,
    )
    quantity: Mapped[int] = mapped_column(nullable=False)
    total: Mapped[Decimal] = mapped_column(
        Numeric(12, 2),
        nullable=False,
    )
    status: Mapped[str] = mapped_column(
        String(30),
        nullable=False,
        default="pending",
    )
```

Database constraints remain necessary even when request validation exists. They protect data during concurrency and non-API operations.

## 6. Repository Layer

Repositories encapsulate database queries.

```python name=app/repositories/order_repository.py
from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models.order import Order


class OrderRepository:
    def __init__(self, db: Session) -> None:
        self._db = db

    def add(self, order: Order) -> None:
        self._db.add(order)

    def get_owned_order(
        self,
        order_id: int,
        owner_id: int,
    ) -> Order | None:
        statement = select(Order).where(
            Order.id == order_id,
            Order.owner_id == owner_id,
        )

        return self._db.scalar(statement)
```

Including `owner_id` in the query helps prevent insecure direct-object references.

The repository should not trust a client-supplied owner or tenant ID. The service must provide identity data derived from validated authentication.

## 7. Service Layer

Services implement business rules and transaction boundaries.

```python name=app/services/order_service.py
from decimal import Decimal

from sqlalchemy.orm import Session

from app.exceptions import ApplicationError
from app.models.order import Order
from app.repositories.order_repository import OrderRepository
from app.schemas.order import OrderCreate


class OrderService:
    def __init__(
        self,
        db: Session,
        repository: OrderRepository,
    ) -> None:
        self._db = db
        self._repository = repository

    def create_order(
        self,
        owner_id: int,
        data: OrderCreate,
        unit_price: Decimal,
    ) -> Order:
        if unit_price <= 0:
            raise ApplicationError(
                code="invalid_product_price",
                message="Order cannot be created",
                status_code=409,
            )

        order = Order(
            owner_id=owner_id,
            product_id=data.product_id,
            quantity=data.quantity,
            total=unit_price * data.quantity,
            status="pending",
        )

        try:
            self._repository.add(order)
            self._db.commit()
            self._db.refresh(order)
        except Exception:
            self._db.rollback()
            raise

        return order

    def get_order(
        self,
        order_id: int,
        owner_id: int,
    ) -> Order:
        order = self._repository.get_owned_order(
            order_id=order_id,
            owner_id=owner_id,
        )

        if order is None:
            raise ApplicationError(
                code="order_not_found",
                message="Order not found",
                status_code=404,
            )

        return order
```

The service:

- Derives ownership from the authenticated user
- Applies business rules
- Controls the transaction
- Returns safe application errors
- Does not depend on HTTP request objects

Catching specific database exceptions is preferable when translating known failures.

## 8. Dependency Injection

FastAPI dependencies assemble services without global mutable state.

```python name=app/dependencies/orders.py
from typing import Annotated

from fastapi import Depends
from sqlalchemy.orm import Session

from app.dependencies.database import get_db
from app.repositories.order_repository import OrderRepository
from app.services.order_service import OrderService


def get_order_service(
    db: Annotated[Session, Depends(get_db)],
) -> OrderService:
    repository = OrderRepository(db)

    return OrderService(
        db=db,
        repository=repository,
    )


OrderServiceDependency = Annotated[
    OrderService,
    Depends(get_order_service),
]
```

Constructor injection makes dependencies explicit and replaceable during tests.

## 9. Thin Routers

Routers should focus on HTTP concerns.

```python name=app/routers/orders.py
from decimal import Decimal

from fastapi import APIRouter, Path, status

from app.dependencies.auth import CurrentUser
from app.dependencies.orders import OrderServiceDependency
from app.schemas.order import OrderCreate, OrderResponse

router = APIRouter(
    prefix="/orders",
    tags=["Orders"],
)


@router.post(
    "",
    response_model=OrderResponse,
    status_code=status.HTTP_201_CREATED,
)
def create_order(
    data: OrderCreate,
    current_user: CurrentUser,
    service: OrderServiceDependency,
) -> OrderResponse:
    order = service.create_order(
        owner_id=current_user.id,
        data=data,
        unit_price=Decimal("50.00"),
    )

    return OrderResponse.model_validate(order)


@router.get(
    "/{order_id}",
    response_model=OrderResponse,
)
def get_order(
    current_user: CurrentUser,
    service: OrderServiceDependency,
    order_id: int = Path(ge=1),
) -> OrderResponse:
    order = service.get_order(
        order_id=order_id,
        owner_id=current_user.id,
    )

    return OrderResponse.model_validate(order)
```

Avoid placing database queries, pricing rules, or authorization logic directly in routers.

## 10. Centralized Application Errors

```python name=app/exceptions.py
class ApplicationError(Exception):
    def __init__(
        self,
        code: str,
        message: str,
        status_code: int,
    ) -> None:
        self.code = code
        self.message = message
        self.status_code = status_code
        super().__init__(message)
```

```python name=app/handlers.py
from fastapi import Request
from fastapi.responses import JSONResponse

from app.exceptions import ApplicationError


async def application_error_handler(
    request: Request,
    exception: ApplicationError,
) -> JSONResponse:
    request_id = getattr(
        request.state,
        "request_id",
        "unknown",
    )

    return JSONResponse(
        status_code=exception.status_code,
        content={
            "error": {
                "code": exception.code,
                "message": exception.message,
                "request_id": request_id,
            }
        },
    )
```

Register the handler during application construction:

```python name=app/main.py
from app.exceptions import ApplicationError
from app.handlers import application_error_handler


application.add_exception_handler(
    ApplicationError,
    application_error_handler,
)
```

Clients receive safe, consistent errors while internal exceptions remain in protected server logs.

## 11. Feature-Based Structure

As an application grows, grouping files by feature may be easier to navigate.

```text name=feature-structure.txt
app/
├── main.py
├── shared/
│   ├── config.py
│   ├── database.py
│   ├── exceptions.py
│   └── security/
├── orders/
│   ├── models.py
│   ├── repository.py
│   ├── router.py
│   ├── schemas.py
│   └── service.py
└── users/
    ├── models.py
    ├── repository.py
    ├── router.py
    ├── schemas.py
    └── service.py
```

### Layer-based organization

Advantages:

- Familiar and simple
- Easy to find all routers or repositories
- Suitable for small applications

Trade-off:

- One feature may be spread across many directories

### Feature-based organization

Advantages:

- Related code stays together
- Easier feature ownership
- Scales well for larger teams

Trade-off:

- Shared boundaries require discipline
- Features may duplicate abstractions if not reviewed

Do not reorganize a stable codebase without a clear maintenance benefit.

## 12. Dependency Direction

Dependencies should generally point inward toward business rules.

```text name=dependency-direction.txt
Router
  ↓
Service
  ↓
Repository interface
  ↓
Database implementation
```

Business logic should not depend directly on:

- FastAPI request objects
- HTTP headers
- A particular database driver
- Environment variables
- Global clients
- Framework response classes

This makes business logic portable and easier to test.

## 13. Ports and Adapters

For applications with multiple external systems, define interfaces around infrastructure.

```python name=app/orders/ports.py
from typing import Protocol


class InventoryGateway(Protocol):
    def reserve(
        self,
        product_id: int,
        quantity: int,
    ) -> bool:
        ...
```

Infrastructure implementation:

```python name=app/infrastructure/inventory_client.py
import httpx

from app.orders.ports import InventoryGateway


class HttpInventoryGateway(InventoryGateway):
    def __init__(self, client: httpx.Client) -> None:
        self._client = client

    def reserve(
        self,
        product_id: int,
        quantity: int,
    ) -> bool:
        response = self._client.post(
            "/reservations",
            json={
                "product_id": product_id,
                "quantity": quantity,
            },
        )
        response.raise_for_status()

        return bool(response.json()["reserved"])
```

The HTTP client should use:

- A trusted configured base URL
- HTTPS
- Explicit timeouts
- Limited retries for safe operations
- Authentication with least privilege
- Safe error handling

Interfaces are useful at real infrastructure boundaries. Avoid creating an interface for every small class.

## 14. Transaction Boundaries

A business operation should define one clear transaction boundary.

```python name=app/services/order_cancellation.py
from sqlalchemy.orm import Session

from app.exceptions import ApplicationError
from app.models.order import Order


def cancel_order(
    db: Session,
    order: Order,
) -> None:
    if order.status != "pending":
        raise ApplicationError(
            code="order_cannot_be_cancelled",
            message="Order cannot be cancelled",
            status_code=409,
        )

    try:
        order.status = "cancelled"
        db.commit()
    except Exception:
        db.rollback()
        raise
```

Avoid committing independently inside several repositories during one business operation. Partial commits can leave data inconsistent.

## 15. External Side Effects and the Outbox Pattern

A database transaction and message publication cannot usually be committed atomically without additional design.

Unsafe sequence:

```text name=unsafe-side-effects.txt
1. Commit order
2. Publish message
3. Message publication fails
```

The order exists, but downstream systems never receive the event.

The transactional outbox pattern stores the event in the same database transaction:

```text name=outbox-flow.txt
Database transaction:
  - Create order
  - Create outbox event
  - Commit both

Background publisher:
  - Read unpublished events
  - Publish event
  - Mark event as published
```

Consumers must be idempotent because message delivery may occur more than once.

## 16. Modular Monolith Before Microservices

A modular monolith keeps deployment simple while maintaining internal boundaries.

```text name=modular-monolith.txt
Single deployable application
├── Orders module
├── Users module
├── Billing module
└── Shared infrastructure
```

Advantages:

- Simple deployment and debugging
- Local transactions
- Lower operational overhead
- Easier refactoring

Consider microservices only when there is a demonstrated need for:

- Independent scaling
- Independent deployment
- Strong team ownership boundaries
- Different availability requirements
- Isolation of high-risk workloads

Microservices add network failures, distributed tracing, eventual consistency, and deployment complexity.

## 17. Avoid Shared Mutable Global State

Unsafe:

```python name=app/unsafe_state.py
active_orders: list[int] = []
```

Global process memory is:

- Not shared across multiple workers
- Lost during restarts
- Unsafe under concurrent modification
- Difficult to test reliably

Use an appropriate durable system:

- Database for application state
- Redis for shared ephemeral state
- Object storage for files
- Queue for background work

Module-level immutable configuration is generally acceptable.

## 18. Configuration Boundaries

Load and validate configuration once at startup.

```python name=app/config.py
from functools import lru_cache

from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    database_url: SecretStr
    inventory_base_url: str
    environment: str = "development"

    model_config = SettingsConfigDict(
        extra="ignore",
    )


@lru_cache
def get_settings() -> Settings:
    return Settings()
```

Do not read arbitrary environment variables throughout the service layer. Central validation prevents inconsistent configuration behavior.

External URLs still require strict allow-list validation for scheme, host, port, and path.

## 19. Unit-Test the Service Layer

```python name=tests/unit/test_order_service.py
from decimal import Decimal
from unittest.mock import Mock

from sqlalchemy.orm import Session

from app.repositories.order_repository import OrderRepository
from app.schemas.order import OrderCreate
from app.services.order_service import OrderService


def test_create_order_uses_authenticated_owner() -> None:
    db = Mock(spec=Session)
    repository = Mock(spec=OrderRepository)

    service = OrderService(
        db=db,
        repository=repository,
    )

    order = service.create_order(
        owner_id=42,
        data=OrderCreate(
            product_id=10,
            quantity=2,
        ),
        unit_price=Decimal("5.00"),
    )

    assert order.owner_id == 42
    assert order.total == Decimal("10.00")
    repository.add.assert_called_once_with(order)
    db.commit.assert_called_once()
```

The test verifies business behavior without starting an HTTP server.

## 20. Integration-Test Repository Security

```python name=tests/integration/test_order_repository.py
from sqlalchemy.orm import Session

from app.models.order import Order
from app.repositories.order_repository import OrderRepository


def test_get_owned_order_does_not_return_another_users_order(
    db: Session,
) -> None:
    order = Order(
        owner_id=100,
        product_id=10,
        quantity=1,
        total=50,
        status="pending",
    )
    db.add(order)
    db.flush()

    repository = OrderRepository(db)

    result = repository.get_owned_order(
        order_id=order.id,
        owner_id=200,
    )

    assert result is None
```

Security boundaries such as ownership and tenant isolation should have dedicated integration tests.

## 21. Common Architecture Mistakes

Avoid:

- Business logic inside routers
- Returning database models without response schemas
- Accepting client-provided owner or tenant IDs
- Repositories that bypass tenant filtering
- Committing separately in every repository method
- Catching all exceptions and hiding failures
- Global mutable state
- Unnecessary interfaces and abstraction layers
- Circular imports between features
- Microservices without an operational need
- Sharing one database account with excessive privileges

Architecture should reduce risk and complexity—not add ceremony.

## Key Points

- Start with a simple layered architecture.
- Keep routers thin and business rules in services.
- Keep parameterized database access in repositories.
- Separate API schemas from database models.
- Derive ownership and tenant identity from validated authentication.
- Define transaction boundaries around complete business operations.
- Inject dependencies explicitly for testability.
- Group by feature when the codebase becomes large.
- Use ports and adapters only at meaningful infrastructure boundaries.
- Prefer a modular monolith until independent services provide measurable value.
- Test authorization boundaries at both service and repository levels.
