# Topic 26: API Versioning, Compatibility, Deprecation, and Lifecycle Management

API lifecycle management lets clients upgrade predictably without unexpected breaking changes.

## 1. What Is a Breaking Change?

A breaking change requires existing clients to modify their code.

Common breaking changes include:

- Removing or renaming an endpoint
- Removing or renaming a response field
- Changing a field’s type or meaning
- Making an optional request field required
- Rejecting values that were previously accepted
- Changing authentication requirements
- Changing pagination or error formats
- Removing an enum value
- Tightening rate limits significantly

Changes that are often backward-compatible include:

- Adding an optional request field
- Adding a response field
- Adding a new endpoint
- Adding an optional query parameter
- Correcting documentation without changing behavior

Clients should tolerate unknown response fields.

---

## 2. URL Path Versioning

A common strategy places the major API version in the path:

```text name=versioned-endpoints.txt
https://api.example.com/v1/products
https://api.example.com/v2/products
```

FastAPI routers can provide version-specific prefixes:

```python name=app/routers/v1/products.py
from fastapi import APIRouter

router = APIRouter(prefix="/products", tags=["Products"])


@router.get("")
def list_products() -> list[dict[str, object]]:
    return [
        {
            "id": 1,
            "name": "Keyboard",
        }
    ]
```

```python name=app/main.py
from fastapi import FastAPI

from app.routers.v1.products import router as products_v1_router

app = FastAPI()

app.include_router(
    products_v1_router,
    prefix="/v1",
)
```

Path versioning is visible, easy to route, and straightforward for clients.

---

## 3. Version Only for Breaking Changes

Do not create a new major version for every feature.

```text name=version-policy.txt
Add optional field       → Keep v1
Add new endpoint         → Keep v1
Fix internal performance → Keep v1
Rename response field    → Create v2
Change field type        → Create v2
Remove endpoint          → Create v2
```

Excessive versions increase maintenance, documentation, testing, and security costs.

---

## 4. Keep Business Logic Shared

Version-specific routers should translate requests and responses while reusing shared services.

```python name=app/services/product_service.py
from dataclasses import dataclass
from decimal import Decimal


@dataclass(frozen=True)
class Product:
    id: int
    name: str
    price: Decimal


def list_products() -> list[Product]:
    return [
        Product(
            id=1,
            name="Keyboard",
            price=Decimal("50.00"),
        )
    ]
```

Version 1 response:

```python name=app/routers/v1/products.py
from fastapi import APIRouter

from app.services.product_service import list_products

router = APIRouter(prefix="/products")


@router.get("")
def get_products() -> list[dict[str, object]]:
    return [
        {
            "id": product.id,
            "name": product.name,
            "price": float(product.price),
        }
        for product in list_products()
    ]
```

Version 2 response:

```python name=app/routers/v2/products.py
from fastapi import APIRouter

from app.services.product_service import list_products

router = APIRouter(prefix="/products")


@router.get("")
def get_products() -> dict[str, object]:
    products = list_products()

    return {
        "items": [
            {
                "product_id": product.id,
                "display_name": product.name,
                "price": {
                    "amount": str(product.price),
                    "currency": "USD",
                },
            }
            for product in products
        ],
        "count": len(products),
    }
```

Keeping business rules shared prevents different API versions from implementing inconsistent authorization or validation behavior.

## 5. Register Multiple Versions

```python name=app/main.py
from fastapi import FastAPI

from app.routers.v1.products import router as products_v1_router
from app.routers.v2.products import router as products_v2_router

app = FastAPI(
    title="Store API",
    version="2.0.0",
)

app.include_router(products_v1_router, prefix="/v1")
app.include_router(products_v2_router, prefix="/v2")
```

Both versions may operate during a documented migration period.

Do not leave obsolete versions running indefinitely. Every supported version increases the attack surface.

---

## 6. Header-Based Versioning

Another strategy uses request headers:

```http name=versioned-request.http
GET /products HTTP/1.1
Host: api.example.com
Accept: application/vnd.example.products-v2+json
```

Advantages:

- Keeps URLs stable
- Supports media-type negotiation

Trade-offs:

- Harder to discover and test manually
- More complicated caching and routing
- Version selection is less visible

Path versioning is usually simpler for public APIs.

---

## 7. Avoid Query-Parameter Versioning

```text name=query-versioning.txt
GET /products?version=2
```

This approach is easy to implement but can complicate:

- Caching
- Logging
- Documentation
- Routing
- Security policies

Prefer path or media-type versioning unless there is a specific reason otherwise.

## 8. Use Explicit Request and Response Models

```python name=app/schemas/v1/products.py
from decimal import Decimal

from pydantic import BaseModel, ConfigDict, Field


class ProductCreateV1(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: str = Field(min_length=1, max_length=100)
    price: Decimal = Field(gt=0, max_digits=10, decimal_places=2)


class ProductResponseV1(BaseModel):
    id: int
    name: str
    price: Decimal
```

Version-specific schemas prevent accidental contract changes caused by modifying a shared model.

Database models should not be returned directly as API contracts.

---

## 9. Additive Changes

Adding an optional field is generally compatible:

```python name=app/schemas/v1/products.py
class ProductResponseV1(BaseModel):
    id: int
    name: str
    price: Decimal
    description: str | None = None
```

However, compatibility also depends on client behavior. Some clients reject unknown fields even though robust clients should ignore them.

Use contract testing and communicate significant additions.

---

## 10. Enum Compatibility

Adding an enum value can break clients that assume they know every possible value.

Initial values:

```text name=order-status-v1.txt
pending
completed
cancelled
```

Later addition:

```text name=order-status-v2.txt
refunded
```

A defensive TypeScript client can preserve unknown values:

```typescript name=client/orderStatus.ts
export type KnownOrderStatus =
  | "pending"
  | "completed"
  | "cancelled"
  | "refunded";

export type OrderStatus = KnownOrderStatus | (string & {});

export function displayOrderStatus(status: OrderStatus): string {
  switch (status) {
    case "pending":
      return "Pending";
    case "completed":
      return "Completed";
    case "cancelled":
      return "Cancelled";
    case "refunded":
      return "Refunded";
    default:
      return "Unknown";
  }
}
```

Document whether enum values may expand over time.

## 11. Safe Database Evolution

API versions and database versions are different concerns. Use backward-compatible schema migrations.

```text name=expand-contract.txt
Expand:
1. Add the new nullable column
2. Deploy code that writes old and new formats
3. Backfill existing records
4. Deploy code that reads the new format

Contract:
5. Stop using the old column
6. Verify no old application versions remain
7. Remove the old column in a later release
```

Never remove a database column while deployed application instances still depend on it.

Back up critical data and test restoration before destructive migrations.

## 12. Mark Deprecated Endpoints in OpenAPI

```python name=app/routers/v1/products.py
from fastapi import APIRouter

router = APIRouter(prefix="/products")


@router.get(
    "",
    deprecated=True,
    summary="List products using the legacy response",
)
def list_products_v1() -> list[dict[str, object]]:
    return []
```

FastAPI marks the operation as deprecated in its generated OpenAPI document.

Documentation should also identify the replacement endpoint and migration deadline.

---

## 13. Deprecation Response Headers

A deprecated endpoint may return lifecycle information:

```python name=app/routers/v1/products.py
from datetime import UTC, datetime

from fastapi import Response


@router.get("", deprecated=True)
def list_products_v1(
    response: Response,
) -> list[dict[str, object]]:
    response.headers["Deprecation"] = "true"
    response.headers["Sunset"] = "Tue, 30 Jun 2027 23:59:59 GMT"
    response.headers["Link"] = (
        '<https://docs.example.com/migrations/products-v2>; '
        'rel="deprecation"'
    )

    return []
```

The date is expressed in HTTP-date format. Ensure the announced date matches the published lifecycle policy.

## 14. Deprecation Timeline

A clear lifecycle might be:

```text name=deprecation-timeline.txt
2026-11-01 → v2 becomes generally available
2027-01-15 → v1 is officially deprecated
2027-04-01 → v1 support becomes security-only
2027-06-30 → v1 is removed
```

The migration period should reflect:

- Client count
- Contractual commitments
- Security risk
- Migration complexity
- Availability of client libraries
- Regulatory requirements

Emergency security changes may require shorter notice.

---

## 15. Publish a Migration Guide

A migration guide should include:

- Deprecated version
- Replacement version
- Exact shutdown date
- Changed endpoints and fields
- Authentication changes
- Before-and-after examples
- Client-library versions
- Testing instructions
- Rollback considerations
- Support contact

Example transformation:

```json name=v1-product-response.json
{
  "id": 1,
  "name": "Keyboard",
  "price": 50.0
}
```

```json name=v2-product-response.json
{
  "product_id": 1,
  "display_name": "Keyboard",
  "price": {
    "amount": "50.00",
    "currency": "USD"
  }
}
```

Using a string for decimal currency values avoids floating-point precision problems.

## 16. Contract Tests

```python name=tests/contract/test_product_versions.py
from fastapi.testclient import TestClient


def test_v1_product_contract(client: TestClient) -> None:
    response = client.get("/v1/products")

    assert response.status_code == 200

    item = response.json()[0]
    assert set(item) == {"id", "name", "price"}


def test_v2_product_contract(client: TestClient) -> None:
    response = client.get("/v2/products")

    assert response.status_code == 200

    payload = response.json()
    assert set(payload) == {"items", "count"}
    assert set(payload["items"][0]) == {
        "product_id",
        "display_name",
        "price",
    }
```

Contract tests protect supported versions from accidental changes.

Exact field checks are appropriate when the contract forbids additional properties. Otherwise, validate required fields while permitting compatible additions.

## 17. OpenAPI Compatibility Checks

Store the approved OpenAPI document and compare proposed changes in CI.

The check should detect:

- Removed operations
- Removed parameters
- Newly required parameters
- Removed response properties
- Type changes
- Authentication changes
- Removed status codes
- Narrowed enum values

Intentional breaking changes should require an explicit version change and approval.

---

## 18. Monitor Version Usage

Record version usage with low-cardinality metrics:

```text name=version-metrics.txt
api_requests_total{version="v1",route="/products",status="200"}
api_requests_total{version="v2",route="/products",status="200"}
```

Do not use user IDs, tokens, full URLs, or request IDs as metric labels.

Monitor:

- Requests per version
- Active clients per version
- Error rates
- Latency
- Deprecated endpoint usage
- Clients still using versions near shutdown

Usage data helps determine whether removal is safe.

---

## 19. Version Security Controls Consistently

Older versions must still receive:

- Authentication fixes
- Authorization checks
- Input validation
- Dependency updates
- Rate limiting
- Logging and monitoring
- Critical vulnerability patches

Never preserve an insecure behavior solely for backward compatibility.

If compatibility conflicts with security, choose the secure behavior, document the change, and provide a migration path.

---

## 20. Retire a Version Safely

Before removal:

1. Confirm the documented sunset date has passed.
2. Notify remaining known clients.
3. Verify replacement documentation and tooling.
4. Review traffic and audit metrics.
5. Back up relevant configuration and records.
6. Remove routes, schemas, tests, and documentation.
7. Remove obsolete permissions and infrastructure.
8. Monitor `404` and client error rates after removal.

Return a clear response during a final transition period if policy permits:

```json name=retired-version-response.json
{
  "error": {
    "code": "api_version_retired",
    "message": "API version v1 is no longer available. Use v2."
  }
}
```

Do not redirect mutation requests automatically between API versions because their semantics may differ.

---

## 21. Recommended Version Policy

```text name=api-version-policy.txt
Versioning:
- Major versions appear in the URL path.
- Breaking changes require a new major version.
- Compatible additions remain in the current version.

Support:
- At most two major versions are supported simultaneously.
- Deprecated versions receive critical security fixes only.
- Every deprecation includes a migration guide and sunset date.

Removal:
- Usage is monitored before removal.
- Clients receive advance notice.
- Obsolete routes, permissions, and infrastructure are removed.
```

## Key Points

- Version only when introducing breaking changes.
- Prefer simple, visible path versioning for public APIs.
- Keep business logic shared but contracts version-specific.
- Treat request and response schemas as public contracts.
- Use backward-compatible database migrations.
- Mark deprecated operations and publish sunset dates.
- Provide migration guides with before-and-after examples.
- Run contract and OpenAPI compatibility checks in CI.
- Monitor deprecated-version usage.
- Continue security maintenance throughout the support period.
- Remove obsolete versions to reduce attack surface.
