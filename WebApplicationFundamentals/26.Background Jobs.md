# Topic 28: Background Jobs, Queues, Scheduled Tasks, and Reliable Event Processing

Background processing moves slow, retryable, or asynchronous work outside the API request-response cycle.

Typical jobs include:

- Sending email
- Generating reports
- Processing uploads
- Synchronizing external systems
- Publishing notifications
- Cleaning expired sessions
- Running scheduled maintenance

## 1. When to Use a Background Job

Use a background job when work:

- Takes too long for an HTTP request
- Must be retried after transient failures
- Can complete asynchronously
- Requires independent scaling
- Should survive API restarts

```text name=request-job-flow.txt
Client → POST /reports
       ← 202 Accepted + job ID

Worker → Generate report
       → Update job status

Client → GET /jobs/{job_id}
       ← completed / failed / pending
```

Do not move work to a queue merely to hide inefficient code. Simple, fast operations should remain synchronous.

## 2. FastAPI `BackgroundTasks`

FastAPI provides in-process background tasks:

```python name=app/routers/notifications.py
import logging

from fastapi import APIRouter, BackgroundTasks, status

router = APIRouter(prefix="/notifications", tags=["Notifications"])
logger = logging.getLogger(__name__)


def send_notification(user_id: int, message: str) -> None:
    logger.info(
        "Sending notification user_id=%s",
        user_id,
    )
    # Send the notification through an approved provider.


@router.post(
    "",
    status_code=status.HTTP_202_ACCEPTED,
)
def create_notification(
    background_tasks: BackgroundTasks,
) -> dict[str, str]:
    background_tasks.add_task(
        send_notification,
        42,
        "Your report is ready",
    )

    return {"status": "accepted"}
```

These tasks execute after the response is sent.

### Appropriate uses

- Small, non-critical operations
- Short tasks
- Work that may safely be lost during shutdown

### Limitations

- Tasks are stored only in process memory.
- They may be lost if the process crashes or restarts.
- They do not provide durable retries.
- They compete with the API process for resources.
- They do not coordinate across application instances.

Use a durable queue for important work.

## 3. Durable Queue Architecture

```text name=queue-architecture.txt
API
 │
 ├── Store application state
 └── Publish job
          ↓
      Durable queue
          ↓
     Worker process
          ↓
 Database / external service
```

Common queue components include:

- A message broker
- One or more worker processes
- Persistent job state
- Retry and dead-letter policies
- Metrics, logs, and alerts

The API and worker should use separate least-privileged identities.

## 4. Job Status Model

```python name=app/models/job.py
from datetime import datetime

from sqlalchemy import DateTime, Enum, ForeignKey, String, Text

        index=True,
        nullable=False,
    )
    job_type: Mapped[str] = mapped_column(
        String(100),
        nullable=False,
    )
    status: Mapped[JobStatus] = mapped_column(
        Enum(JobStatus),
        default=JobStatus.PENDING,
        nullable=False,
        index=True,
    )
    error_code: Mapped[str | None] = mapped_column(
        String(100),
        nullable=True,
    )
    error_message: Mapped[str | None] = mapped_column(
        Text,
        nullable=True,
    )
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        nullable=False,
    )
    started_at: Mapped[datetime | None] = mapped_column(
        DateTime(timezone=True),
    )
    completed_at: Mapped[datetime | None] = mapped_column(
        DateTime(timezone=True),

```

Store safe error information only. Do not persist stack traces, credentials, tokens, or sensitive payloads in client-visible job records.

## 7. Authorize Job Status Requests

```python name=app/routers/jobs.py
from uuid import UUID

from fastapi import APIRouter, HTTPException, status
from sqlalchemy import select

from app.dependencies import DatabaseSession
from app.dependencies.auth import CurrentUser
from app.models.job import Job

router = APIRouter(prefix="/jobs", tags=["Jobs"])


@router.get("/{job_id}")
def get_job(
    job_id: UUID,
    current_user: CurrentUser,
    db: DatabaseSession,
) -> Job:
    job = db.scalar(
        select(Job).where(
            Job.id == job_id,
            Job.owner_id == current_user.id,
        )
    )

    if job is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Job not found",
        )

    return job
```

Including `owner_id` in the query prevents one user from reading another user’s job status.

Use a dedicated response model rather than returning the persistence model directly in production.

## 8. The Dual-Write Problem

This sequence is unreliable:

```text name=dual-write-failure.txt
1. Commit job to database
2. Publish queue message
3. Publishing fails

Result: A pending job exists, but no worker receives it.
```

Reversing the order creates another failure:

```text name=reverse-dual-write-failure.txt
1. Publish queue message
2. Database commit fails

Result: A worker receives a job that does not exist.
```

Use the transactional outbox pattern when the database and broker cannot share one transaction.

## 9. Transactional Outbox

Store an outgoing event in the same transaction as the application change.

```python name=app/models/outbox_event.py
from datetime import datetime
from uuid import UUID, uuid4

from sqlalchemy import DateTime, JSON, String
from sqlalchemy.orm import Mapped, mapped_column

from app.database import Base


class OutboxEvent(Base):
    __tablename__ = "outbox_events"

    id: Mapped[UUID] = mapped_column(
        primary_key=True,
        default=uuid4,
    )
    event_type: Mapped[str] = mapped_column(
        String(100),
        nullable=False,
        index=True,
    )
    payload: Mapped[dict[str, object]] = mapped_column(
        JSON,
        nullable=False,
    )
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        nullable=False,
    )
    published_at: Mapped[datetime | None] = mapped_column(
        DateTime(timezone=True),
        nullable=True,
        index=True,
    )
```

Create the job and outbox event atomically:

```python name=app/services/report_jobs.py
from datetime import UTC, datetime

from sqlalchemy.orm import Session

from app.models.job import Job, JobStatus
from app.models.outbox_event import OutboxEvent


def create_report_job(
    db: Session,
    owner_id: int,
) -> Job:
    job = Job(
        owner_id=owner_id,
        job_type="generate_report",
        status=JobStatus.PENDING,
        created_at=datetime.now(UTC),
    )
    db.add(job)
    db.flush()

    event = OutboxEvent(
        event_type="report.requested",
        payload={"job_id": str(job.id)},
        created_at=datetime.now(UTC),
    )
    db.add(event)

    db.commit()
    db.refresh(job)

    return job
```

A separate publisher reads unpublished outbox events, sends them to the broker, and records successful publication.

## 10. Outbox Publisher

```python name=app/workers/outbox_publisher.py
from datetime import UTC, datetime
from typing import Protocol

from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models.outbox_event import OutboxEvent


class MessagePublisher(Protocol):
    def publish(
        self,
        event_type: str,
        payload: dict[str, object],
        message_id: str,
    ) -> None:
        ...


def publish_pending_events(
    db: Session,
    publisher: MessagePublisher,
    batch_size: int = 100,
) -> int:
    events = list(
        db.scalars(
            select(OutboxEvent)
            .where(OutboxEvent.published_at.is_(None))
            .order_by(OutboxEvent.created_at)
            .limit(batch_size)
        )
    )

    published_count = 0

    for event in events:
        publisher.publish(
            event_type=event.event_type,
            payload=event.payload,
            message_id=str(event.id),
        )

        event.published_at = datetime.now(UTC)
        db.commit()
        published_count += 1

    return published_count
```

Publishing and marking an event as published still cannot normally be atomic. Therefore, the broker may receive the same event more than once.

Consumers must be idempotent.

For concurrent publishers, use safe row-claiming such as database locks with `SKIP LOCKED`, where supported.

## 11. At-Least-Once Delivery

Most durable systems provide **at-least-once delivery**:

```text name=at-least-once-delivery.txt
Worker receives message
        ↓
Worker completes operation
        ↓
Acknowledgment is lost
        ↓
Broker sends the same message again
```

Code must assume duplicate delivery is possible.

“Exactly once” is usually achieved as an application-level effect through idempotency, unique constraints, and transactions—not by assuming a message appears only once.

## 13. Worker Processing

```python name=app/workers/report_worker.py
from datetime import UTC, datetime
from uuid import UUID

from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models.job import Job, JobStatus


def process_report_job(
    db: Session,
    job_id: UUID,
) -> None:
    job = db.scalar(
        select(Job).where(Job.id == job_id)
    )

    if job is None:
        return

    if job.status == JobStatus.COMPLETED:
        return

    job.status = JobStatus.RUNNING
    job.started_at = datetime.now(UTC)
    db.commit()

    try:
        # Generate and securely store the report.
        report_storage_key = generate_report(job)

        job.status = JobStatus.COMPLETED
        job.completed_at = datetime.now(UTC)
        job.error_code = None
        job.error_message = None
        db.commit()

        # Persist report_storage_key through an approved field/model.
        _ = report_storage_key

    except TemporaryDependencyError:
        db.rollback()
        raise

    except Exception:
        db.rollback()

        failed_job = db.get(Job, job_id)

        if failed_job is not None:
            failed_job.status = JobStatus.FAILED
            failed_job.error_code = "report_generation_failed"
            failed_job.error_message = "Report generation failed"
            failed_job.completed_at = datetime.now(UTC)
            db.commit()

        raise
```

Use specific exception types in real code. Log technical details securely while exposing only safe error information.

## 14. Retry Policy

Retry only failures likely to be temporary:

| Failure | Retry? |
|---|---|
| Network timeout | Usually |
| Temporary `503` | Usually |
| Broker unavailable | Usually |
| Invalid input | No |
| Missing permission | No |
| Unsupported file type | No |
| Permanent business conflict | No |

Use exponential backoff with jitter:

```python name=app/workers/retry_policy.py
import random


def retry_delay_seconds(
    attempt: int,
    maximum_seconds: float = 300,
) -> float:
    if attempt < 1:
        raise ValueError("attempt must be at least 1")

    exponential_delay = min(2 ** (attempt - 1), maximum_seconds)
    jitter = random.uniform(0, exponential_delay * 0.2)

    return exponential_delay + jitter
```

Jitter prevents many workers from retrying simultaneously after an outage.

Set a maximum attempt count and maximum delay. Infinite retries can keep malformed messages circulating forever.

## 15. Dead-Letter Queues

After exhausting retries, move the message to a dead-letter queue.

```text name=dead-letter-flow.txt
Main queue
   ↓ processing fails
Retry with backoff
   ↓ retry limit reached
Dead-letter queue
   ↓
Alert and controlled investigation
```

A dead-letter process should:

- Alert operators
- Preserve the message ID and failure category
- Avoid exposing secrets in dashboards
- Support controlled replay
- Record who initiated replay
- Prevent infinite replay loops

Never automatically replay all failed messages after a code change without assessing side effects.

## 16. Message Payload Security

Prefer small messages containing identifiers:

```json name=report-requested-message.json
{
  "message_id": "3a6a3f45-f85a-4c99-84ae-d0458cb20313",
  "event_type": "report.requested",
  "schema_version": 1,
  "job_id": "2c9f8571-8867-4d45-8aa4-60021c06f02c",
  "occurred_at": "2026-10-25T12:00:00Z"
}
```

Avoid placing these values in messages:

- Passwords
- Access or refresh tokens
- Session IDs
- API keys
- Full payment details
- Large uploaded files
- Unnecessary personal data

Fetch sensitive data from an authorized source at processing time. Encrypt the broker connection and stored messages where supported.

## 18. Least-Privilege Worker Identities

Different workers should use separate credentials:

```text name=worker-identities.txt
report-worker:
- Read report input data
- Write generated reports
- Update report job status

email-worker:
- Read approved email jobs
- Call email provider
- Update email job status

outbox-publisher:
- Read and update outbox records
- Publish to approved topics
```

A report worker should not automatically receive administrator database access or permission to publish to every queue.

## 19. Job Cancellation

Cancellation is cooperative. A worker must check whether cancellation was requested.

```python name=app/models/job.py
cancel_requested_at: Mapped[datetime | None] = mapped_column(
    DateTime(timezone=True),
)
```

```python name=app/services/job_cancellation.py
from datetime import UTC, datetime
from uuid import UUID

from fastapi import HTTPException
from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models.job import Job, JobStatus


def request_job_cancellation(
    db: Session,
    job_id: UUID,
    owner_id: int,
) -> None:
    job = db.scalar(
        select(Job).where(
            Job.id == job_id,
            Job.owner_id == owner_id,
        )
    )

    if job is None:
        raise HTTPException(404, "Job not found")

    if job.status in {JobStatus.COMPLETED, JobStatus.FAILED}:
        raise HTTPException(409, "Job cannot be cancelled")

    job.cancel_requested_at = datetime.now(UTC)
    db.commit()
```

A worker should check cancellation between safe processing steps. Abruptly terminating a process can leave partial side effects.

## 20. Scheduled Tasks

Scheduled tasks handle recurring work:

- Delete expired sessions
- Retry outbox publication
- Produce daily reports
- Remove abandoned uploads
- Rotate temporary records

```python name=app/tasks/cleanup_sessions.py
from datetime import UTC, datetime

from sqlalchemy import delete
from sqlalchemy.orm import Session

from app.models.session import UserSession


def delete_expired_sessions(db: Session) -> int:
    result = db.execute(
        delete(UserSession).where(
            UserSession.expires_at < datetime.now(UTC)
        )
    )
    db.commit()

    return result.rowcount or 0
```

Use an external scheduler, orchestrator, or queue scheduler for durable production schedules.

Do not start an independent scheduler inside every API replica unless duplicate execution is explicitly safe.

## 21. Prevent Concurrent Scheduled Runs

Multiple scheduler instances may start the same task.

Possible protections include:

- Distributed locks
- Database advisory locks
- Unique execution records
- Leader election
- Idempotent operations

```text name=scheduled-job-lock.txt
Scheduler instance A → Acquires lock → Runs cleanup
Scheduler instance B → Lock unavailable → Skips this run
```

Locks require expiration and recovery handling so a crashed worker does not block future runs forever.

## 22. Time Zones and Scheduling

Store timestamps in UTC:

```python name=app/tasks/time.py
from datetime import UTC, datetime

current_time = datetime.now(UTC)
```

For user-facing schedules:

1. Store the user’s IANA time-zone identifier, such as `Europe/Paris`.
2. Calculate execution using a time-zone-aware library.
3. Handle daylight-saving transitions explicitly.
4. Store the resulting execution timestamp in UTC.

Avoid fixed numeric offsets because they do not model daylight-saving changes.

## 23. Graceful Worker Shutdown

A worker receiving a termination signal should:

1. Stop accepting new jobs.
2. Finish or safely release the current job.
3. Avoid acknowledging incomplete work.
4. Close broker and database connections.
5. Exit before the platform’s termination deadline.

```text name=worker-shutdown.txt
Termination signal
      ↓
Stop consuming
      ↓
Complete or abandon safely
      ↓
Acknowledge only completed work
      ↓
Close connections and exit
```

Jobs should be designed so redelivery after an interrupted shutdown is safe.

## 24. Queue Backpressure

If producers create jobs faster than workers process them, queue depth grows.

Monitor:

- Queue depth
- Age of oldest message
- Job processing duration
- Retry count
- Dead-letter count
- Worker utilization
- Success and failure rates

Possible responses:

- Scale workers
- Reduce producer rate
- Apply API rate limits
- Reject excess work with `429` or `503`
- Prioritize critical queues
- Optimize slow handlers

Do not scale workers beyond the capacity of databases and downstream services.

## 25. Separate Queues by Workload

```text name=queue-separation.txt
high-priority queue → password and security notifications
default queue       → ordinary business events
batch queue         → reports and large exports
```

Separating workloads prevents a large batch job from delaying security-sensitive work.

Workers should consume only the queues required for their role.

## 29. Operational Checklist

Before deploying background processing:

- Define message schemas and versioning.
- Validate every message.
- Make consumers idempotent.
- Set explicit timeouts and retry limits.
- Configure exponential backoff with jitter.
- Provide a dead-letter process.
- Use the transactional outbox for reliable publication.
- Encrypt broker connections.
- Apply least-privileged worker credentials.
- Avoid secrets and unnecessary personal data in payloads.
- Monitor queue depth and oldest-message age.
- Test duplicate delivery and worker interruption.
- Define safe replay and cancellation procedures.
- Document job retention and cleanup policies.

## Key Points

- Use in-process tasks only for short, non-critical work.
- Use a durable queue for important or retryable jobs.
- Return `202 Accepted` with an authorized status endpoint.
- Assume messages can be delivered more than once.
- Achieve safe processing through idempotency and database constraints.
- Use a transactional outbox to avoid unreliable database-and-broker dual writes.
- Retry only transient failures with bounded backoff and jitter.
- Dead-letter permanently failing messages for controlled investigation.
- Validate messages as untrusted input.
- Run workers with least privilege and monitor queue health.
