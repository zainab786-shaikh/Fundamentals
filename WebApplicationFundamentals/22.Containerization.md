# Topic 24: Containerization and Secure Deployment

Containerization packages the API and its runtime dependencies into a consistent deployment unit. Secure deployment applies least privilege, immutable infrastructure, secret management, health checks, and controlled releases.

## 1. Application Dependencies

Pin production dependencies to tested versions.

```text name=requirements.txt
fastapi==0.115.12
pydantic-settings==2.9.1
sqlalchemy==2.0.41
uvicorn[standard]==0.34.2
```

Use an automated dependency-update process and run vulnerability scanning before deployment.

---

## 2. Secure Dockerfile

```dockerfile name=Dockerfile
FROM python:3.13-slim AS runtime

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PORT=8000

WORKDIR /app

RUN groupadd --system --gid 10001 api \
    && useradd \
        --system \
        --uid 10001 \
        --gid api \
        --no-create-home \
        --shell /usr/sbin/nologin \
        api

COPY requirements.txt ./

RUN python -m pip install --upgrade pip \
    && python -m pip install --requirement requirements.txt

COPY --chown=api:api app ./app

USER api

EXPOSE 8000

CMD ["sh", "-c", "uvicorn app.main:app --host 0.0.0.0 --port ${PORT}"]
```

Important protections:

- Uses a small official runtime image.
- Runs as a non-root user.
- Copies only required application files.
- Disables Python bytecode and unbuffered-log delays.
- Does not place secrets in the image.
- Uses the executable form of the startup command where practical.

For stronger reproducibility, reference the base image by digest.

---

## 3. Do Not Run as Root

```dockerfile name=Dockerfile
USER api
```

A non-root user limits damage if the application is compromised.

The process should not need permission to:

- Install packages
- Modify application code
- Access the Docker socket
- Change operating-system configuration
- Bind privileged ports below `1024`

## 5. Build and Run Locally

```bash name=scripts/run-container.sh
set -euo pipefail

docker build --tag secure-api:local .

docker run --rm \
  --name secure-api \
  --publish 127.0.0.1:8000:8000 \
  --env-file .env.local \
  secure-api:local
```

Binding to `127.0.0.1` avoids exposing the development container to the wider network.

Do not commit `.env.local`.

## 6. Environment Configuration

```python name=app/config.py
from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    environment: str = "development"
    database_url: SecretStr
    jwt_secret: SecretStr
    allowed_hosts: list[str] = []
    cors_origins: list[str] = []

    model_config = SettingsConfigDict(
        env_file=None,
        extra="ignore",
    )


settings = Settings()
```

Production secrets should come from a deployment secret manager rather than an image, source file, or command-line argument.

## 7. Fail Fast on Unsafe Production Settings

```python name=app/config.py
from pydantic import model_validator


class Settings(BaseSettings):
    environment: str = "development"
    debug: bool = False
    database_url: SecretStr
    jwt_secret: SecretStr
    allowed_hosts: list[str] = []
    cors_origins: list[str] = []

    model_config = SettingsConfigDict(extra="ignore")

    @model_validator(mode="after")
    def validate_production_settings(self) -> "Settings":
        if self.environment == "production":
            if self.debug:
                raise ValueError(
                    "Debug mode must be disabled in production"
                )

            if not self.allowed_hosts:
                raise ValueError(
                    "Production requires an allowed-host list"
                )

            if "*" in self.cors_origins:
                raise ValueError(
                    "Wildcard CORS is not allowed in production"
                )

            if len(self.jwt_secret.get_secret_value()) < 32:
                raise ValueError(
                    "JWT secret must contain at least 32 characters"
                )

        return self
```

Failing during startup is safer than silently deploying an insecure configuration.

## 8. Trusted Hosts and HTTPS Redirects

```python name=app/main.py
from fastapi import FastAPI
from fastapi.middleware.httpsredirect import HTTPSRedirectMiddleware
from fastapi.middleware.trustedhost import TrustedHostMiddleware

from app.config import settings

app = FastAPI(debug=settings.debug)

app.add_middleware(
    TrustedHostMiddleware,
    allowed_hosts=settings.allowed_hosts,
)

if settings.environment == "production":
    app.add_middleware(HTTPSRedirectMiddleware)
```

`TrustedHostMiddleware` rejects unexpected `Host` headers.

In many deployments, HTTPS redirection and TLS termination are handled by a trusted ingress or reverse proxy. Configure forwarded headers only for known proxy addresses.

## 9. Security Headers

```python name=app/middleware/security_headers.py
from fastapi import Request, Response


async def security_headers_middleware(
    request: Request,
    call_next,
) -> Response:
    response = await call_next(request)

    response.headers["Strict-Transport-Security"] = (
        "max-age=31536000; includeSubDomains"
    )
    response.headers["X-Content-Type-Options"] = "nosniff"
    response.headers["Referrer-Policy"] = "no-referrer"
    response.headers["X-Frame-Options"] = "DENY"
    response.headers["Permissions-Policy"] = (
        "camera=(), microphone=(), geolocation=()"
    )

    return response
```

Register the middleware:

```python name=app/main.py
from app.middleware.security_headers import (
    security_headers_middleware,
)

app.middleware("http")(security_headers_middleware)
```

Enable HSTS only after confirming that the domain and applicable subdomains support HTTPS exclusively.

For browser-facing applications, also define a tested Content Security Policy.

## 10. Health Checks

```python name=app/routers/health.py
from fastapi import APIRouter, HTTPException, status
from sqlalchemy import text

from app.dependencies import DatabaseSession

router = APIRouter(prefix="/health", tags=["System"])


@router.get("/live")
def liveness() -> dict[str, str]:
    return {"status": "alive"}


@router.get("/ready")
def readiness(db: DatabaseSession) -> dict[str, str]:
    try:
        db.execute(text("SELECT 1"))
    except Exception:
        raise HTTPException(
            status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
            detail="Service unavailable",
        ) from None

    return {"status": "ready"}
```

- Liveness determines whether the process should restart.
- Readiness determines whether the instance should receive traffic.

Do not require authentication for internal orchestrator health checks, but restrict their network exposure.

## 11. Docker Compose for Local Development

```yaml name=compose.yaml
services:
  api:
    build:
      context: .
    init: true
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      ENVIRONMENT: development
      DATABASE_URL: postgresql+psycopg://api:development@database:5432/api
      JWT_SECRET: local-development-secret-change-me
      ALLOWED_HOSTS: '["localhost","127.0.0.1"]'
      CORS_ORIGINS: '["http://localhost:3000"]'
    depends_on:
      database:
        condition: service_healthy
    read_only: true
    tmpfs:
      - /tmp
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL

  database:
    image: postgres:17
    environment:
      POSTGRES_DB: api
      POSTGRES_USER: api
      POSTGRES_PASSWORD: development
    volumes:
      - database_data:/var/lib/postgresql/data
    healthcheck:
      test:
        - CMD-SHELL
        - pg_isready -U api -d api
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  database_data:
```

This configuration:

- Exposes the API only on the local machine.
- Uses a read-only application filesystem.
- Drops Linux capabilities.
- Prevents privilege escalation.
- Keeps the database port private to the Compose network.

The inline credentials are suitable only for isolated local development.

## 12. Read-Only Container Filesystem

```yaml name=compose.yaml
services:
  api:
    read_only: true
    tmpfs:
      - /tmp
```

An immutable filesystem makes persistence by an attacker more difficult.

Files that must persist should be written to explicitly mounted storage. Prefer private object storage for uploaded files.

---

## 13. Drop Linux Capabilities

```yaml name=compose.yaml
services:
  api:
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
```

The API normally does not need additional operating-system capabilities.

Add a capability only when there is a documented requirement.

## 14. Resource Limits

```yaml name=compose.yaml
services:
  api:
    mem_limit: 512m
    cpus: 1.0
    pids_limit: 200
```

Resource limits reduce the effect of memory leaks, fork bombs, and abusive workloads.

Choose limits using load testing and production measurements. Limits that are too low can cause unnecessary restarts.

## 15. Database Least Privilege

Use separate database accounts for separate responsibilities:

```text name=database-roles.txt
api_runtime → Reads and updates application data
migration   → Applies approved schema changes
backup      → Reads data required for backups
admin       → Reserved for controlled administrative work
```

The runtime account should not normally be able to:

- Create database users
- Grant permissions
- Drop the database
- Access unrelated schemas
- Apply arbitrary migrations

Never run the API using a database superuser account.

---

## 16. Database Migrations

Apply migrations as a controlled deployment step rather than from every API replica.

```bash name=scripts/migrate.sh
set -euo pipefail

alembic upgrade head
```

Recommended sequence:

```text name=deployment-sequence.txt
1. Back up critical data
2. Run backward-compatible migration
3. Deploy compatible application version
4. Monitor errors and latency
5. Remove deprecated schema only in a later release
```

Use an expand-and-contract strategy for breaking schema changes.

## 17. Graceful Shutdown

```python name=app/main.py
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    app.state.http_client = httpx.AsyncClient(
        timeout=httpx.Timeout(5.0),
    )

    yield

    await app.state.http_client.aclose()


app = FastAPI(lifespan=lifespan)
```

The deployment platform should send a termination signal and allow enough time for active requests to finish.

Avoid abruptly killing instances during deployments.

## 18. Container Vulnerability Scanning

Example with Trivy:

```bash name=scripts/scan-container.sh
set -euo pipefail

docker build --tag secure-api:scan .

trivy image \
  --exit-code 1 \
  --severity HIGH,CRITICAL \
  --ignore-unfixed \
  secure-api:scan
```

Scan:

- Application dependencies
- Operating-system packages
- Container images
- Infrastructure configuration
- Committed secrets

Review exceptions instead of permanently ignoring all findings.

## 20. CI Build and Scan

```yaml name=.github/workflows/container.yml
name: Container

on:
  pull_request:
  push:
    branches:
      - main

permissions:
  contents: read

jobs:
  test-build-scan:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write

    steps:
      - name: Check out source
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.13"
          cache: pip

      - name: Install dependencies
        run: |
          python -m pip install --requirement requirements.txt
          python -m pip install pytest pip-audit

      - name: Audit Python dependencies
        run: pip-audit

      - name: Run tests
        run: pytest

      - name: Build container
        run: docker build --tag secure-api:${{ github.sha }} .

      - name: Scan container
        uses: aquasecurity/trivy-action@0.30.0
        with:
          image-ref: secure-api:${{ github.sha }}
          severity: HIGH,CRITICAL
          ignore-unfixed: true
          exit-code: "1"
```

For stronger supply-chain protection:

- Pin actions to full commit SHAs.
- Use short-lived cloud identity federation.
- Sign published images.
- Generate provenance and an SBOM.
- Protect deployment environments with required approvals.

## 21. Deployment Strategies

### Rolling deployment

Gradually replaces old instances.

- Simple and resource-efficient
- Temporarily runs two versions
- Requires backward-compatible changes

### Blue-green deployment

Runs old and new environments simultaneously.

- Fast rollback by switching traffic
- Requires additional infrastructure
- Database changes still need compatibility

### Canary deployment

Sends a small percentage of traffic to the new release.

- Limits the impact of defects
- Requires good metrics and traffic control
- More operationally complex

Use canary or blue-green deployment for high-risk releases.

## 22. Deployment Validation

Run smoke tests after deployment.

```bash name=scripts/smoke-test.sh
set -euo pipefail

base_url="${BASE_URL:?BASE_URL is required}"

case "$base_url" in
  https://staging.example.com|https://api.example.com)
    ;;
  *)
    echo "Refusing unapproved target: $base_url" >&2
    exit 1
    ;;
esac

curl \
  --fail \
  --silent \
  --show-error \
  --max-time 10 \
  "${base_url}/health/live"
```

The strict URL allow-list prevents the script from sending requests to an unintended host.

Validate:

- Health and readiness
- Authentication
- Critical read and write paths
- Database migration status
- Error rate and latency
- Logs and metrics
- Background-job processing

## 23. Rollback Planning

Before deployment:

1. Back up critical data.
2. Confirm the backup can be restored.
3. Record the currently deployed image digest.
4. Ensure database changes are backward-compatible.
5. Define measurable rollback thresholds.

Rollback when indicators exceed approved limits, such as:

- Elevated `5xx` responses
- Increased latency
- Authentication failures
- Data-integrity errors
- Failed health checks

Rolling back application code may not reverse destructive database migrations. Plan schema rollback separately.

---

## 24. Production Security Checklist

- Run as a non-root user.
- Use a minimal, patched base image.
- Keep the filesystem read-only where possible.
- Drop unnecessary Linux capabilities.
- Never place secrets in images or source control.
- Use HTTPS and trusted-host validation.
- Disable debug mode and verbose production errors.
- Apply request, memory, CPU, and process limits.
- Use least-privileged database and cloud identities.
- Scan dependencies, images, configuration, and secrets.
- Use controlled migrations and backward-compatible releases.
- Configure health checks and graceful shutdown.
- Centralize logs, metrics, traces, and alerts.
- Maintain tested backup and rollback procedures.
- Deploy immutable images identified by digest.
