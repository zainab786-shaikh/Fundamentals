Lesson 23: Your First Real JSON-RPC A2A Request Handler

This is the lesson where you'll finally connect:

A2A Concepts
        +
Network Requests


Everything you've learned so far is hidden inside a JSON-RPC request.

The A2A Protocol uses structured request/response interactions for operations such as task submission and task retrieval, enabling interoperable communication between agents.

Problem Statement

Until now, we've been calling:

agent.process("Mumbai")


But in reality, another agent doesn't import your Python class.

Instead it sends:

{
  "id": 1,
  "method": "tasks/send",
  "params": {
    ...
  }
}


Question:

How does an A2A agent understand this request?

Think Like a Restaurant

Previously:

Customer
    |
Order:
Pizza


Now:

Customer
    |
Ticket #1
Order: Pizza


The ticket number helps track the request.

First JSON-RPC Request
{
  "id": 1,
  "method": "tasks/send",
  "params": {
    "city": "Mumbai"
  }
}


Let's decode it.

Field 1: id
"id": 1


Meaning:

Request Number 1


Later the response will contain:

"id": 1


so the caller knows:

This response belongs to request #1

Field 2: method
"method": "tasks/send"


Meaning:

What action should I perform?


Examples:

tasks/send
tasks/get
tasks/cancel

Field 3: params
"params"


Meaning:

Data needed to execute the action

Building a Request Handler

Imagine this request arrives:

request = {

    "id": 1,

    "method": "tasks/send",

    "params": {

        "city": "Mumbai"
    }
}

Naive Handler
def handle_request(request):

    return "ok"


Too simple.

Need to inspect:

request["method"]

First Real Handler
def handle_request(request):

    method = request["method"]

    if method == "tasks/send":

        return {
            "message":
            "Task accepted"
        }


Usage:

response = handle_request(request)

print(response)


Output:

{
    "message":
    "Task accepted"
}

Creating a Task

Remember:

Message
    ↓
Task


Let's create one.

def handle_request(request):

    if request["method"] == "tasks/send":

        return {

            "task_id": "W001",

            "status": "submitted"
        }


Output:

{
    "task_id": "W001",
    "status": "submitted"
}

Becoming More A2A-Like

Response should reference the original request id.

def handle_request(request):

    return {

        "id": request["id"],

        "result": {

            "task_id": "W001",

            "status": "submitted"
        }
    }


Output:

{
    "id": 1,

    "result": {

        "task_id": "W001",

        "status": "submitted"
    }
}

Why "result"?

Think:

Request
      ↓
Result


The protocol needs a clear place for successful execution output.

Simulating Work

Agent processes weather.

city = request["params"]["city"]

weather = f"Sunny in {city}"


Create artifact:

artifact = {

    "artifact_id": "A001",

    "content": weather
}

Final Response
{
    "id": 1,

    "result": {

        "task_id": "W001",

        "status": "completed",

        "artifact": {

            "artifact_id": "A001",

            "content": "Sunny in Mumbai"
        }
    }
}


Look familiar?

We've already learned:

Task
 ↓
Artifact


The protocol is just wrapping it differently.

Full Example
def handle_request(request):

    city = request["params"]["city"]

    artifact = {

        "artifact_id": "A001",

        "content": f"Sunny in {city}"
    }

    return {

        "id": request["id"],

        "result": {

            "task_id": "W001",

            "status": "completed",

            "artifact": artifact
        }
    }


request = {

    "id": 1,

    "method": "tasks/send",

    "params": {

        "city": "Mumbai"
    }
}

response = handle_request(request)

print(response)

{
 'id': 1,

 'result': {

    'task_id': 'W001',

    'status': 'completed',

    'artifact': {

       'artifact_id': 'A001',

    }
 }
}

Supporting Multiple Methods

What if the request is:

{
  "method":"tasks/get"
}


Now we need routing.

def handle_request(request):

    method = request["method"]

    if method == "tasks/send":

        return {
            "message":
            "Send Task"
        }

    elif method == "tasks/get":

        return {
            "message":
            "Get Task Status"
        }

Mental Model

Think:

method
=
Menu Option


Examples:

tasks/send

tasks/get

Retrieve task

tasks/cancel

Error Handling

Suppose:

{
  "method": "unknown_method"
}


Response:

{
    "id": 1,

    "error": {

        "code":
        "INVALID_METHOD",

        "message":
        "Unknown method"
    }
}

Why Errors Need Structure

Bad:

"Something went wrong"


Good:

{
    "code":"INVALID_METHOD",
    "message":"Unknown method"
}


Machines can understand it.

Major Insight

When you read an A2A request like:

{
  "id": 42,
  "method": "tasks/send",
  "params": {...}
}


translate it mentally into:

Request #42

Please create a task.


When you see:

{
  "id": 42,
  "result": {...}
}


translate it into:

Here's the task outcome.


That's all.
