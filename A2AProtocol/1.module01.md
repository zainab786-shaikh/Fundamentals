Lesson 1: Why Do We Need A2A?

Before learning the protocol, let's experience the problem A2A was created to solve.

The Agent2Agent (A2A) Protocol is an open standard that allows agents built by different teams, vendors, or frameworks to communicate using a common language.

Scenario

You are building a Travel Agent.

To plan a trip, it needs weather information from a Weather Agent.

User
  |
Travel Agent
  |
Weather Agent

Problem 1: Tight Coupling

Suppose Team A creates a Weather Agent.

class WeatherAgent:
    def get_weather(self, city):
        return f"Weather in {city}: Sunny"


Travel Agent directly calls it:

weather_agent = WeatherAgent()

result = weather_agent.get_weather("Mumbai")

print(result)


Output:

Weather in Mumbai: Sunny


Looks fine.

New Problem

A different company creates another Weather Agent.

class NewWeatherAgent:
    def fetch_weather(self, location):
        return f"Weather in {location}: Rainy"


Notice:

get_weather()


became

fetch_weather()


Travel Agent breaks:

weather_agent.get_weather("Mumbai")


Error:

AttributeError:
'NewWeatherAgent' has no attribute 'get_weather'

Why This Happens

The Travel Agent is assuming:

Method Name
Parameters
Return Format


Every new weather provider may choose different names.

Provider A -> get_weather(city)

Provider B -> fetch_weather(location)

Provider C -> weather(city_name)


Soon:

Travel Agent
   |
   +--- custom code for A
   +--- custom code for B
   +--- custom code for C


Messy.

Real-World Analogy

Imagine every website invented its own internet protocol.

Instead of:

HTTP


every website had:

MyProtocol
YourProtocol
TheirProtocol


Browsers would be impossible to build.

That's why HTTP exists.

Likewise, A2A gives agents a common communication model.

First A2A Idea: Don't Call Functions

Instead of calling functions directly:

weather_agent.get_weather("Mumbai")


send a standard message.

Think:

Agent A
      |
   Message
      |
Agent B

Simple Message Example
message = {
    "skill": "weather_lookup",
    "city": "Mumbai"
}


Travel Agent sends:

{
    "skill": "weather_lookup",
    "city": "Mumbai"
}


Weather Agent reads it and responds.

Minimal Simulation
Travel Agent
request = {
    "skill": "weather_lookup",
    "city": "Mumbai"
}

Weather Agent
def handle_message(message):

    if message["skill"] == "weather_lookup":

        city = message["city"]

        return {
            "status": "success",
            "weather": f"Sunny in {city}"
        }


Usage:

response = handle_message(request)

print(response)


Output:

{
    'status': 'success',
    'weather': 'Sunny in Mumbai'
}

What Improved?

Previously:

weather_agent.get_weather("Mumbai")


Travel Agent needed to know:

Class name
Method name
Parameters
Internal implementation

Now:

{
   "skill": "weather_lookup",
   "city": "Mumbai"
}


Travel Agent only knows:

I need weather_lookup


It doesn't care how Weather Agent is implemented.

Mental Model

Think about ordering food.

You don't enter the kitchen and call:

cook.make_pizza()


Instead you submit:

Order:
Pizza
Size: Large


The kitchen figures out how to prepare it.

A2A works similarly:

Agent
   |
Task/Message
   |
Another Agent

Key Takeaway

The first lesson of A2A is:

Agents should communicate through standardized messages rather than knowing each other's internal code.

This enables interoperability between independently built agents.

Exercise

Create two agents:

Calculator Agent
def handle_message(message):

    if message["skill"] == "add":
        return {
            "result": message["a"] + message["b"]
        }

Client
request = {
    "skill": "add",
    "a": 10,
    "b": 20
}

response = handle_message(request)

print(response)


Expected output:

{'result': 30}


This is not yet full A2A, but you've already learned the core idea behind the entire protocol:

Function Calls  →  Messages

Coupling        →  Interoperability
