Lesson 13: Real A2A Message Structure

Up to now we've used simplified messages:

{
    "skill": "weather_lookup",
    "city": "Mumbai"
}


That's great for learning, but now let's connect our understanding to the actual concepts used in the A2A Protocol. The protocol defines structured objects such as Messages, Parts, Tasks, and Artifacts rather than arbitrary dictionaries.

The Problem

Consider this:

{
    "skill": "weather_lookup",
    "city": "Mumbai"
}


Questions:

Who sent it?
Is it from a user or agent?
Does it contain text?
Does it contain a file?
Does it contain structured data?

Our simple format doesn't answer those questions.

A2A Solution: Message

A2A introduces a structured Message object.

Conceptually:

Message
   |
   +-- role
   |
   +-- parts

Why "role"?

Suppose three entities exist:

User
Travel Agent
Weather Agent


When a message arrives, we need to know who produced it.

Example:

{
    "role": "user"
}


or

{
    "role": "agent"
}

First Realistic Message
message = {
    "role": "user",
    "parts": [
        {
            "text": "What is the weather in Mumbai?"
        }
    ]
}

Visual Representation
Message
 |
 +-- role = user
 |
 +-- parts
        |
        +-- "What is the weather in Mumbai?"

Why Parts?

Imagine a request:

Analyze this PDF and summarize it.


The message may contain:

Text
+
PDF


One message can contain multiple pieces of content.

Hence:

parts = [...]


instead of:

text = ...

Example 1: Text Part
message = {
    "role": "user",
    "parts": [
        {
            "type": "text",
            "text": "Hello Agent"
        }
    ]
}

Example 2: Multiple Parts
message = {
    "role": "user",
    "parts": [

        {
            "type": "text",
            "text": "Analyze this report"
        },

        {
            "type": "file",
            "file_name": "sales.pdf"
        }
    ]
}

Mental Model

Think of email.

An email contains:

Body
Attachments
Images


Similarly:

Message
  |
  +-- Parts

Let's Create Python Classes

Instead of raw dictionaries:

from dataclasses import dataclass

@dataclass
class Part:
    type: str
    content: str


Message:

from dataclasses import dataclass

@dataclass
class Message:
    role: str
    parts: list


Usage:

part = Part(
    type="text",
    content="Hello Agent"
)

message = Message(
    role="user",
    parts=[part]
)

print(message)


Output:

Message(
   role='user',
   parts=[
      Part(...)
   ]
)

Connecting Message and Task

Earlier we learned:

Message → Task


Now we can represent that formally.

User sends:

message = {
    "role": "user",
    "parts": [
        {
            "text": "Generate sales report"
        }
    ]
}


Agent creates:

task = {
    "task_id": "123",
    "status": "submitted"
}

Connecting Task and Artifact

Task completes:

{
    "task_id": "123",
    "status": "completed"
}


Output:

artifact = {
    "artifact_id": "report-001",
    "content": "Sales grew 25%"
}

Full Flow
Message
    ↓
Task
    ↓
Task States
    ↓
Artifact

Let's Build Everything Together
message = {
    "role": "user",
    "parts": [
        {
            "type": "text",
            "text": "Generate Sales Report"
        }
    ]
}

task = {
    "task_id": "123",
    "status": "working"
}

artifact = {
    "artifact_id": "report-001",
    "content": "Sales increased 25%"
}

Mental Mapping

From our simplified course:

{
    "skill": "weather_lookup",
    "city": "Mumbai"
}


Think of it as becoming:

{
    "role": "user",

    "parts": [

        {
            "type": "text",

            "text":
            "Get weather for Mumbai"
        }

    ]
}


The idea is the same.

Only the structure becomes more general.

The Most Important Insight

Many beginners get overwhelmed when reading the protocol spec.

Don't.

Whenever you see:

Message
Parts
Tasks
Artifacts


translate it mentally into:

Request
Work Order
Progress
Result


That's all that's happening.
