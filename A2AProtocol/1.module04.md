Lesson 4: Messages

So far we've learned:

Agent Card  → Who am I?
Skill       → What can I do?


Now comes the next question:

How does one agent actually ask another agent to perform a skill?

The answer is: Message.

In the A2A Protocol, messages are the fundamental communication unit exchanged between agents.

The Problem

Suppose we have:

Calculator Agent


with skills:

add
subtract


The client knows the agent exists.

The client knows the skill name.

Now how does it request:

10 + 20


?

Bad Solution #1

Call a Python method directly.

calculator.add(10, 20)


Problem:

Client knows internal implementation.


This creates tight coupling.

Bad Solution #2

Send random data.

{
    "x": 10,
    "y": 20
}


What do x and y mean?

Add?

Subtract?

Multiply?

Nobody knows.

A2A Solution

Agents communicate through structured messages.

Think:

Human -> Email

Agent -> Message


A message clearly explains:

What skill is needed?
What data is required?

Our First Message

Let's ask the Calculator Agent to add numbers.

message = {
    "skill": "add",
    "a": 10,
    "b": 20
}


This says:

Use skill: add
Input A: 10
Input B: 20

Visual Flow
Client Agent
     |
     | Message
     v
{
   "skill": "add",
   "a": 10,
   "b": 20
}
     |
     v
Calculator Agent

Building the Receiver
class CalculatorAgent:

    def handle_message(self, message):

        if message["skill"] == "add":

            return {
                "result": message["a"] + message["b"]
            }

Sending the Message
agent = CalculatorAgent()

message = {
    "skill": "add",
    "a": 10,
    "b": 20
}

response = agent.handle_message(message)

print(response)


Output:

{'result': 30}

Why This Is Better

The client only knows:

Skill name
Input data


It doesn't know:

Class name
Method name
Database
Framework
Internal logic


That's the key idea behind interoperability.

Adding More Skills

Let's extend the agent.

class CalculatorAgent:

    def handle_message(self, message):

        skill = message["skill"]

        if skill == "add":
            return {
                "result": message["a"] + message["b"]
            }

        if skill == "subtract":
            return {
                "result": message["a"] - message["b"]
            }

Example 1
message = {
    "skill": "add",
    "a": 50,
    "b": 5
}


Output:

{
    "result": 55
}

Example 2
message = {
    "skill": "subtract",
    "a": 50,
    "b": 5
}


Output:

{
    "result": 45
}

Real-World Analogy

Imagine ordering food.

You don't enter the kitchen and call:

cook.make_burger()


Instead you submit:

Order:
Burger
Quantity: 1


The kitchen interprets the order.

Similarly:

{
    "skill": "add",
    "a": 10,
    "b": 20
}


is an order sent to an agent.

A More A2A-Like Structure

Actual A2A messages are richer than our simple examples and contain structured content parts.

Simplified representation:

message = {
    "role": "user",
    "parts": [
        {
            "text": "Add 10 and 20"
        }
    ]
}


Conceptually:

role  -> who sent it
parts -> content


We'll gradually evolve toward the full protocol structure.

Problem-Solving Exercise
Requirement

Create a Weather Agent.

Supported skill:

weather_lookup


Input:

{
    "skill": "weather_lookup",
    "city": "Mumbai"
}


Expected Output:

{
    "weather": "Sunny in Mumbai"
}

Solution
class WeatherAgent:

    def handle_message(self, message):

        if message["skill"] == "weather_lookup":

            city = message["city"]

            return {
                "weather": f"Sunny in {city}"
            }


agent = WeatherAgent()

message = {
    "skill": "weather_lookup",
    "city": "Mumbai"
}

print(agent.handle_message(message))


Output:

{
    'weather': 'Sunny in Mumbai'
}

What We've Learned

A Message answers:

What do you want me to do?
What inputs are required?


Structure:

Agent Card -> Discover agent

Skill      -> Choose capability

Message    -> Invoke capability

Next Lesson: Tasks

We'll encounter the first major limitation of messages:

What if the work takes 5 minutes?


For example:

Generate annual report
Analyze 10,000 documents
Create travel itinerary

A normal message-response model breaks down.

That's where Tasks enter the picture, and you'll finally see why A2A needs task IDs and task states.
