Today we'll learn something important:

How are these concepts actually sent over the network?

The A2A Protocol uses JSON-based protocol messages and task-oriented interactions between agents. The protocol specification defines standardized request/response patterns so independently built agents can interoperate.

Problem Statement

Our examples so far looked like:

{
    "skill": "weather_lookup",
    "city": "Mumbai"
}


That's fine for learning.

But imagine:

Agent A built by Google
Agent B built by Microsoft
Agent C built by SAP


How can they all communicate consistently?

They need a common message format.

Real-World Analogy

Think about a phone call.

You don't say:

Maybe I'll invent my own language.


Everyone agrees on:

Language
Grammar
Rules


Similarly, A2A agents need standard message formats.

Our Simplified Message

We previously sent:

{
    "skill": "weather_lookup",
    "city": "Mumbai"
}


Conceptually:

Do weather lookup for Mumbai

Real Protocol Style

A request contains:

Method
Parameters
Identifier


Think:

{
    "id": 1,
    "method": "tasks/send",
    "params": {...}
}

Understanding Each Field
id
"id": 1


Think:

Request Number


When the response returns:

"id": 1


you know which request it belongs to.

method
"method": "tasks/send"


Think:

What operation do you want?


Examples:

tasks/send
tasks/get
tasks/cancel

params
"params": {...}


Think:

Input Data

First A2A-Style Request

Let's ask a Weather Agent something.

{
  "id": 1,
  "method": "tasks/send",
  "params": {
    "message": {
      "role": "user",
      "parts": [
        {
          "type": "text",
          "text": "Weather in Mumbai"
        }
      ]
    }
  }
}


Don't panic.

You've already learned every concept inside this.

Translate It Into English
Request #1

Operation:
Send Task

Message:
Weather in Mumbai


That's all.

Agent Response

Agent might respond:

{
  "id": 1,
  "result": {
    "task_id": "T1",
    "status": "submitted"
  }
}


Translation:

Request accepted.

Created Task T1.

Mapping to What You Already Know

Before:

{
    "task_id": "T1",
    "status": "submitted"
}


Now:

{
    "id": 1,
    "result": {
        "task_id": "T1",
        "status": "submitted"
    }
}


Same idea.

Extra structure for interoperability.

Getting Task Status

Previously:

get_task("T1")


Protocol-style:

{
  "id": 2,
  "method": "tasks/get",
  "params": {
    "task_id": "T1"
  }
}

Response
{
  "id": 2,
  "result": {
    "task_id": "T1",
    "status": "working",
    "progress": 50
  }
}


Meaning:

Task T1 is 50% complete.

Completed Task

Response:

{
  "id": 2,
  "result": {
    "task_id": "T1",
    "status": "completed",
    "artifact": {
      "artifact_id": "A1",
      "content": "Sunny in Mumbai"
    }
  }
}


You've already learned:

Task
↓
Artifact


So this should look familiar.

Error Handling

Suppose an unknown skill is requested.

{
  "id": 1,
  "error": {
    "code": "INVALID_SKILL",
    "message": "Skill not supported"
  }
}


Translation:

I received your request,
but I cannot perform it.
