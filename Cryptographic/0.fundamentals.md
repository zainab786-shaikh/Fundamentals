## 1.1 Why encryption exists

**The story:** Alice wants to send Bob a note, but the note travels through many hands (post office, couriers, neighbors). Anyone along the way can read it, and anyone can change it.

She wants three things:

| Goal | Plain meaning | Question it answers |
|---|---|---|
| **Confidentiality** | Only Bob can read it | Who can see it? |
| **Integrity** | Nobody changed it on the way | Is this what Alice wrote? |
| **Availability** | Bob can actually get it | Can the message arrive at all? |

This is the **CIA triad**. Encryption mainly gives you confidentiality. Integrity needs extra tools (Section 3), which is why "just encrypt it" is often not enough.

---

## 1.2 Core terms

Alice writes a note in a language only she and Bob understand:

- **Plaintext:** the original message ("Meet at noon").
- **Algorithm (cipher):** the *method* of scrambling, like "shift each letter".
- **Key:** the *secret setting* the method uses, like "shift by 3".
- **Ciphertext:** the scrambled result ("Phhw dw qrrq").

An algorithm is like a lock design, and the key is the particular key that fits your lock.

```python name=caesar.py
def caesar(text: str, key: int) -> str:
    """Toy cipher: shift each letter by `key`. For learning only, never for real use."""
    out = []
    for ch in text:
        if ch.isalpha():
            base = ord('A') if ch.isupper() else ord('a')
            out.append(chr((ord(ch) - base + key) % 26 + base))
        else:
            out.append(ch)
    return "".join(out)

ciphertext = caesar("Meet at noon", key=3)
print(ciphertext)                 # Phhw dw qrrq
print(caesar(ciphertext, -3))     # Meet at noon  (decrypt = shift back)
```

## 1.3 Kerckhoffs's principle: the secret must be the key, not the method

**The story:** Alice's town invents a secret scrambling machine and hopes nobody learns how it works. Then a clerk leaves, a machine is stolen, and the secret is out. Now every message ever sent is exposed, and the town must invent a whole new machine.

Compare a town where everyone knows how the lock is built, but each person has their own key. If a key leaks, you change that one key.

> **Thought question:** Which would you trust more, a cipher only its inventor has seen, or one the whole world has attacked for 20 years and failed to break?

**The principle:** Assume the attacker knows your algorithm. Security must rest *only* on the key.

Our Caesar cipher fails the key side of this. The algorithm is public, so everything depends on the key, but there are only 25 possible keys:

```python name=brute_force.py
from caesar import caesar

intercepted = "Phhw dw qrrq"
for key in range(1, 26):
    print(key, caesar(intercepted, -key))
# Key 3 prints "Meet at noon". An attacker finds it instantly.
```

**Lesson:** A key must come from a space so huge that trying every one is impossible. Modern AES-256 has 2²⁵⁶ keys. Section 2 covers it.

---

## 1.4 Threat models: who are we defending against?

You can't defend against "everyone" without knowing what they can do. Think of three villains in the post office:

| Villain | Ability | Real-world example |
|---|---|---|
| **Eavesdropper (passive)** | Reads mail, changes nothing | Someone sniffing café Wi-Fi |
| **Man-in-the-middle (active)** | Reads, *modifies*, and forges mail | A rogue router or hostile network |
| **Replayer** | Saves a valid message and re-sends it later | Re-sending "Pay Mallory $100" ten times |

Encrypting hides content from the eavesdropper. It does *not* stop the other two. Here is a toy demonstration of the replay problem:

```python name=replay.py
from caesar import caesar

# Bank "encrypts" its commands. The attacker can't read them...
msg = caesar("PAY MALLORY 100", key=7)

# ...but doesn't need to. They just record and resend it.
for _ in range(3):
    print("Bank received:", caesar(msg, -7))   # Bank pays three times
```

The attacker never learned the key, and still won. The fix needs more than secrecy: proof that a message is **fresh** and **untampered**. This is why real protocols add nonces, timestamps, and authentication tags, which we'll meet in Sections 2, 3, and 7.

|---|---|

| Secret methods leak | Keep only the **key** secret (Kerckhoffs) |
| Small key space is guessable | Use huge keys and modern algorithms |

## 2.1 One shared key, and the problem it creates

**The story:** Alice and Bob own identical padlocks and identical keys. Alice locks a box, sends it, and Bob opens it. This is **symmetric encryption**: the same key locks and unlocks.

It's fast and simple, but it raises two problems:

1. **Key distribution:** How did Bob get the key without a spy copying it? You'd need a secure channel to set up a secure channel.
2. **Key explosion:** If 100 people each want private chats with everyone else, that is 4,950 separate keys.

> **Thought question:** If you already have a secure way to hand over the key, why not use it to send the message itself?

Section 4 solves this. For now, assume Alice and Bob already share a key.

---

## 2.2 Block ciphers and stream ciphers

Two ways to scramble a long message:

| Type | Analogy | How it works |
|---|---|---|
| **Block cipher** | Shredding a book page by page | Encrypts fixed-size chunks (AES uses 16 bytes) |
| **Stream cipher** | A one-time scribble over each letter | Generates a keystream and mixes it with the data byte by byte |

Both turn a short key into a long, random-looking stream or permutation. The attacker sees only noise.

---

## 2.3 AES: the world's standard block cipher

**AES** (Advanced Encryption Standard) was chosen in 2001 after a public competition, which is Kerckhoffs's principle in action. Its key sizes are 128, 192, or 256 bits. Even AES-128 is far beyond brute force.

At an intuitive level, AES repeatedly mixes and substitutes the bits of each 16-byte block, using the key, until the output looks random. You don't need the internals. You need to know **how to use it safely**, and that is where the next topics matter.

---

## 2.4 Modes of operation: AES alone isn't enough

AES encrypts exactly **one 16-byte block**. Real messages are longer. A **mode** says how to handle many blocks.

**ECB (the naive mode):** encrypt each block independently. The problem is that identical plaintext blocks produce identical ciphertext blocks, so patterns leak. The famous example is the "ECB penguin": an encrypted image whose outline is still visible.

```python name=ecb_leak.py
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
import os

key = os.urandom(32)  # AES-256 key
enc = Cipher(algorithms.AES(key), modes.ECB()).encryptor()

# Two identical 16-byte blocks
data = b"ATTACK AT DAWN!!" * 2
ct = enc.update(data) + enc.finalize()

print(ct[:16].hex())
print(ct[16:].hex())
# The two lines are identical, so the attacker learns the blocks repeat.
```

**The fix is to add variation per message and per block:**

| Mode | Idea | Status |
|---|---|---|
| **ECB** | Blocks are independent | Never use |
| **CBC** | Each block is mixed with the previous ciphertext block | Legacy. Needs separate integrity and is prone to padding-oracle attacks |
| **CTR** | Turns AES into a stream cipher using a counter | Good, but gives no integrity |
| **GCM** | CTR plus a built-in authentication tag | **Recommended** |

---

## 2.5 Authenticated encryption (AEAD)

Recall Section 1: an active attacker can modify messages. With plain CTR, flipping a ciphertext bit flips the matching plaintext bit, and nobody notices.

**The story:** Alice's locked box now also has a tamper-evident seal. If anyone touches it, Bob refuses to open it.

**AEAD** (Authenticated Encryption with Associated Data) does both at once:
- It encrypts the message (confidentiality).
- It attaches a **tag** that proves the data is unmodified (integrity).
- It can also authenticate extra **associated data**, such as a header, without encrypting it.

The two standard choices are **AES-GCM** and **ChaCha20-Poly1305**. ChaCha20 is a stream cipher that is fast on devices without AES hardware support.

```python name=aead_demo.py
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.exceptions import InvalidTag
import os

key = AESGCM.generate_key(bit_length=256)
aes = AESGCM(key)

nonce = os.urandom(12)                  # unique per message (see 2.6)
header = b"from=alice;to=bob"           # authenticated but not encrypted
ct = aes.encrypt(nonce, b"Meet at noon", header)

print("Decrypted:", aes.decrypt(nonce, ct, header))

# Now an attacker flips one bit
tampered = bytearray(ct)
tampered[0] ^= 1
try:
    aes.decrypt(nonce, bytes(tampered), header)
except InvalidTag:
    print("Tampering detected, message rejected")

# Changing the header is detected too
try:
    aes.decrypt(nonce, ct, b"from=mallory;to=bob")
except InvalidTag:
    print("Header tampering detected")
```

**Security takeaway:** Always use an AEAD mode, and never skip checking the tag. The library raises an exception for you, so don't swallow it.

## 2.6 Nonces: never reuse them

A **nonce** ("number used once") is a unique value per message. It ensures that encrypting the same text twice gives different ciphertext.

**The story:** Alice uses a fresh, random-looking scribble pattern for each note. If she reuses one pattern on two notes, a spy can compare the two scrambled notes. The pattern cancels out, and what remains is the two messages combined, which is easy to untangle.

Here is the failure with a stream-style cipher:

```python name=nonce_reuse.py
from cryptography.hazmat.primitives.ciphers.aead import ChaCha20Poly1305
import os

key = ChaCha20Poly1305.generate_key()
c = ChaCha20Poly1305(key)
nonce = os.urandom(12)

m1 = b"Launch at 0600 "
m2 = b"Abort the launch"[:len(m1)]

ct1 = c.encrypt(nonce, m1, None)[:len(m1)]   # same nonce used twice: the bug
ct2 = c.encrypt(nonce, m2, None)[:len(m2)]

# The attacker XORs the two ciphertexts and never touches the key.
xor_ct = bytes(a ^ b for a, b in zip(ct1, ct2))
xor_pt = bytes(a ^ b for a, b in zip(m1, m2))
print(xor_ct == xor_pt)   # True: the keystream cancelled out
```

The attacker now holds `m1 XOR m2`. If they can guess part of one message, they recover the other. With AES-GCM, nonce reuse is worse: it can also leak the authentication key, letting attackers **forge** messages.

**Rules:**
- Use a unique nonce for every message under the same key.
- Random 96-bit nonces are fine for moderate volumes. For huge volumes, use a counter or a misuse-resistant mode such as AES-GCM-SIV.
- The nonce is not secret. Send it along with the ciphertext.

## 3.1 What a hash is

**The story:** Imagine a machine that takes any document, from one word to a whole library, and prints a short fingerprint. The same document always gives the same fingerprint. Change a single comma and the fingerprint looks completely different. And you cannot rebuild the document from the fingerprint.

That is a **cryptographic hash function**. It has three key properties:

| Property | Plain meaning | Why it matters |
|---|---|---|
| **Preimage resistance** | From a fingerprint, you can't find an input that produces it | Hashes can't be "reversed" |
| **Second-preimage resistance** | Given one document, you can't craft a different one with the same fingerprint | Nobody can swap in a forged file |
| **Collision resistance** | You can't find *any* two documents with the same fingerprint | Signatures and certificates depend on it |

```python name=hash_demo.py
import hashlib

print(hashlib.sha256(b"Pay Bob $100").hexdigest())
print(hashlib.sha256(b"Pay Bob $101").hexdigest())
# One character changed, and the output is completely different.
# The output is always 32 bytes, however long the input is.
```

> **Thought question:** A hash is not encryption. There is no key and no way back. So what is it good for?

Answer: **verifying that data is unchanged**, for example file downloads, Git commits, and certificate signatures.

---

## 3.2 SHA-2, SHA-3, and the retired hashes

| Algorithm | Status | Note |
|---|---|---|
| **MD5** | Broken | Collisions can be made in seconds |
| **SHA-1** | Broken | Practical collision shown in 2017 (SHAttered), so browsers rejected SHA-1 certificates |
| **SHA-256 / SHA-512 (SHA-2)** | Good | The workhorse today |
| **SHA-3** | Good | A different internal design, kept as a backup if SHA-2 ever weakens |

**The story of why "broken" matters:** If an attacker can create two documents with the same fingerprint, they can get a CA to sign a harmless one and then substitute the malicious one. The signature still "matches." That is why old hashes were retired from certificates.

**Rule:** Use SHA-256 or better, and never use MD5 or SHA-1 for security.

---

## 3.3 MACs and HMAC: a fingerprint only key holders can make

**The problem:** A plain hash gives no protection against an active attacker. Mallory changes the message, recomputes the hash, and swaps both. Nothing looks wrong.

**The fix:** Mix a **secret key** into the fingerprint. This is a **MAC** (Message Authentication Code). Only someone who knows the key can create or check a valid one. **HMAC** is the standard way to build a MAC from a hash.

```python name=hmac_demo.py
import hmac, hashlib, os

key = os.urandom(32)
msg = b"Pay Bob $100"
tag = hmac.new(key, msg, hashlib.sha256).digest()

def verify(key, msg, tag) -> bool:
    expected = hmac.new(key, msg, hashlib.sha256).digest()
    return hmac.compare_digest(expected, tag)   # constant-time comparison

print(verify(key, msg, tag))                  # True
print(verify(key, b"Pay Bob $999", tag))      # False: tampered
print(verify(os.urandom(32), msg, tag))       # False: wrong key (forgery)
```

**Security note:** Always compare tags with `hmac.compare_digest`, not `==`. A normal comparison stops at the first mismatch, and an attacker can measure the timing to guess the tag byte by byte (a timing side channel).

This is what the AEAD tag from Section 2 does, using a similar idea. Encryption keeps the message secret, and the MAC proves it wasn't altered.

## 3.4 Password hashing: a different problem

**The story:** A website stores passwords. One night the database leaks. What did the site store?

| Storage | Result after the leak |
|---|---|
| Plaintext | Every account is instantly compromised |
| Encrypted | The key is usually on the same server, so it leaks too |
| Plain SHA-256 | Attackers test billions of guesses per second on GPUs, and common passwords fall in minutes |
| Salted, slow hash | Each guess is expensive, and precomputed tables are useless |

Two ideas fix this:

1. **Salt:** a random value stored next to each hash. Two users with the password `hunter2` get different hashes, so one precomputed "rainbow table" can't crack everyone.
2. **Deliberate slowness (key stretching):** a normal hash is fast, which is *bad* for passwords. Password hashes are tuned to cost real time and memory, so each guess costs the attacker too.

**Use Argon2id** (the current recommendation), or bcrypt or scrypt if Argon2 isn't available.

```python name=password_demo.py
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher()   # sensible defaults; salt is generated automatically

stored = ph.hash("correct horse battery staple")
print(stored)   # contains the algorithm, parameters, salt, and hash

try:
    ph.verify(stored, "correct horse battery staple")
    print("Login OK")
    ph.verify(stored, "wrong guess")
except VerifyMismatchError:
    print("Login rejected")

# Re-hash at login if parameters have been strengthened since
if ph.check_needs_rehash(stored):
    stored = ph.hash("correct horse battery staple")
```

**Security takeaways:**
- Never invent your own password scheme, and never use plain SHA-256 or MD5 for passwords.
- Add rate limiting and lockout to login, because slow hashing doesn't stop online guessing.
- Return the same generic error for "unknown user" and "wrong password."

# Section 4: Asymmetric (Public-Key) Cryptography

Install: `pip install cryptography`

---

## 4.1 The core idea: a lock anyone can close, but only you can open

**The story:** Bob makes a thousand identical open padlocks and hands them out freely, to friends, strangers, and even spies. He keeps the only key. Alice snaps one of Bob's padlocks onto her box and sends it. Even Alice can't reopen it, and neither can the spies who also hold Bob's padlocks. Only Bob can.

This solves the key-distribution problem from Section 2. Nothing secret ever had to travel.

| Piece | Who has it | Role |
|---|---|---|
| **Public key** | Everyone | Encrypts, or verifies signatures |
| **Private key** | Only the owner | Decrypts, or creates signatures |

> **Thought question:** If the padlock is public, what stops a spy from handing Alice *their own* padlock and claiming it's Bob's? Hold that thought. It is the whole reason certificates exist (Section 6).

---

## 4.2 Why does this work? One-way problems

You don't need the math, just the intuition: some operations are **easy forwards and brutally hard backwards**.

- **Mixing paint:** Mixing two colors is easy. Separating them again is nearly impossible.
- **Multiplying primes:** Multiplying two huge primes is instant. Finding them from the product is infeasible. This is the basis of **RSA**.
- **Elliptic curves:** A similar one-way trick on points of a curve. It gives the same security with much smaller keys. This is **ECC**.

The public key is the "easy direction" result. The private key is the secret that makes the "hard direction" easy for its owner.

---

## 4.3 RSA, ECDSA, and Ed25519

| Algorithm | Used for | Notes |
|---|---|---|
| **RSA** | Encryption, signatures | Older, large keys (2048-bit minimum, 3072 preferred) |
| **ECDSA** | Signatures | Small keys, but needs good randomness per signature |
| **Ed25519** | Signatures | Modern, fast, hard to misuse, so a good default |
| **X25519** | Key exchange | Modern default (see 4.4) |

```python name=rsa_demo.py
from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes

private_key = rsa.generate_private_key(public_exponent=65537, key_size=3072)
public_key = private_key.public_key()

oaep = padding.OAEP(
    mgf=padding.MGF1(algorithm=hashes.SHA256()),
    algorithm=hashes.SHA256(),
    label=None,
)

ct = public_key.encrypt(b"Meet at noon", oaep)   # anyone can do this
print(private_key.decrypt(ct, oaep))             # only the key owner can
```

**Security note:** Always use OAEP padding. Raw or PKCS#1 v1.5 encryption padding has known attacks. RSA can only encrypt tiny messages, which is why 4.6 exists.

---

## 4.4 Key exchange and forward secrecy

**The story (the paint analogy):** Alice and Bob each pick a secret color. They publicly agree on a common base color, such as yellow. Each mixes their secret into it and sends the mixture across the open room. Each then mixes their own secret into the *other's* mixture. Both now hold the identical final color. A spy saw only the mixtures, and un-mixing paint is infeasible.

That is **Diffie-Hellman**. Two strangers derive a shared secret over a watched channel, with no prior secret.

```python name=ecdh_demo.py
from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

alice_priv = X25519PrivateKey.generate()
bob_priv = X25519PrivateKey.generate()

# Only the public halves cross the wire
alice_shared = alice_priv.exchange(bob_priv.public_key())
bob_shared = bob_priv.exchange(alice_priv.public_key())
print(alice_shared == bob_shared)   # True

# Never use the raw shared secret directly: derive a proper key
def derive(shared: bytes) -> bytes:
    return HKDF(algorithm=hashes.SHA256(), length=32,
                salt=None, info=b"chat v1").derive(shared)

print(derive(alice_shared) == derive(bob_shared))   # True
```

**Forward secrecy:** Alice and Bob generate **fresh temporary (ephemeral) keys** for each session and then throw them away. If a long-term key is stolen next year, old recorded traffic still can't be decrypted. Without this, an attacker can record everything now and decrypt it later. TLS 1.3 requires forward secrecy.

**Caveat:** Plain Diffie-Hellman doesn't prove *who* you're talking to. A man-in-the-middle can run one exchange with Alice and another with Bob. Signatures fix that.

## 4.5 Digital signatures

**The story:** Bob signs a letter with a wax seal that only his ring can make. Anyone who knows what Bob's seal looks like (his public key) can check it. Two things follow:

- **Authenticity:** it came from the holder of the private key.
- **Non-repudiation:** Bob can't later claim he didn't sign it, because no one else had the ring.

This differs from an HMAC (Section 3). With HMAC, both sides share the key, so either could have made the tag. With a signature, only the signer can.

```python name=sign_demo.py
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey
from cryptography.exceptions import InvalidSignature

priv = Ed25519PrivateKey.generate()
pub = priv.public_key()

doc = b"I, Bob, agree to pay Alice $100"
sig = priv.sign(doc)

try:
    pub.verify(sig, doc)
    print("Valid signature")
    pub.verify(sig, b"I, Bob, agree to pay Alice $1000")
except InvalidSignature:
    print("Forgery detected")
```

Under the hood, the document is hashed first and the hash is signed. That's why collision-resistant hashes matter (Section 3).

---

## 4.6 Hybrid encryption: the best of both

| | Symmetric (AES) | Asymmetric (RSA/ECC) |
|---|---|---|
| Speed | Very fast | Slow |
| Message size | Unlimited | Tiny |
| Key distribution | Hard | Easy |

Each has the strength the other lacks, so real systems **combine them**:

1. Use asymmetric crypto (key exchange) to agree on a temporary symmetric key.
2. Use that key with AES-GCM or ChaCha20-Poly1305 for the actual data.

```python name=hybrid_demo.py
import os
from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.hazmat.primitives import hashes

def session_key(shared: bytes) -> bytes:
    return HKDF(algorithm=hashes.SHA256(), length=32,
                salt=None, info=b"hybrid demo").derive(shared)

bob_priv = X25519PrivateKey.generate()        # Bob's key; public half is published
alice_eph = X25519PrivateKey.generate()       # Alice's one-time key

# Alice encrypts
key = session_key(alice_eph.exchange(bob_priv.public_key()))
nonce = os.urandom(12)
ct = AESGCM(key).encrypt(nonce, b"A long message... " * 100, None)
# Alice sends: alice_eph.public_key(), nonce, ct

# Bob decrypts
key_b = session_key(bob_priv.exchange(alice_eph.public_key()))
print(AESGCM(key_b).decrypt(nonce, ct, None)[:19])
```

This is the pattern behind HTTPS, Signal, and encrypted email. Sections 7 and 8 are variations of it.

**Note:** This demo is unauthenticated. Alice doesn't know that the public key she holds is really Bob's. Fixing that is Section 6.

|---|---|

# Section 5: Randomness and Key Management

Install: `pip install cryptography`

---

## 5.1 Randomness: the foundation under everything

**The story:** Alice picks a secret key by asking, "What's a number nobody would guess?" She types her birthday. An attacker tries birthdays first and finds the key in minutes. The cipher was perfect, but the key was guessable.

Every key, nonce, and salt we've used so far came from `os.urandom`. If those values are predictable, the strongest algorithm is worthless.

| Source | Predictable? | Use for security? |
|---|---|---|
| `random` module (Mersenne Twister) | Yes. Seeing about 600 outputs reveals its internal state | **Never** |
| Timestamp or PID as seed | Yes. The attacker guesses the time | **Never** |
| Human-chosen "random" | Yes. Humans are predictable | **Never** |
| **CSPRNG** (`os.urandom`, `secrets`) | No | **Always** |

A **CSPRNG** (cryptographically secure pseudo-random number generator) is seeded by the operating system with real unpredictable events (hardware noise, timing jitter). It expands that seed into as many unpredictable bytes as you need.

```python name=randomness.py
import random, secrets, os

# WRONG: seeded with a guessable value, so fully reproducible
random.seed(1730000000)           # e.g. "the current time"
weak_key = random.getrandbits(128)

random.seed(1730000000)           # the attacker guesses the same seed
print(weak_key == random.getrandbits(128))   # True: the attacker has your key

# RIGHT: draws from the OS CSPRNG
key = secrets.token_bytes(32)     # same quality as os.urandom(32)
token = secrets.token_urlsafe(32) # for session IDs, reset links, API tokens
print(key.hex(), token)
```

**Real-world failures:**
- **Debian OpenSSL (2006-2008):** a code change reduced the randomness to about 32,000 possible keys, so all generated SSH and TLS keys were guessable.
- **Android Bitcoin wallets (2013):** weak random numbers in signatures leaked private keys.
- **Sony PS3:** ECDSA used the same "random" value every time, which exposed the signing key.

**Rule:** Use `secrets` or `os.urandom` for anything security-related, and never use `random`.

> **Thought question:** A freshly booted virtual machine or embedded device has seen almost no unpredictable events. Is its randomness good yet? (Modern OSes handle this, but it's a classic cause of weak keys.)

---

## 5.2 Key lifecycle: generate, store, rotate, revoke

A key isn't a one-time choice. It has a life:

| Stage | Question | Good practice |
|---|---|---|
| **Generate** | Is it unpredictable? | CSPRNG, library functions, never hand-made |
| **Store** | Where does it live? | Not in source code, not in Git, not in logs |
| **Use** | Who can reach it? | Least privilege, one key per purpose |
| **Rotate** | What if it leaked unnoticed? | Replace on a schedule, which limits the damage window |
| **Revoke / destroy** | What if we know it leaked? | Disable it quickly and re-encrypt or re-issue |

**The story:** A developer hardcodes an API key and commits it. Bots scan public repos and find it within minutes. Deleting the file later doesn't help, because Git history remembers. The only real fix is **revoking the key**.

```python name=key_storage.py
import os

# WRONG: hardcoded, ends up in Git, logs, and screenshots
API_KEY = "sk_live_51H8..."

# BETTER: injected by the environment, which is set by a secrets manager or CI
api_key = os.environ.get("API_KEY")
if not api_key:
    raise RuntimeError("API_KEY is not set")   # fail closed, never fall back to a default
```

**Rotation made easy: key IDs.** Tag each ciphertext with the key version that made it. You can then add a new key, decrypt old data with the old one, and re-encrypt gradually. The `cryptography` library has a ready-made tool for this idea:

```python name=rotation.py
from cryptography.fernet import Fernet, MultiFernet

old = Fernet(Fernet.generate_key())
token = old.encrypt(b"customer record")       # encrypted under the old key

new = Fernet(Fernet.generate_key())
mf = MultiFernet([new, old])                  # first key encrypts, all keys can decrypt

print(mf.decrypt(token))                      # old data still readable
rotated = mf.rotate(token)                    # re-encrypted under the new key
print(new.decrypt(rotated))                   # now the old key can be retired
```

**Security notes:**
- Never log keys, tokens, or plaintext secrets.
- Add secret scanning to CI (for example GitHub secret scanning and push protection).
- Use separate keys per environment and purpose, so a leaked test key doesn't open production.
- Plan for revocation *before* you need it.

## 5.3 HSMs, KMS, and secrets managers

**The problem:** Even with environment variables, the key sits in your app's memory and on your server. If the server is breached, the key goes with it.

**The idea:** Keep the key in a vault that **performs operations for you but never hands the key out**. Your app says "decrypt this" and receives only the result.

| Tool | Analogy | What it does |
|---|---|---|
| **HSM** (Hardware Security Module) | A bank vault with a built-in calculator | Tamper-resistant hardware. Keys are generated inside and can't be exported |
| **KMS** (Key Management Service: AWS KMS, Azure Key Vault, Google Cloud KMS) | The vault, rented as a service | Manages keys, access policies, audit logs, and rotation, usually backed by HSMs |
| **Secrets manager** (Key Vault secrets, AWS Secrets Manager, HashiCorp Vault) | A safe-deposit box for passwords and tokens | Stores and delivers secrets at runtime with access control and auditing |

**Envelope encryption** is the pattern that ties them together and extends the hybrid idea from Section 4:

1. The KMS holds a master key (the **KEK**, key-encryption key) that never leaves it.
2. For each piece of data, your app generates a fresh **data key (DEK)** and encrypts the data with it using AES-GCM.
3. The KMS encrypts the DEK, and you store the **wrapped DEK** next to the data.
4. To read, you ask the KMS to unwrap the DEK, then decrypt locally.

```python name=envelope.py
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

# Stand-in for a real KMS. In production this key never leaves the KMS or HSM.
class FakeKMS:
    def __init__(self):
        self._kek = AESGCM.generate_key(bit_length=256)   # the master key stays inside
    def wrap(self, dek: bytes) -> bytes:
        nonce = os.urandom(12)
        return nonce + AESGCM(self._kek).encrypt(nonce, dek, b"dek-wrap")
    def unwrap(self, wrapped: bytes) -> bytes:
        return AESGCM(self._kek).decrypt(wrapped[:12], wrapped[12:], b"dek-wrap")

kms = FakeKMS()

# Encrypt
dek = AESGCM.generate_key(bit_length=256)            # fresh key per record
nonce = os.urandom(12)
ct = AESGCM(dek).encrypt(nonce, b"credit card 4111...", None)
record = {"wrapped_dek": kms.wrap(dek), "nonce": nonce, "ct": ct}
del dek                                              # the plaintext DEK isn't stored

# Decrypt
dek2 = kms.unwrap(record["wrapped_dek"])
print(AESGCM(dek2).decrypt(record["nonce"], record["ct"], None))
```

**Why this is good:**
- The master key never touches your app, and every use is logged and permissioned.
- Rotating the master key means re-wrapping small DEKs, not re-encrypting terabytes.
- A stolen database is useless without KMS access.

**Caveat:** The KMS becomes the crown jewel, so protect it with least-privilege access policies, audit logging, and alerts on unusual use.

| Problem | Solution |
|---|---|
| Predictable "random" values break good ciphers | CSPRNG only: `secrets`, `os.urandom` |
| Keys leak through code, Git, and logs | Environment or secrets manager, with secret scanning |
| A long-lived key is a long-term risk | Rotate on a schedule, and use key IDs or MultiFernet |
| A server breach exposes keys in memory | KMS or HSM, where the key never leaves the vault |
| Re-encrypting everything on rotation is costly | Envelope encryption (DEK wrapped by KEK) |

## 6.1 The trust problem

**The story:** You type `mybank.com`. A stranger on the café Wi-Fi answers and says, "Here's the bank's public key." Everything from Section 4 works perfectly, but you are now encrypting to the **stranger**. Strong crypto with the wrong person is worthless.

> **Thought question:** How can you verify an identity over a channel you can't trust, with no prior contact?

**The solution:** A trusted third party vouches for the binding "this name ↔ this public key" using a **digital signature** (Section 4.5). That signed statement is a **certificate**. It works like a passport: a government you trust signs a statement that this photo belongs to this name.

---

## 6.2 Anatomy of an X.509 certificate

| Field | Plain meaning |
|---|---|
| **Subject** | Who the certificate is for |
| **SAN** (Subject Alternative Name) | The hostnames it's valid for (`example.com`, `www.example.com`). Browsers check this, not the old CN field |
| **Public key** | The key being vouched for |
| **Issuer** | Who signed it |
| **Validity** | Not-before and not-after dates |
| **Key usage / EKU** | What the key may do (for example, web server authentication) |
| **Basic constraints** | Whether this certificate may itself sign other certificates (CA:TRUE/FALSE) |
| **Signature** | The issuer's signature over all of the above |

Any change to any field breaks the signature, which is the same hash-and-sign idea from Sections 3 and 4.

```python name=make_cert.py
import datetime
from cryptography import x509
from cryptography.x509.oid import NameOID
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.asymmetric import ec

key = ec.generate_private_key(ec.SECP256R1())
name = x509.Name([x509.NameAttribute(NameOID.COMMON_NAME, "demo.local")])
now = datetime.datetime.now(datetime.timezone.utc)

cert = (
    x509.CertificateBuilder()
    .subject_name(name)
    .issuer_name(name)                      # same as subject, so self-signed
    .public_key(key.public_key())
    .serial_number(x509.random_serial_number())
    .not_valid_before(now)
    .not_valid_after(now + datetime.timedelta(days=30))
    .add_extension(x509.SubjectAlternativeName([x509.DNSName("demo.local")]), critical=False)
    .add_extension(x509.BasicConstraints(ca=False, path_length=None), critical=True)
    .sign(key, hashes.SHA256())
)

print(cert.subject, "| issued by:", cert.issuer)
print("SAN:", cert.extensions.get_extension_for_class(x509.SubjectAlternativeName).value)
```

## 6.3 Certificate Authorities and the chain of trust

Nobody can personally know every website's key, so trust is delegated in a chain:

```
Root CA  (self-signed, kept offline, trusted by your device)
   └── Intermediate CA  (signed by the root, used day to day)
          └── Leaf certificate  (example.com, signed by the intermediate)
```

**Why intermediates?** The root key is so valuable that it stays in an offline HSM. If an intermediate is compromised, only that branch is revoked. The root survives.

**Verification:** Your browser receives the leaf and intermediate. It checks that the leaf's signature verifies under the intermediate's key, and that the intermediate's signature verifies under a root it already trusts. It also checks dates, hostname, and key usage.

```python name=chain_demo.py
import datetime
from cryptography import x509
from cryptography.x509.oid import NameOID
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.asymmetric import ec

now = datetime.datetime.now(datetime.timezone.utc)
def name(cn): return x509.Name([x509.NameAttribute(NameOID.COMMON_NAME, cn)])

def issue(subject_cn, subject_key, issuer_cn, issuer_key, is_ca, days, san=None):
    b = (x509.CertificateBuilder()
         .subject_name(name(subject_cn)).issuer_name(name(issuer_cn))
         .public_key(subject_key.public_key())
         .serial_number(x509.random_serial_number())
         .not_valid_before(now).not_valid_after(now + datetime.timedelta(days=days))
         .add_extension(x509.BasicConstraints(ca=is_ca, path_length=None), critical=True))
    if san:
        b = b.add_extension(x509.SubjectAlternativeName([x509.DNSName(san)]), critical=False)
    return b.sign(issuer_key, hashes.SHA256())

root_k, inter_k, leaf_k = (ec.generate_private_key(ec.SECP256R1()) for _ in range(3))
root  = issue("Demo Root CA", root_k, "Demo Root CA", root_k, True, 3650)
inter = issue("Demo Intermediate", inter_k, "Demo Root CA", root_k, True, 1825)
leaf  = issue("shop.demo", leaf_k, "Demo Intermediate", inter_k, False, 90, san="shop.demo")

# Verify each link: raises InvalidSignature if forged
leaf.verify_directly_issued_by(inter)
inter.verify_directly_issued_by(root)
print("Chain verified: leaf -> intermediate -> root")

# A forged leaf signed by an attacker's key fails
evil_k = ec.generate_private_key(ec.SECP256R1())
forged = issue("shop.demo", evil_k, "Demo Intermediate", evil_k, False, 90, san="shop.demo")
try:
    forged.verify_directly_issued_by(inter)
except Exception as e:
    print("Forgery rejected:", type(e).__name__)
```

## 6.4 Trust stores

**Where does the first trust come from?** From a **trust store**, a list of root certificates shipped with your operating system or browser (Windows, macOS, Linux, Firefox, Chrome). It is the one thing you must trust without proof.

- Root programs (Microsoft, Apple, Mozilla, Google) audit CAs and remove ones that misbehave. DigiNotar (2011) and Symantec (2017-18) were distrusted this way.
- Adding a root to your trust store lets that root vouch for **any** site, so corporate proxies and malware abuse this. Only install roots you fully trust.

---

## 6.5 Certificate lifecycle

1. **Generate a key pair** on the server. The private key never leaves it.
2. **Create a CSR** (Certificate Signing Request): your public key and requested names, signed with your private key to prove you hold it.
3. **CA validates control** of the domain. This is the real proof of ownership.
4. **CA issues** the signed certificate.
5. **Install, monitor, renew.**

**Let's Encrypt and ACME:** The ACME protocol automates this. The CA gives your server a challenge, such as placing a token at `http://yourdomain/.well-known/acme-challenge/...` or adding a DNS TXT record. If you can do it, you control the domain. Certificates are free and short-lived (90 days, with shorter lifetimes being phased in), so automation is **required**, not optional.

```python name=csr_demo.py
from cryptography import x509
from cryptography.x509.oid import NameOID
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import ec

key = ec.generate_private_key(ec.SECP256R1())

csr = (x509.CertificateSigningRequestBuilder()
       .subject_name(x509.Name([x509.NameAttribute(NameOID.COMMON_NAME, "shop.demo")]))
       .add_extension(x509.SubjectAlternativeName([x509.DNSName("shop.demo")]), critical=False)
       .sign(key, hashes.SHA256()))

print(csr.is_signature_valid)                       # True: proves possession of the key
print(csr.public_bytes(serialization.Encoding.PEM).decode()[:60], "...")
# Only the CSR goes to the CA. The private key stays with you.
```

**Security notes:** Protect the private key file (permissions `600`, or an HSM or KMS), and monitor expiry. Expired certificates are a common cause of outages.

## 6.6 Revocation: taking back a trusted certificate

**The problem:** A server's private key leaks, but its certificate is valid for 80 more days. How do you tell the world to stop trusting it?

| Mechanism | How it works | Weakness |
|---|---|---|
| **CRL** | The CA publishes a big list of revoked serial numbers | Large and slow, and clients often cache it |
| **OCSP** | The browser asks the CA "is serial X still good?" | Slows connections, **leaks which sites you visit**, and often "fails open" if the CA is unreachable |
| **OCSP stapling** | The server fetches a signed, time-stamped OCSP answer and attaches it to the handshake | Fixes privacy and latency |
| **Short-lived certificates** | Certificates expire in days, so revocation matters less | Needs full automation |

The industry is moving toward short-lived certificates because revocation has never worked reliably. Expiry is the dependable revocation.

---

## 6.7 Certificate Transparency (CT)

**The problem:** A CA, through a breach or a mistake, issues a certificate for `yourbank.com` to an attacker. Nobody notices.

**The solution:** Public, append-only logs. CAs must record every certificate in these logs, and browsers require proof of logging (an SCT) before they accept a certificate. Domain owners can watch the logs (for example with crt.sh) and detect certificates they didn't request.

The principle is that **misissuance can't be prevented, but it can be made impossible to hide**. Compare a notary's public ledger: forgeries are still possible, but they leave a trace.

---

## 6.8 Self-signed certificates, private CAs, and mTLS

| Option | Use when | Risk |
|---|---|---|
| **Self-signed** | Quick local testing | No third party vouches for it, so clients get warnings. Tempting to "just ignore" them |
| **Private CA** | Internal services, devices, and company networks | You must distribute and protect your own root |
| **mTLS** (mutual TLS) | Service-to-service, APIs, zero-trust networks | More certificates to manage |

**mTLS:** In normal HTTPS only the **server** shows a certificate. In mTLS the **client** also presents one, so both sides prove identity. This is like both parties showing passports at the border instead of only one.

```python name=trust_the_right_way.py
import ssl, urllib.request

# WRONG: "fixes" the warning by disabling verification, which invites man-in-the-middle
bad = ssl.create_default_context()
bad.check_hostname = False
bad.verify_mode = ssl.CERT_NONE

# RIGHT: keep verification on, and trust your private CA explicitly
ctx = ssl.create_default_context(cafile="my-private-root.pem")   # trust only this root
# For mTLS, the client also presents its own certificate:
# ctx.load_cert_chain(certfile="client.crt", keyfile="client.key")

# urllib.request.urlopen("https://internal.service.local", context=ctx)
```

**Security takeaway:** Never disable certificate validation to make an error go away. Instead, fix the trust (add the right CA) and keep hostname checking on.

# Section 7: TLS, Encryption in HTTP (HTTPS)

No new installs. We use Python's standard `ssl` and `socket` modules.

---

## 7.1 HTTP vs HTTPS: what is and isn't protected

**The story:** Plain HTTP is a postcard. Every courier, café router, and ISP can read it and rewrite it. HTTPS is HTTP inside a sealed, tamper-evident envelope, and TLS builds that envelope.

| Item | Visible to an observer on HTTPS? |
|---|---|
| Page content, form data, passwords | Hidden |
| URL path and query string (`/account?id=7`) | Hidden |
| Headers and cookies | Hidden |
| Destination IP address | **Visible** |
| Hostname (via SNI, see 7.8) | **Visible** unless ECH is used |
| Approximate size and timing of traffic | **Visible** |

**Takeaway:** HTTPS gives confidentiality and integrity for the content. It doesn't hide who you talk to, or roughly how much.

---

## 7.2 The TLS handshake, step by step

TLS has one job: in a few milliseconds, two strangers must **agree on a secret key** and **verify the server's identity**. It reuses every idea from Sections 2 to 6.

**TLS 1.3 handshake (1 round trip):**

```
Client                                         Server
  | ClientHello: versions, ciphers,              |
  |   my ephemeral X25519 public key  ---------> |
  |                                              | picks cipher, makes own ephemeral key
  | <--------- ServerHello: its public key       |
  |   (both sides now derive the shared key; everything below is encrypted)
  | <--------- Certificate chain                 |
  | <--------- CertificateVerify: signature over the handshake
  | <--------- Finished (MAC over the transcript)|
  | Finished  ------------------------------->   |
  |============ encrypted application data ======|
```

How each piece maps to what you learned:

| Step | Purpose | Section |
|---|---|---|
| Ephemeral key exchange (X25519) | Agree on a secret over a watched channel, with forward secrecy | 4.4 |
| Certificate chain | Prove the public key belongs to the hostname | 6 |
| CertificateVerify signature | Prove the server holds the matching **private** key (a stolen certificate alone is useless) | 4.5 |
| Finished message (MAC) | Prove nobody tampered with the negotiation, which stops downgrade attacks | 3.3 |
| AES-GCM or ChaCha20 data | Fast bulk encryption with integrity | 2.5 |

**TLS 1.2 vs 1.3:**

| | TLS 1.2 | TLS 1.3 |
|---|---|---|
| Round trips | 2 | 1 (0 on resumption) |
| Forward secrecy | Optional | **Mandatory** |
| Weak algorithms (RC4, CBC, RSA key transport, SHA-1) | Possible | **Removed** |
| Certificate sent | In clear | Encrypted |

The pattern is that TLS 1.3 removed options. Fewer choices mean fewer ways to be misconfigured.

---

## 7.3 Cipher suites and negotiation

A **cipher suite** is the agreed set of algorithms. For example, `TLS_AES_256_GCM_SHA384` means AES-256-GCM for data and SHA-384 for key derivation. In TLS 1.3 the key exchange and signature algorithms are negotiated separately. TLS 1.3 has only five suites, all AEAD.

**Negotiation:** The client lists what it supports, and the server picks. The risk is a **downgrade attack**, where a man-in-the-middle strips the strong options. TLS defends against it by authenticating the whole negotiation inside the Finished message.

```python name=tls_inspect.py
import socket, ssl

ctx = ssl.create_default_context()            # verification ON, modern defaults
ctx.minimum_version = ssl.TLSVersion.TLSv1_2  # refuse anything older

host = "example.com"
with socket.create_connection((host, 443), timeout=10) as sock:
    with ctx.wrap_socket(sock, server_hostname=host) as tls:   # server_hostname drives SNI and hostname checking
        print("Protocol:", tls.version())
        print("Cipher:  ", tls.cipher())
        cert = tls.getpeercert()
        print("Subject: ", cert["subject"])
        print("Issuer:  ", cert["issuer"])
        print("Expires: ", cert["notAfter"])
        print("SANs:    ", cert.get("subjectAltName"))
```

---

## 7.4 How certificates are validated during the handshake

When the client receives the certificate chain, it checks:

1. **Chain:** each signature verifies up to a root in the trust store (6.3 and 6.4).
2. **Hostname:** the name you typed appears in the **SAN**.
3. **Validity:** today's date is within the dates.
4. **Usage:** the certificate is allowed for server authentication, and the intermediates are allowed to be CAs.
5. **Revocation and CT:** a stapled OCSP response, if present, and proof of Certificate Transparency logging.

If **any** check fails, the connection must stop.

```python name=validation_fails.py
import socket, ssl

def try_connect(host, connect_to=None):
    ctx = ssl.create_default_context()
    try:
        with socket.create_connection((connect_to or host, 443), timeout=10) as s:
            with ctx.wrap_socket(s, server_hostname=host):
                return "OK"
    except ssl.SSLCertVerificationError as e:
        return f"REJECTED: {e.verify_message}"

print(try_connect("example.com"))                     # OK
print(try_connect("wrong.host.badssl.com"))           # hostname mismatch
print(try_connect("expired.badssl.com"))              # expired certificate
print(try_connect("self-signed.badssl.com"))          # untrusted issuer
```

`badssl.com` is a public test site. Each failure is the protection working. The attacks from 6.1 stop here.

**Security takeaway:** Never set `verify_mode = CERT_NONE` or `check_hostname = False` (or `verify=False` in `requests`). It turns TLS back into a postcard with extra steps.

## 7.5 Session resumption and 0-RTT

**The problem:** A full handshake costs time, and reconnecting repeatedly is wasteful.

**Resumption:** After the first handshake, the server gives the client a **session ticket**, an encrypted blob holding a secret. On reconnect the client presents the ticket and skips the certificate work. This is faster and cheaper.

**0-RTT (early data):** TLS 1.3 lets a resuming client send application data in its **very first message**, with zero waiting.

**The catch is replay.** Recall the replay attacker from Section 1.4. Early data has no fresh server contribution, so an attacker can capture and resend it.

| Request | 0-RTT safe? |
|---|---|
| `GET /logo.png` (idempotent) | Yes |
| `POST /transfer?to=mallory&amount=100` | **No**. It could be replayed and run twice |

**Rules:** Allow 0-RTT only for safe, idempotent requests, or disable it. Servers should reject early data for state-changing endpoints.

## 7.6 HSTS, secure cookies, and mixed content

HTTPS only helps if the browser actually uses it.

**The attack (SSL stripping):** A user types `bank.com`. The browser tries HTTP first, and a man-in-the-middle keeps them on HTTP while talking HTTPS to the bank.

| Defense | What it does |
|---|---|
| **HSTS** header | Tells the browser "for the next N seconds, only ever use HTTPS for this site and refuse certificate-error bypasses" |
| **HSTS preload** | Ships your domain in the browser, so even the *first* visit is protected |
| **`Secure` cookie flag** | The cookie is never sent over plain HTTP |
| **`HttpOnly` and `SameSite`** | Block script access and cross-site sending of the cookie |
| **No mixed content** | An HTTPS page that loads an HTTP script hands control to the attacker, so browsers block it |

```python name=secure_headers.py
# Example headers a server should send over HTTPS
headers = {
    "Strict-Transport-Security": "max-age=63072000; includeSubDomains; preload",
    "X-Content-Type-Options": "nosniff",
    "Content-Security-Policy": "default-src 'self'; upgrade-insecure-requests",
}
cookie = "session=abc123; Secure; HttpOnly; SameSite=Strict; Path=/"
```

**Caution:** Only add `includeSubDomains` and `preload` once **every** subdomain supports HTTPS. Preloading is hard to undo.

## 7.7 HTTP/3 and QUIC

HTTP/1.1 and HTTP/2 run over TCP, with TLS added on top. **HTTP/3** runs over **QUIC**, which is built on UDP and has TLS 1.3 **built in**.

| Benefit | Why |
|---|---|
| Faster connection setup | Transport and crypto handshakes are combined |
| Encryption is mandatory | There is no unencrypted QUIC |
| Less head-of-line blocking | Lost packets only delay their own stream |
| Connection migration | Switching from Wi-Fi to mobile data doesn't drop the connection |

The security model is the same (TLS 1.3, certificates, forward secrecy). Only the delivery changed.

## 7.8 Encrypted SNI and ECH

**The problem:** One server IP hosts many sites, so the client must say which name it wants in the ClientHello. That field is **SNI**, and it is sent **in clear text**. An observer sees `bank.com`, even though the rest is encrypted.

**The fix:** **ECH** (Encrypted Client Hello) encrypts the real ClientHello using a public key the site publishes in DNS. An observer sees only a generic outer name, often a large shared provider.

| Gap | Remaining |
|---|---|
| Hostname in SNI | Closed by ECH |
| DNS lookups | Need DoH or DoT (Section 8) |
| Destination IP | Still visible, although hidden if many sites share a CDN |

Privacy needs several pieces working together. TLS alone doesn't provide it.

## 8.1 SSH, SMTP with STARTTLS, and DNS over HTTPS/TLS

### SSH: a remote shell you can trust

**The story:** You log in to a server over the internet. Before you type your password, you need to know you're talking to the real server. SSH solves this with the same handshake pattern as TLS: ephemeral key exchange, then a server signature, then symmetric encryption.

The trust model differs from the web:

| | HTTPS | SSH |
|---|---|---|
| Who vouches for the server? | A CA (chain of trust) | **You**, on first connect (TOFU: trust on first use) |
| Where is the trust stored? | OS or browser trust store | `~/.ssh/known_hosts` |
| Client login | Password, cookie, or certificate | **Key pair** (recommended) or password |

On first connection, SSH shows the server's key fingerprint and asks, "Do you recognize this?" It saves your answer. If the key later changes, SSH warns loudly:

```
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
```

This is either a reinstalled server or a man-in-the-middle. **Don't just delete the `known_hosts` line**. Verify through another channel first.

**Key-based login** works because of signatures (Section 4.5). The server stores your **public** key. At login it sends a challenge, and you sign it with your private key. No secret crosses the wire, so a stolen server database doesn't expose your key.

```python name=ssh_challenge.py
import os
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey
from cryptography.exceptions import InvalidSignature

# Setup: the user's public key is saved on the server (authorized_keys)
user_priv = Ed25519PrivateKey.generate()
server_has = user_priv.public_key()

# Login: the server sends a fresh random challenge (this prevents replay, see 1.4)
challenge = os.urandom(32)

# The client proves it holds the private key without revealing it
signature = user_priv.sign(challenge)

try:
    server_has.verify(signature, challenge)
    print("Login accepted")
except InvalidSignature:
    print("Login rejected")

# A recorded signature is useless next time, because the challenge differs
```

**Security notes:** Use Ed25519 keys with a passphrase on the private key. Disable password login (`PasswordAuthentication no`) and root login on servers. Never share or commit private keys.

### SMTP and STARTTLS: email's retrofitted encryption

**The story:** Email was designed in the 1980s as a postcard system. Encryption was added later with **STARTTLS**: the client connects in plain text and says "can we upgrade to TLS?"

**The problem:** The upgrade is **opportunistic**. A man-in-the-middle can delete the "STARTTLS is supported" line, and the two servers quietly continue unencrypted. This is the downgrade attack from 7.3, with nothing to detect it.

| Protection | Idea |
|---|---|
| **Implicit TLS** (ports 465, 993, 995) | TLS from the first byte, with no upgrade step to strip |
| **MTA-STS / DANE** | The domain publishes a policy: "always require verified TLS for mail to me" |

Even with perfect transport encryption, **every mail server along the path can read the message**. TLS only protects each hop. For privacy against the servers themselves, you need end-to-end encryption (8.2).

### DNS over HTTPS and TLS: hiding the lookups

**The problem:** Before connecting to `bank.com`, your device asks DNS for the IP address. Traditional DNS is plain UDP, so anyone on the path can see (and forge) every lookup. ECH (7.8) can't help if the DNS query reveals the name.

| Protocol | How it works |
|---|---|
| **DoT** (DNS over TLS) | DNS wrapped in TLS on a dedicated port (853) |
| **DoH** (DNS over HTTPS) | DNS wrapped in HTTPS on port 443, so it blends in with web traffic |

Both encrypt the lookup between you and your resolver. The resolver still sees your queries, so you are choosing **whom to trust**, not removing the need for trust. They also don't prove the answer is true. That's **DNSSEC**, a signature system for DNS data.

## 8.2 End-to-end encryption: Signal and the double ratchet

**The story:** With HTTPS, you trust the server. It decrypts your message and re-encrypts it for the recipient, so the company can read everything and so can anyone who breaches it. In **end-to-end encryption (E2EE)** the server only carries sealed envelopes it can't open. Only the two endpoints hold keys.

| | Transport encryption (TLS) | End-to-end encryption |
|---|---|---|
| Who can read it? | You, the server, the recipient | You and the recipient only |
| Server breach | Messages exposed | Only ciphertext exposed |

### The problem with one long-lived key

Suppose Alice and Bob agree on one key and use it for years. If an attacker steals it **once**, every past and future message is exposed. That's a disaster for something you use daily.

### The solution: change the key after every message

The Signal protocol's **double ratchet** works like a ratchet wrench that only turns one way:

1. **Symmetric ratchet:** every message uses a fresh key derived from the previous one by a **one-way hash** (Section 3). Old keys are deleted. A thief who steals today's key can't run the hash backwards to read yesterday's messages. This is **forward secrecy**.
2. **Diffie-Hellman ratchet:** whenever the conversation turns around, the parties exchange **new ephemeral public keys** (Section 4.4) and mix the result in. A thief who stole a key **heals** the conversation as soon as fresh randomness arrives. This is **post-compromise security**.

> **Thought question:** If every message has its own key and old keys are destroyed, what does an attacker who records everything and steals your phone tomorrow actually get?

Only the messages you still have stored on the phone, and nothing from the wire.

```python name=ratchet_demo.py
import hmac, hashlib
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

def kdf(chain_key: bytes):
    """One-way step: derive (next chain key, message key). It can't be reversed."""
    next_chain = hmac.new(chain_key, b"chain", hashlib.sha256).digest()
    msg_key    = hmac.new(chain_key, b"msg",   hashlib.sha256).digest()
    return next_chain, msg_key

chain = os.urandom(32)   # in reality, this comes from an authenticated key exchange
sent = []

for text in [b"hi", b"meet at noon", b"bring the files"]:
    chain, mk = kdf(chain)                 # the old chain key is overwritten
    nonce = os.urandom(12)
    sent.append((nonce, AESGCM(mk).encrypt(nonce, text, None)))
    del mk                                 # the message key is used once, then gone

# If an attacker steals `chain` now, they can read FUTURE messages from it
# (until a DH ratchet step heals it), but not the three above: the hash can't go backwards.
print(f"{len(sent)} messages sent, each with its own key")
```

*This is a simplified symmetric ratchet only. Real Signal adds the DH ratchet, out-of-order message handling, and authenticated setup (X3DH/PQXDH). Never build your own messaging protocol. Use Signal's libraries or MLS.*

### The remaining trust problem

How does Alice know the public key she received really belongs to Bob? The server could substitute its own, which is a man-in-the-middle again (see 4.1). Signal addresses this with **safety numbers**: a fingerprint of both parties' keys that you can compare in person or on a call. Verify it for high-risk conversations.

**What E2EE doesn't hide:** metadata, meaning who talks to whom, when, and how often. It also doesn't protect against a compromised device or an unlocked screen.

## 8.3 VPNs: WireGuard and IPsec

**The story:** You're in a hostile café. Instead of trusting each app individually, you build an **encrypted tunnel** from your laptop to a trusted gateway. All traffic travels inside it, so the café sees only one encrypted stream going to one place.

A VPN shifts the trust. It protects the **local network leg**, but your VPN provider can now see where your traffic goes. You are choosing whom to trust, not removing trust.

| | WireGuard | IPsec (IKEv2) |
|---|---|---|
| Design | Small, modern, about 4,000 lines of code | Large, old, many options |
| Crypto | Fixed modern choices (X25519, ChaCha20-Poly1305, BLAKE2s) | Negotiable suites |
| Identity | Each peer has a **public key**, like SSH | Certificates or pre-shared keys |
| Typical use | Personal VPNs, site-to-site, mesh networks | Enterprise and built-in OS clients |

**Why WireGuard's simplicity is a security feature:** There's no cipher negotiation, so no downgrade attacks (7.3). A small codebase means fewer bugs and easier audits. It follows the same lesson as TLS 1.3: removing choices removes ways to fail.

Conceptually, every WireGuard peer is configured like this:

```ini name=wg0.conf
[Interface]
PrivateKey = <this device's private key, never shared>
Address    = 10.0.0.2/32

[Peer]
PublicKey  = <the server's public key>
Endpoint   = vpn.example.com:51820
AllowedIPs = 0.0.0.0/0          # send all traffic through the tunnel
```

Identity is a public key you exchange out of band, much like SSH's `authorized_keys`. It works with no certificate authority.

**Security notes:**
- A VPN doesn't make you anonymous. The provider sees your traffic metadata.
- HTTPS is still needed inside the tunnel, because traffic is plain once it leaves the VPN gateway.
- Protect private keys, and remove a peer's public key from the server when a device is lost.

| **SSH** | Is this the real server, and how do I log in safely? | Host key (TOFU), and key-pair login via signatures |
| **Email** | Encryption added later can be stripped | Implicit TLS, MTA-STS, DANE. E2EE for real privacy |
| **DNS** | Lookups reveal where you go | DoH or DoT (and DNSSEC for authenticity) |
| **Chat** | The server can read everything | E2EE with keys only at the endpoints |
| **Stolen key exposes history** | One key lasts forever | Double ratchet: forward secrecy and healing |
| **Hostile local network** | Can't trust each app | VPN tunnel (WireGuard, IPsec), with trust moved to the gateway |

**Common thread:** Every system answers two questions: *how do we agree on a key?* (key exchange) and *how do we know who we're talking to?* (certificates, TOFU, safety numbers, or pre-shared public keys). Only the answer to the second differs.

# Section 9: Attacks and Failure Modes

Install: `pip install cryptography`

**Theme:** Almost no real-world break defeats the math. Attackers go around it: the protocol, the implementation, the people, or the trust model. Each failure below teaches a design lesson.

## 9.1 Man-in-the-middle and downgrade attacks

**The story:** Mallory stands between Alice and Bob. To Alice she pretends to be Bob, and to Bob she pretends to be Alice. She decrypts, reads, and re-encrypts every message. Both sides see a "secure" connection.

Unauthenticated key exchange (4.4) is exactly this vulnerable. The defenses are the ones you've met:

| Attack | Defense | Where |
|---|---|---|
| Impersonating a server | Certificates and hostname validation | 6, 7.4 |
| Stripping HTTPS | HSTS and preload | 7.6 |
| Stripping STARTTLS | Implicit TLS, MTA-STS | 8.1 |
| Swapping a chat key | Safety numbers | 8.2 |

**Downgrade attacks:** Mallory doesn't break strong crypto. She convinces both sides to use weak crypto, by tampering with the negotiation.

- **FREAK, Logjam (2015):** attackers forced connections to old, deliberately weak "export-grade" keys that could be cracked.
- **Defense:** authenticate the negotiation (TLS Finished messages), and **remove old options entirely**. Backward compatibility is an attack surface.

```python name=downgrade_policy.py
import ssl

ctx = ssl.create_default_context()
ctx.minimum_version = ssl.TLSVersion.TLSv1_2   # refuse SSLv3, TLS 1.0, TLS 1.1
# Never "enable legacy support for old clients" without a clear, temporary reason.
```

> **Thought question:** If your server supports the strong option *and* the weak one, which one is only as strong as the weakest link?

---

## 9.2 Historical TLS flaws

| Attack | Year | What went wrong | Lesson |
|---|---|---|---|
| **BEAST** | 2011 | Predictable IVs in CBC mode let attackers recover cookie bytes | Predictable "random" values (5.1) |
| **CRIME / BREACH** | 2012-13 | **Compression** before encryption leaked secrets through the size of the output | Encryption hides content, not length (7.1) |
| **Heartbleed** | 2014 | A missing bounds check in OpenSSL's heartbeat feature returned 64 KB of server memory per request, including private keys | A bug in the implementation, not the math |
| **POODLE** | 2014 | Forced downgrade to SSL 3.0, whose CBC padding could be exploited | Downgrade plus legacy support (9.1) |
| **ROBOT** | 2017 | A 19-year-old RSA padding oracle came back in new implementations | Old attacks return when you ignore them |

### Heartbleed in a story

The client sends "echo back this 4-letter word: `bird`", but declares the length as 64,000 letters. The server trusted the declared length, copied 64,000 bytes starting at `bird`, and sent back whatever else sat in memory: passwords, session cookies, even the TLS private key.

```python name=heartbleed_idea.py
memory = bytearray(b"bird" + b"|admin_password=hunter2|PRIVATE_KEY=...")

def heartbeat_vulnerable(payload_len: int) -> bytes:
    return bytes(memory[:payload_len])           # trusts the attacker's length

def heartbeat_safe(payload: bytes, claimed_len: int) -> bytes:
    if claimed_len != len(payload):              # validate input against reality
        raise ValueError("length mismatch, request discarded")
    return payload

print(heartbeat_vulnerable(60))                  # leaks neighboring secrets
```

**Lessons:**
- Validate every length and input. Never trust what the peer claims.
- Python is memory-safe, but C is not. Memory-safe languages remove this entire bug class.
- **Forward secrecy** (4.4) limits the damage. A stolen server key can't decrypt recorded traffic.
- After such a bug, **patch, then rotate keys and certificates, then revoke the old ones**. Patching alone isn't enough because the keys may already be stolen.

## 9.3 Compromised CAs and misissued certificates

Recall the root of trust (6.3, 6.4): any trusted CA can vouch for **any** domain.

**The story (DigiNotar, 2011):** Attackers breached a Dutch CA and issued themselves certificates for `*.google.com`. About 300,000 Iranian users were then silently intercepted, because their browsers trusted DigiNotar's root. The browsers saw valid chains. The company went bankrupt, and its root was removed from every trust store.

| Layer | Defense |
|---|---|
| **Certificate Transparency** (6.7) | Misissued certificates become publicly visible, so domain owners can detect them |
| **CAA DNS records** | The domain owner states which CAs may issue for it |
| **Trust store removal** | Browsers and OSes distrust misbehaving CAs (DigiNotar, Symantec) |
| **Short lifetimes** | Limit how long a bad certificate works |
| **Certificate pinning** (mostly retired) | Hard to maintain, and a mistake can lock out your own users |

```text name=caa_record.txt
example.com.  CAA 0 issue "letsencrypt.org"
example.com.  CAA 0 iodef "mailto:security@example.com"
```

Only the named CA may issue, and misissue attempts get reported to you.

**Lesson:** You can't make every CA perfect, so you add **detection and limit the blast radius**.

## 9.4 Side-channel attacks and implementation bugs

**The story:** A safecracker doesn't pick the lock. He listens to the clicks. The lock design is sound, but its behavior leaks information.

A **side channel** leaks secrets through *how* a computation happens: its time, power use, cache access, or sound. You already saw the simplest one in 3.3, when `==` on a MAC returns faster the earlier it finds a mismatch.

```python name=timing_leak.py
import hmac, time

secret = b"A" * 32 + b"X"

def bad_compare(a: bytes, b: bytes) -> bool:
    for x, y in zip(a, b):
        if x != y:
            return False          # exits early: the time reveals how many bytes matched
    return len(a) == len(b)

def timed(guess):
    t = time.perf_counter_ns()
    for _ in range(20000):
        bad_compare(secret, guess)
    return time.perf_counter_ns() - t

print("wrong first byte:   ", timed(b"B" + b"A" * 32))
print("right first 32 bytes:", timed(b"A" * 32 + b"Y"))   # noticeably slower

# FIX: constant-time comparison
hmac.compare_digest(secret, b"A" * 33)
```

Other real examples:

| Attack | Leak |
|---|---|
| **Lucky13, Bleichenbacher/ROBOT** | Different error messages or timing reveal whether padding was valid (a **padding oracle**) |
| **Spectre / Meltdown** | CPU speculation leaves traces in the cache that other processes can read |
| **Nonce reuse** (2.6) | Not a side channel, but a classic implementation mistake that exposes keys |
| **Weak RNG** (5.1) | Predictable keys |

**Lessons:**
- Use **well-reviewed libraries**, which are written by specialists to be constant-time. Never write crypto primitives yourself.
- Return **identical errors** for every failure type (for example, generic "decryption failed").
- Keep libraries **updated**. Many fixes arrive as routine patches.
- Reduce exposure: don't run untrusted code next to secrets on shared hardware.

## 9.5 Quantum threats and post-quantum cryptography

**The story:** A quantum computer isn't just a faster computer. It runs certain algorithms, notably **Shor's algorithm**, that crack the "easy forward, hard backward" problems in Section 4.2 (factoring and elliptic curves) efficiently. Such a machine doesn't exist at useful scale today, but it might.

| Primitive | Quantum impact | Action |
|---|---|---|
| **RSA, ECDSA, Ed25519, DH, X25519** | **Broken** by Shor | Replace with post-quantum algorithms |
| **AES-256, ChaCha20** | Weakened only modestly (Grover's algorithm roughly halves the effective strength) | AES-256 remains fine |
| **SHA-256 / SHA-3** | Similar modest weakening | Fine |

### "Harvest now, decrypt later"

An attacker doesn't need a quantum computer **today**. They can record encrypted traffic now and decrypt it later, when the machine exists. Anything that must stay secret for 10 to 30 years (medical, government, and trade secrets) is already at risk.

> **Thought question:** If your data must stay secret until 2045, what must you do about the key exchange you use in 2026?

### The solution: post-quantum cryptography (PQC)

NIST standardized the first algorithms in 2024:

| Standard | Algorithm | Replaces | Purpose |
|---|---|---|---|
| FIPS 203 | **ML-KEM** (from Kyber) | Diffie-Hellman / X25519 | Key exchange |
| FIPS 204 | **ML-DSA** (from Dilithium) | RSA / ECDSA / Ed25519 | Signatures |
| FIPS 205 | **SLH-DSA** (from SPHINCS+) | Same | Signatures, a hash-based backup |

These rely on different hard problems (lattices and hashes) that quantum computers aren't known to solve quickly.

**The practical approach is hybrid:** combine classical and post-quantum together, for example **X25519 + ML-KEM**. If either one holds, the connection is safe. This hedges against two risks: that quantum computers arrive, and that the newer algorithms have undiscovered flaws. Major browsers and CDNs already use hybrid key exchange in TLS.

```python name=hybrid_pq_idea.py
import hashlib

# Concept only: combine two independent secrets so an attacker must break BOTH.
# Real code should use a vetted TLS or crypto library, not hand-rolled combiners.
def combine(classical_secret: bytes, pq_secret: bytes) -> bytes:
    return hashlib.sha256(classical_secret + pq_secret).digest()
```

**What to do now (crypto agility):**
1. **Inventory** where you use RSA, ECC, and DH.
2. Design so algorithms can be **swapped without rewriting** (no hardcoded algorithm names scattered through the code).
3. Enable hybrid key exchange where your TLS stack supports it.
4. Prioritize long-lived secrets, and expect signatures and certificates to migrate later.

|---|---|---|

## 10.1 Inspecting TLS in practice

**The story:** A doctor doesn't guess, they examine. You can examine any HTTPS connection yourself in three ways.

### Option A: `openssl s_client`

```bash name=inspect.sh
# Connect, show the chain, and print the negotiated protocol and cipher
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null

# Print just the leaf certificate's key fields
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName

# Test whether a server still accepts an old protocol (it should refuse)
openssl s_client -connect example.com:443 -servername example.com -tls1_1 </dev/null
```

What to look for:

| Output | Meaning |
|---|---|
| `Protocol: TLSv1.3` and a `TLS_AES_*` or `TLS_CHACHA20_*` cipher | The modern baseline |
| `Verification: OK` or `Verify return code: 0 (ok)` | The chain validated to a trusted root |
| Chain with leaf then intermediate | The server sends its intermediate correctly |
| `notAfter` date | When it expires, so put it in monitoring |
| Handshake failure on `-tls1_1` | Good. Old protocols are disabled |

### Option B: browser dev tools
Click the padlock, then the certificate details, to see the chain, SAN, and expiry. The **Security** panel in Chrome DevTools shows the protocol and cipher. In the **Network** tab, the Protocol column shows `h2` or `h3` (HTTP/2 or HTTP/3).

### Option C: Wireshark
Capture traffic and filter with `tls.handshake`. You'll see the ClientHello, including the **SNI in clear text** (7.8), and the encrypted data after it. The practical lesson is that you can see the metadata but not the content. For decryption in a lab, browsers can export session keys through the `SSLKEYLOGFILE` environment variable. **Use that only on your own machines, and protect the file**, since it unlocks the captured traffic.

## 10.2 Generating keys and certificates with OpenSSL

The commands below create a private CA and a server certificate signed by it (6.3 and 6.8). This is the right pattern for internal and development use, instead of a bare self-signed certificate.

```bash name=make_pki.sh
set -euo pipefail
umask 077                       # new files are private by default (private keys)

# 1. Root CA key and certificate (the root key would be kept offline in production)
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out ca.key
openssl req -x509 -new -key ca.key -sha256 -days 1825 \
  -subj "/CN=Demo Private Root CA" \
  -addext "basicConstraints=critical,CA:TRUE" \
  -addext "keyUsage=critical,keyCertSign,cRLSign" \
  -out ca.crt

# 2. Server key and CSR
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out server.key
openssl req -new -key server.key -subj "/CN=app.internal.test" -out server.csr

# 3. CA signs the CSR. SAN is required, and browsers ignore CN.
cat > server.ext <<'EOF'
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature
extendedKeyUsage=serverAuth
subjectAltName=DNS:app.internal.test
EOF
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -sha256 -days 90 -extfile server.ext -out server.crt

# 4. Verify the chain
openssl verify -CAfile ca.crt server.crt
```

Notes:
- Keep `ca.key` offline or in an HSM in real use, and never commit `*.key` files. Add `*.key` and `*.pem` to `.gitignore`.
- Use a short lifetime (90 days here), and automate renewal.
- Install `ca.crt` only on machines that should trust this CA. Anyone who holds `ca.key` can impersonate any site to those machines.

## 10.3 Configuring TLS securely

**Principle:** Don't hand-pick cipher suites from memory. Use a maintained, reviewed profile, and re-check it periodically.

| Setting | Recommended direction |
|---|---|
| Protocols | TLS 1.3, plus TLS 1.2 only if you need older clients |
| Cipher suites | AEAD with forward secrecy only (ECDHE with AES-GCM or ChaCha20-Poly1305) |
| Certificates | ECDSA P-256 or RSA 2048+ (3072 preferred), from a trusted CA, with automated renewal |
| OCSP stapling | On |
| HSTS | On, after confirming every subdomain supports HTTPS |
| 0-RTT | Off, or only for idempotent requests (7.5) |
| Private key | Mode `600`, owned by the service user, ideally in a KMS or HSM |

**Mozilla's SSL Configuration Generator** (ssl-config.mozilla.org) produces ready-made nginx, Apache, HAProxy, and other configs for its "Modern" and "Intermediate" profiles. I recommend starting there, rather than copying a blog post from 2016.

An nginx sketch of the shape you should end up with. Generate the exact current values from Mozilla's tool:

```nginx name=nginx-tls.conf
server {
    listen 443 ssl;
    http2 on;                       # syntax for recent nginx; older versions use "listen 443 ssl http2"
    server_name app.example.com;

    ssl_certificate     /etc/ssl/app/fullchain.pem;   # leaf + intermediate
    ssl_certificate_key /etc/ssl/app/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;
    # ssl_ciphers  <paste the list from the Mozilla generator>

    ssl_stapling on;
    ssl_stapling_verify on;

    add_header Strict-Transport-Security "max-age=63072000" always;
    add_header X-Content-Type-Options "nosniff" always;
}
```

**Test your result** with an external scanner such as Qualys SSL Labs (public sites), or `testssl.sh` / `nmap --script ssl-enum-ciphers` (anything you can reach). Add certificate-expiry alerts to monitoring too.

## 10.4 Using crypto libraries correctly

**Rule of thumb:** use a high-level, hard-to-misuse API, and let it make the choices.

You asked for Python throughout, so the examples are in Python. The equivalents are the Web Crypto API (`crypto.subtle`) for TypeScript and `System.Security.Cryptography` (`AesGcm`, `RandomNumberGenerator`, `Rfc2898DeriveBytes`) for .NET, if you ever need them.

```python name=safe_crypto_toolkit.py
import os, secrets, base64
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey
from cryptography.exceptions import InvalidTag, InvalidSignature
from argon2 import PasswordHasher   # pip install argon2-cffi

# 1. Encrypt data: AEAD, a fresh random nonce, and the nonce stored with the ciphertext
def encrypt(key: bytes, plaintext: bytes, aad: bytes = b"") -> bytes:
    nonce = os.urandom(12)
    return nonce + AESGCM(key).encrypt(nonce, plaintext, aad)

def decrypt(key: bytes, blob: bytes, aad: bytes = b"") -> bytes:
    try:
        return AESGCM(key).decrypt(blob[:12], blob[12:], aad)
    except InvalidTag:
        raise ValueError("decryption failed") from None   # generic error (9.4)

# 2. Load the key from the environment or a secrets manager, never from source code
key = base64.b64decode(os.environ["DATA_KEY_B64"])
assert len(key) == 32, "DATA_KEY_B64 must decode to 32 bytes"

# 3. Passwords: Argon2id, never SHA-256
ph = PasswordHasher()

# 4. Tokens and IDs: the secrets module
reset_token = secrets.token_urlsafe(32)

# 5. Signatures: Ed25519, with verification failure treated as a hard stop
priv = Ed25519PrivateKey.generate()
sig = priv.sign(b"release-1.0.tar.gz digest")
try:
    priv.public_key().verify(sig, b"release-1.0.tar.gz digest")
except InvalidSignature:
    raise SystemExit("untrusted artifact")
```

Generate the key once, outside the code: `python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"`. Then store it in your secrets manager.

**Checklist:**
- AEAD only (AES-GCM or ChaCha20-Poly1305), with a unique nonce per message.
- Keys from a CSPRNG, stored outside the code, rotated, and one per purpose.
- Compare secrets with `hmac.compare_digest`.
- Verify TLS, and never pass `verify=False`.
- Keep libraries updated, and run `pip-audit` (or Dependabot) in CI.

## 10.5 Common mistakes

Here is each classic mistake next to its fix.

| Mistake | Why it hurts | Fix |
|---|---|---|
| **Rolling your own crypto** (custom cipher, XOR "encryption", home-made protocol) | Subtle flaws that only experts catch. Kerckhoffs (1.3) | Vetted libraries and standard protocols |
| **Hardcoded keys** | Leak through Git, builds, and logs (5.2) | Environment or secrets manager, and secret scanning |
| **Disabled certificate validation** | Removes MITM protection entirely (7.4) | Fix the trust (install the right CA) instead |
| **ECB mode or unauthenticated CBC and CTR** | Pattern leaks and tampering (2.4) | AEAD |
| **Reused nonces** | Leaks plaintext and can expose auth keys (2.6) | Random or counter nonce, unique per key |
| **`random` for secrets** | Predictable (5.1) | `secrets` / `os.urandom` |
| **Fast hash for passwords** | Billions of guesses per second (3.4) | Argon2id |
| **MD5 or SHA-1 for security** | Collisions (3.2) | SHA-256 or better |
| **`==` for comparing MACs or tokens** | Timing leak (9.4) | `hmac.compare_digest` |
| **Detailed crypto error messages** | Padding oracles (9.4) | One generic error |
| **No rotation or expiry monitoring** | Outages and long exposure (5.2, 6.5) | Automate renewal and alert on expiry |
| **Encrypting when you needed hashing, or the reverse** | Reversible passwords, or unrecoverable data | Passwords are hashed. Data you must read back is encrypted |
| **Believing encryption means safe** | It doesn't hide metadata or protect a compromised endpoint (7.1, 8.2) | Think through the threat model (1.4) |

# Course wrap-up: the whole story in one page

1. **Foundations:** Protect confidentiality, integrity, and freshness against realistic attackers. The key is the secret, never the method.
2. **Symmetric:** Fast and strong, but both sides need the key. Use AEAD with unique nonces.
3. **Hashing:** Fingerprints detect change. HMAC adds a key, and Argon2id protects passwords.
4. **Asymmetric:** Solves key sharing (key exchange) and proof of authorship (signatures). Combined with symmetric as hybrid encryption.
5. **Randomness and keys:** Everything depends on unpredictable, well-guarded keys, which a KMS can protect.
6. **Certificates and PKI:** Bind a name to a key through a chain of signatures, with transparency and short lifetimes as safety nets.
7. **TLS:** All of the above in one handshake, which is HTTPS.
8. **Other protocols:** The same pieces, with different answers to "who do I trust?"
9. **Failures:** Systems break at the edges (negotiation, code, trust, people), and quantum computing will force a migration.
10. **Practice:** Use standard tools, and verify, automate, and monitor.

**The two questions behind every secure system:**
1. *How do we agree on a key nobody else has?*
2. *How do we know who we're agreeing with?*
