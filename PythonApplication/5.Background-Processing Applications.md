# 5. Background-Processing Applications

A background-processing application performs work outside the main user request or program flow. Common examples include sending emails, processing files, generating reports, and importing data.

---

## 5.1 Background Processing Fundamentals

### Foreground versus background work

- **Foreground work:** The user waits until the operation finishes.
- **Background work:** The application accepts the request and processes it later.

```python name=foreground_background.py
from concurrent.futures import ThreadPoolExecutor
import time

executor = ThreadPoolExecutor(max_workers=2)


def generate_report(report_id: int) -> None:
    time.sleep(2)
    print(f"Report {report_id} generated")


# Foreground: blocks for two seconds.
generate_report(1)

# Background: returns immediately.
executor.submit(generate_report, 2)
print("Request accepted")
```

In production, use a durable queue instead of an in-process thread when work must survive application restarts.

---

### Jobs, tasks, workers, and queues

- **Job/task:** A unit of work, such as sending one email.
- **Queue:** Stores jobs waiting to run.
- **Producer:** Adds jobs to the queue.
- **Worker/consumer:** Takes and executes jobs.

```text
Producer → Queue → Worker → Result
```

For example, a web API produces an email job, while a separate worker sends the email.

---

### Synchronous versus asynchronous execution

- **Synchronous:** Operations execute one after another.
- **Asynchronous:** A program can wait for I/O without blocking other work.
- **Background queue:** Work may execute in another process or computer.

```python name=async_execution.py
import asyncio


async def download(name: str) -> str:
    await asyncio.sleep(1)  # Simulates network I/O.
    return f"{name} downloaded"


async def main() -> None:
    results = await asyncio.gather(
        download("file-a"),
        download("file-b"),
    )
    print(results)


asyncio.run(main())
```

`asyncio` is effective for I/O-bound work. For CPU-intensive work, use processes or distributed workers.

---

### Delayed and scheduled jobs

- **Delayed job:** Runs after a specified delay.
- **Scheduled job:** Runs at a specific time or according to a repeating schedule.

```python name=delayed_job.py
from threading import Timer


def cleanup() -> None:
    print("Cleanup started")


Timer(5, cleanup).start()
print("Cleanup scheduled in five seconds")
```

`Timer` is suitable only for simple in-process work because the schedule is lost if the process stops.

---

### Batch processing

Batch processing handles multiple records together rather than one at a time.

```python name=batch_processing.py
records = list(range(10))
batch_size = 3

for start in range(0, len(records), batch_size):
    batch = records[start : start + batch_size]
    print(f"Processing {batch}")
```

Batches reduce scheduling and database overhead, but very large batches can consume excessive memory.

---

### Distributed worker architecture

Distributed workers run across multiple processes or computers:

```text
Application instances
        ↓
Redis or RabbitMQ
        ↓
Worker 1   Worker 2   Worker 3
```

Advantages include horizontal scaling and failure isolation. Challenges include duplicate delivery, network failure, shared state, and monitoring.

---

### Task states and lifecycle

A typical lifecycle is:

```text
Created → Queued → Running → Succeeded
                         ↘ Failed → Retrying
                                  → Dead-lettered
```

Common states include:

- **Pending:** Created but not queued.
- **Queued:** Waiting for a worker.
- **Running:** Currently executing.
- **Succeeded:** Completed successfully.
- **Failed:** Ended with an error.
- **Retrying:** Waiting for another attempt.
- **Cancelled:** Stopped intentionally.

---

## 5.2 Job Scheduling

### One-time scheduled jobs

A one-time job runs at a specific date and time.

Examples:

- Publish a message tomorrow.
- Delete a temporary file in one hour.
- Activate a subscription at midnight.

```python name=one_time_schedule.py
from datetime import datetime, timedelta, timezone

run_at = datetime.now(timezone.utc) + timedelta(hours=1)
print(f"Job will run at {run_at.isoformat()}")
```

Store scheduled times in UTC and convert them to the user's time zone for display.

---

### Interval-based jobs

An interval schedule repeats after a fixed duration:

```text
Every 10 seconds
Every 15 minutes
Every 6 hours
```

Use intervals for polling, health checks, or periodic synchronization.

---

### Calendar and cron-style schedules

Calendar schedules run at specified clock times:

```text
Every Monday at 09:00
At midnight on the first day of every month
Every weekday at 18:30
```

A traditional five-field cron expression contains:

```text
minute hour day-of-month month day-of-week
```

Example:

```text
0 9 * * 1-5
```

This represents 09:00 every weekday, subject to the scheduler’s cron syntax and time zone.

---

### Time-zone handling

Use aware `datetime` values and `zoneinfo`.

```python name=time_zones.py
from datetime import datetime
from zoneinfo import ZoneInfo

utc_time = datetime.now(ZoneInfo("UTC"))
local_time = utc_time.astimezone(ZoneInfo("Asia/Kolkata"))

print(utc_time.isoformat())
print(local_time.isoformat())
```

Avoid fixed offsets such as `UTC+5` for geographic regions because daylight-saving rules can change offsets.

---

### Misfire handling

A **misfire** occurs when a job could not run at its scheduled time—for example, because the scheduler was stopped.

Possible policies:

- Run immediately after recovery.
- Skip the missed execution.
- Run only if the delay is within a grace period.
- Combine several missed runs into one execution.

The correct choice depends on whether missing or duplicating the work is more harmful.

---

### Overlapping-job prevention

An overlap happens when a previous execution is still running when the next one starts.

Possible controls:

- Allow only one running instance.
- Skip the new execution.
- Queue the new execution.
- Use a distributed lock.

```python name=local_overlap_prevention.py
from threading import Lock

job_lock = Lock()


def scheduled_job() -> None:
    if not job_lock.acquire(blocking=False):
        print("Previous execution is still running; skipping")
        return

    try:
        print("Running scheduled job")
    finally:
        job_lock.release()
```

A local lock does not protect multiple machines. Distributed systems need a shared lock or a unique database constraint.

---

### Persistent schedules

A persistent schedule is stored in a database or another durable store rather than process memory.

It preserves:

- Job definition
- Trigger or schedule
- Next execution time
- Job identifier
- Relevant metadata

Avoid storing untrusted executable code in job data. Store a permitted task name and validated parameters instead.

---

### Scheduler recovery after restart

After a restart, a scheduler should:

1. Reload persistent schedules.
2. Identify missed jobs.
3. Apply the misfire policy.
4. Prevent duplicate executions.
5. Continue calculating future run times.

Persistent schedules do not automatically make the work exactly-once; tasks should still be idempotent.

---

## 5.3 APScheduler

APScheduler runs Python functions at specified times. It is useful when scheduling belongs inside one application.

Install the version required by your project:

```bash
python -m pip install APScheduler
```

> APScheduler APIs can differ between major versions. The following compact examples use the widely used APScheduler 3.x API style.

---

### Configuring schedulers

Common scheduler types include:

- `BlockingScheduler`: Owns and blocks the current process.
- `BackgroundScheduler`: Runs in a background thread.
- `AsyncIOScheduler`: Integrates with `asyncio`.

```python name=apscheduler_basic.py
from apscheduler.schedulers.blocking import BlockingScheduler


def health_check() -> None:
    print("System is healthy")


scheduler = BlockingScheduler(timezone="UTC")
scheduler.add_job(health_check, "interval", minutes=5, id="health-check")
scheduler.start()
```

Use a dedicated scheduler process in production to avoid multiple web-server instances creating duplicate schedules.

---

### Date, interval, and cron triggers

```python name=apscheduler_triggers.py
from datetime import datetime, timedelta, timezone
from apscheduler.schedulers.background import BackgroundScheduler


def run_job(message: str) -> None:
    print(message)


scheduler = BackgroundScheduler(timezone="UTC")

# Run once.
scheduler.add_job(
    run_job,
    "date",
    run_date=datetime.now(timezone.utc) + timedelta(minutes=1),
    args=["One-time job"],
)

# Run repeatedly.
scheduler.add_job(
    run_job,
    "interval",
    minutes=10,
    args=["Interval job"],
)

# Run every weekday at 09:00 UTC.
scheduler.add_job(
    run_job,
    "cron",
    day_of_week="mon-fri",
    hour=9,
    minute=0,
    args=["Cron job"],
)

scheduler.start()
```

---

### Thread and process executors

- **Thread executor:** Appropriate for network or file I/O.
- **Process executor:** Appropriate for CPU-heavy Python work.

```python name=apscheduler_executors.py
from apscheduler.executors.pool import (
    ProcessPoolExecutor,
    ThreadPoolExecutor,
)
from apscheduler.schedulers.background import BackgroundScheduler

executors = {
    "default": ThreadPoolExecutor(max_workers=10),
    "cpu": ProcessPoolExecutor(max_workers=2),
}

scheduler = BackgroundScheduler(executors=executors, timezone="UTC")
```

Functions sent to process workers must be serializable and normally defined at module level.

---

### Persistent job stores

A persistent job store saves schedules outside memory. A common SQL-backed configuration uses SQLAlchemy.

```python name=apscheduler_job_store.py
import os
from apscheduler.jobstores.sqlalchemy import SQLAlchemyJobStore
from apscheduler.schedulers.background import BackgroundScheduler

database_url = os.environ["SCHEDULER_DATABASE_URL"]

scheduler = BackgroundScheduler(
    jobstores={"default": SQLAlchemyJobStore(url=database_url)},
    timezone="UTC",
)
```

Keep credentials in environment variables or a secret manager. Use TLS and least-privilege database credentials.

---

### Adding, modifying, and removing jobs

```python name=apscheduler_job_management.py
from apscheduler.schedulers.background import BackgroundScheduler

scheduler = BackgroundScheduler(timezone="UTC")


def cleanup() -> None:
    print("Cleaning temporary files")


scheduler.add_job(
    cleanup,
    "interval",
    hours=1,
    id="cleanup",
    replace_existing=True,
)

scheduler.reschedule_job("cleanup", trigger="interval", hours=2)
scheduler.remove_job("cleanup")
```

Stable job IDs make updates and duplicate prevention easier.

---

### Handling missed executions

```python name=apscheduler_misfires.py
scheduler.add_job(
    cleanup,
    "interval",
    minutes=5,
    id="cleanup",
    coalesce=True,
    misfire_grace_time=60,
    max_instances=1,
)
```

- `coalesce=True`: Combines multiple missed runs into one.
- `misfire_grace_time=60`: Runs only if no more than 60 seconds late.
- `max_instances=1`: Prevents local overlapping executions.

---

### Monitoring scheduled jobs

Listeners receive job events.

```python name=apscheduler_monitoring.py
import logging
from apscheduler.events import EVENT_JOB_ERROR, EVENT_JOB_EXECUTED

logger = logging.getLogger(__name__)


def job_listener(event: object) -> None:
    if getattr(event, "exception", None):
        logger.error("Scheduled job failed", extra={"job_id": event.job_id})
    else:
        logger.info("Scheduled job completed", extra={"job_id": event.job_id})


scheduler.add_listener(job_listener, EVENT_JOB_EXECUTED | EVENT_JOB_ERROR)
```

Do not log job arguments when they may contain secrets or personal information.

---

### Graceful scheduler shutdown

```python name=apscheduler_shutdown.py
import signal
from apscheduler.schedulers.background import BackgroundScheduler

scheduler = BackgroundScheduler(timezone="UTC")
scheduler.start()


def stop_scheduler(signum: int, frame: object) -> None:
    scheduler.shutdown(wait=True)


signal.signal(signal.SIGTERM, stop_scheduler)
signal.signal(signal.SIGINT, stop_scheduler)
signal.pause()
```

`wait=True` allows currently executing jobs to finish.

## 5.4 Task Queues

### Producers, queues, workers, and consumers

```text
Producer → Queue/Broker → Consumer/Worker → Result store
```

- The producer submits a message.
- The broker stores and routes it.
- A worker receives and processes it.
- An optional result store records the outcome.

---

### Task routing

Routing sends different tasks to appropriate queues:

```text
emails → email workers
images → image workers
reports → report workers
```

This prevents a large report from delaying urgent email delivery.

---

### Priority queues

Priority queues process urgent work first:

```text
High: password reset email
Normal: invoice generation
Low: weekly statistics
```

Priority usually affects ordering, but it may not guarantee strict ordering across multiple workers.

---

### Delayed tasks

A delayed task becomes available after a countdown or at a specified time.

Examples:

- Send a reminder in 24 hours.
- Retry an API request in 60 seconds.
- Delete an expired resource tomorrow.

A durable broker or scheduler should store delayed tasks when restart recovery is required.

---

### Retries and failure handling

Retry only errors that may be temporary:

- Network timeout
- Temporary service outage
- Broker connection failure
- Database deadlock

Do not repeatedly retry permanent errors such as invalid email addresses or malformed payloads.

---

### Task acknowledgements

An acknowledgement tells the broker that processing succeeded.

- **Acknowledge before execution:** Lower duplicate risk, but work may be lost if the worker crashes.
- **Acknowledge after execution:** Better delivery reliability, but a crash can cause duplicate execution.

Therefore, tasks should be safe to run more than once.

---

### Result storage

A result backend may store:

- Task state
- Return value
- Error information
- Completion time

Avoid storing large results in the backend. Save large files in object storage and return only a reference.

---

### Dead-letter queues

A dead-letter queue stores messages that cannot be processed after allowed attempts.

Operations teams can then:

1. Inspect the failure.
2. Correct the underlying problem.
3. Safely replay the message.
4. Archive or remove invalid messages.

---

### Idempotent task design

An idempotent task produces the same final state when executed more than once.

```python name=idempotent_order.py
def mark_order_paid(database: object, order_id: int) -> None:
    order = database.get_order(order_id)

    if order.status == "paid":
        return

    database.update_order_status(order_id, "paid")
```

For stronger protection, use a transaction and a unique database constraint.

## 5.5 Celery

Celery is a distributed task-queue system commonly used with Redis or RabbitMQ.

Install an appropriate transport extra:

```bash
python -m pip install "celery[redis]"
```

---

### Celery application configuration

```python name=celery_app.py
import os
from celery import Celery

broker_url = os.environ["CELERY_BROKER_URL"]
result_backend = os.environ["CELERY_RESULT_BACKEND"]

app = Celery(
    "tasks",
    broker=broker_url,
    backend=result_backend,
)

app.conf.update(
    task_serializer="json",
    result_serializer="json",
    accept_content=["json"],
    timezone="UTC",
    enable_utc=True,
    task_track_started=True,
)
```

JSON avoids unsafe Python object deserialization. Broker and backend URLs should come from secure configuration.

---

### Defining and calling tasks

```python name=tasks.py
from celery_app import app


@app.task
def add(left: int, right: int) -> int:
    return left + right
```

Producer:

```python name=enqueue_task.py
from tasks import add

result = add.delay(4, 6)
print(f"Task ID: {result.id}")
```

Calling `.delay()` queues the task. Calling `add(4, 6)` directly runs it synchronously.

---

### Brokers such as Redis or RabbitMQ

- **Redis:** Simple setup and suitable for many applications.
- **RabbitMQ:** Dedicated message broker with advanced routing and acknowledgement features.

Use:

- Authentication
- TLS
- Private networking
- Firewall restrictions
- Separate least-privilege broker accounts

Do not expose either broker directly to the public internet.

---

### Worker configuration

Start a worker:

```bash
celery -A celery_app.app worker --loglevel=INFO --concurrency=4
```

Configure concurrency based on workload:

- Higher concurrency for I/O-heavy tasks.
- Process-based workers for CPU-heavy tasks.
- Separate queues for different resource requirements.

---

### Retries and task time limits

```python name=retrying_task.py
import requests
from celery_app import app


@app.task(
    bind=True,
    autoretry_for=(requests.Timeout, requests.ConnectionError),
    retry_backoff=True,
    retry_jitter=True,
    max_retries=5,
    soft_time_limit=25,
    time_limit=30,
)
def fetch_status(self: object, url: str) -> int:
    # In production, validate the complete URL against an allow-list
    # before making the request to prevent SSRF.
    response = requests.get(url, timeout=10)
    response.raise_for_status()
    return response.status_code
```

Only retry temporary failures. A hard time limit may terminate a task abruptly, so cleanup and idempotency remain important.

---

### Task chains, groups, and chords

- **Chain:** Tasks run sequentially.
- **Group:** Tasks run in parallel.
- **Chord:** A group completes, then a final callback runs.

```python name=celery_workflows.py
from celery import chain, chord, group
from tasks import add

sequential = chain(add.s(1, 2), add.s(3))
parallel = group(add.s(1, 2), add.s(3, 4))
with_callback = chord(parallel)(add.s(10))
```

Use orchestration carefully because large workflows can create many broker messages and backend results.

---

### Periodic tasks

Celery Beat schedules periodic tasks.

```python name=celery_periodic.py
from celery.schedules import crontab
from celery_app import app

app.conf.beat_schedule = {
    "daily-cleanup": {
        "task": "maintenance.cleanup",
        "schedule": crontab(hour=2, minute=0),
    }
}
```

Run Beat as a single logical scheduler unless using a scheduler designed for leader election.

---

### Result backends

Result backends store task status and return values.

Common choices include:

- Redis
- Relational databases
- RPC-based result delivery

Set result expiration and avoid retaining sensitive results longer than necessary.

```python name=celery_result_config.py
app.conf.update(
    result_expires=3600,
    task_ignore_result=False,
)
```

For fire-and-forget tasks, use `ignore_result=True` to reduce storage.

---

### Worker monitoring and administration

Useful commands include:

```bash
celery -A celery_app.app status
celery -A celery_app.app inspect active
celery -A celery_app.app inspect reserved
```

Flower provides a web-based Celery dashboard. Protect administrative dashboards with authentication, TLS, and restricted network access.

## 5.7 Batch-Processing Systems

### Processing records in batches

```python name=record_batches.py
def batched(values: list[int], size: int):
    for start in range(0, len(values), size):
        yield values[start : start + size]


for batch in batched(list(range(10)), 4):
    print(batch)
```

Batch database writes to reduce connection and transaction overhead.

---

### Chunking large workloads

Do not load very large files entirely into memory.

```python name=file_chunks.py
from pathlib import Path
from collections.abc import Iterator


def read_chunks(path: Path, size: int = 1024 * 1024) -> Iterator[bytes]:
    with path.open("rb") as file:
        while chunk := file.read(size):
            yield chunk


for chunk in read_chunks(Path("large.bin")):
    print(f"Read {len(chunk)} bytes")
```

Choose a chunk size that balances memory usage and I/O efficiency.

---

### Parallel batch execution

```python name=parallel_batches.py
from concurrent.futures import ProcessPoolExecutor


def process_batch(batch: list[int]) -> int:
    return sum(value * value for value in batch)


batches = [[1, 2], [3, 4], [5, 6]]

with ProcessPoolExecutor(max_workers=2) as executor:
    results = list(executor.map(process_batch, batches))

print(results)
```

Limit parallelism so CPU, memory, database, and remote services are not overloaded.

---

### Checkpoints and restartability

A checkpoint records completed progress.

```python name=batch_checkpoint.py
import json
from pathlib import Path

checkpoint_path = Path("checkpoint.json")


def save_checkpoint(last_record_id: int) -> None:
    temporary_path = checkpoint_path.with_suffix(".tmp")
    temporary_path.write_text(
        json.dumps({"last_record_id": last_record_id}),
        encoding="utf-8",
    )
    temporary_path.replace(checkpoint_path)
```

Atomic replacement reduces the chance of leaving a partially written checkpoint.

---

### Progress tracking

Track meaningful counters:

```python name=batch_progress.py
total = 100
completed = 0

for record_id in range(total):
    # Process record.
    completed += 1

    if completed % 10 == 0:
        print(f"{completed}/{total} completed")
```

For distributed jobs, store progress in a shared database or metrics service.

---

### Partial-failure handling

A batch should normally record each failed item without discarding successful work.

```python name=partial_failures.py
failures: list[dict[str, str | int]] = []

for record_id in range(5):
    try:
        if record_id == 3:
            raise ValueError("Invalid record")
        print(f"Processed {record_id}")
    except ValueError as error:
        failures.append({"record_id": record_id, "error": str(error)})

print(f"Failures: {len(failures)}")
```

Do not include secrets or sensitive record contents in failure reports.

---

### Resource limits

Consider limits for:

- Memory
- CPU time
- Number of workers
- Open files
- Database connections
- Network request rate
- Maximum input size
- Per-task execution time

Apply limits at both the application and operating-system/container levels.

---

### Batch reports and summaries

A useful batch summary includes:

```python name=batch_summary.py
summary = {
    "total": 100,
    "succeeded": 96,
    "failed": 3,
    "skipped": 1,
    "duration_seconds": 42.8,
}

print(summary)
```

Return a non-zero exit code when failures should cause automation or CI to stop.

## 5.8 Background Application Use Cases

### Scheduled report generation

Typical flow:

```text
Scheduler → report task → database query → file storage → notification
```

Run heavy queries on replicas where appropriate and authorize access to generated reports.

---

### Email and notification delivery

Queueing prevents an email provider from delaying the user request.

```python name=email_task.py
def send_welcome_email(user_id: int) -> None:
    user = load_user(user_id)
    if user.welcome_email_sent:
        return

    email_provider.send(user.email, "Welcome")
    mark_welcome_email_sent(user.id)
```

Pass a user ID rather than the complete user object or password-related data.

---

### Document and file conversion

Examples include:

- CSV to JSON
- PNG to JPEG
- Office document to PDF
- Video transcoding

Validate file type and size, isolate converters, and never trust only the filename extension.

---

### File synchronization

A synchronization task compares source and destination state, transfers changes, and records a checkpoint.

Use checksums or version identifiers to detect changes. Validate destination paths to prevent path traversal.

---

### Large-file processing

Use streaming or chunks instead of reading the complete file into memory.

Examples:

- Calculating a checksum
- Parsing a large CSV
- Uploading multipart data
- Compressing a backup

---

### Data import and export

Imports should:

1. Validate the schema.
2. Reject or report malformed rows.
3. Process in batches.
4. Use transactions.
5. support restart from a checkpoint.
6. Produce a summary.

Exports should enforce authorization to prevent users from exporting data they cannot view.

---

### Network polling

```python name=network_polling.py
import requests

response = requests.get(
    "https://status.example.com/health",
    timeout=(3, 10),
)
response.raise_for_status()
print(response.json())
```

For user-provided URLs, strictly allow-list scheme, host, port, and path to prevent server-side request forgery.

---

### Cleanup and maintenance jobs

Examples include:

- Removing expired sessions
- Deleting temporary files
- Archiving old records
- Rotating logs
- Rebuilding indexes

Cleanup tasks should have a dry-run mode and conservative retention rules.

---

## 5.9 Reliability and Failure Management

### Automatic retries with exponential backoff

Exponential backoff increases the delay after each failure.

```python name=exponential_backoff.py
import random
import time


def run_with_retry(operation, attempts: int = 4):
    for attempt in range(attempts):
        try:
            return operation()
        except TimeoutError:
            if attempt == attempts - 1:
                raise

            delay = min(2**attempt, 30) + random.random()
            time.sleep(delay)
```

Jitter prevents many workers from retrying simultaneously.

---

### Timeout handling

Apply timeouts to:

- HTTP requests
- Database operations
- External commands
- Queue tasks
- Lock acquisition

```python name=subprocess_timeout.py
import subprocess

subprocess.run(
    ["python", "--version"],
    check=True,
    timeout=10,
)
```

Avoid `shell=True` when any command data may be influenced by a user.

---

### Poison-message isolation

A poison message always fails because its content is permanently invalid.

Handle it by:

1. Validating before execution.
2. Limiting retries.
3. Moving it to a dead-letter queue.
4. Alerting operators.
5. Recording a safe failure reason.

Do not let one poison message repeatedly block the queue.

---

### Dead-letter queues

A dead-letter record should include:

- Message or task identifier
- Task type
- Failure category
- Attempt count
- Safe error summary
- First and latest failure times

Sensitive payloads should be encrypted, redacted, or omitted.

---

### Idempotency and duplicate prevention

Use an idempotency key and a unique database constraint.

```python name=idempotency.py
def process_payment(database: object, payment_id: str) -> None:
    if database.payment_exists(payment_id):
        return

    with database.transaction():
        database.insert_payment_once(payment_id)
        database.mark_payment_completed(payment_id)
```

The uniqueness rule must be enforced atomically by the database, not only through a prior lookup.

---

### Distributed locking

A distributed lock coordinates work across machines.

A safe design needs:

- Unique lock ownership token
- Expiration
- Atomic acquisition
- Ownership check before release
- Handling for long-running jobs

A lock reduces overlap but does not replace idempotency because a worker can fail after performing work but before recording completion.

---

### Graceful worker shutdown

When receiving a termination signal, a worker should:

1. Stop accepting new jobs.
2. Finish or safely release current work.
3. Save checkpoints.
4. Close network and database connections.
5. Exit within the platform’s shutdown period.

Container platforms should provide enough termination grace time.

---

### Recovery after worker or broker failure

- **Worker failure:** Unacknowledged tasks are usually delivered again.
- **Broker failure:** Producers may need connection retries and buffering policies.
- **Result-backend failure:** Work may succeed even though its result cannot be stored.
- **Network partition:** Duplicate or delayed delivery may occur.

Design for **at-least-once delivery**, unless the complete system explicitly guarantees otherwise.

---

## 5.10 Monitoring and Operations

### Structured logging

Structured logs use consistent named fields.

```python name=structured_logging.py
import json
import logging

logger = logging.getLogger("worker")
logging.basicConfig(level=logging.INFO)

event = {
    "event": "task_completed",
    "task_id": "a7f2",
    "task_type": "report",
    "duration_ms": 428,
}

logger.info(json.dumps(event))
```

Never log passwords, tokens, connection strings, or unnecessary personal data.

---

### Task and job metrics

Useful metrics include:

- Tasks started, succeeded, failed, and retried
- Queue wait time
- Execution duration
- Timeout count
- Dead-letter count
- Throughput per minute

Track percentiles such as p50, p95, and p99 for duration rather than averages alone.

---

### Queue depth monitoring

Queue depth is the number of waiting tasks.

A growing queue can indicate:

- Insufficient workers
- Slow external dependencies
- Failed consumers
- A sudden traffic increase
- Poison messages

Also monitor the age of the oldest task because a short queue can still contain badly delayed work.

---

### Worker health checks

A useful health check verifies:

- The worker process is running.
- The event loop or heartbeat is responsive.
- The broker is reachable.
- Recent jobs are being processed.

Do not mark a worker healthy only because its operating-system process exists.

---

### Failure alerts

Create alerts for actionable conditions:

- Failure rate above a threshold
- No active workers
- Queue wait time too high
- Dead-letter queue growth
- Repeated scheduler failures
- Broker connection loss

Use sustained thresholds to avoid alerting on one harmless transient failure.

---

### Job tracing and correlation identifiers

A correlation ID connects logs across an API request and its background task.

```python name=correlation_id.py
from uuid import uuid4

correlation_id = str(uuid4())

job_payload = {
    "report_id": 42,
    "correlation_id": correlation_id,
}

print(job_payload)
```

Use a server-generated identifier. Do not treat the identifier as authorization or expose sensitive information through it.

---

### Administrative dashboards

A dashboard commonly displays:

- Active and unavailable workers
- Queue sizes
- Running and failed tasks
- Retry counts
- Job durations
- Scheduled jobs

Protect it with strong authentication, HTTPS, role-based access, and network restrictions.

---

### Performance and capacity monitoring

Monitor:

- CPU and memory usage
- Broker storage and connections
- Worker concurrency
- Database connection-pool usage
- External API rate limits
- Average and percentile task duration
- Tasks produced versus tasks completed

Scale based on queue wait time and resource use, not queue size alone.

## 5.11 Background-Processing Security

### Authenticating broker connections

Use unique broker credentials for each application or environment.

```python name=secure_broker_configuration.py
import os

broker_url = os.environ["CELERY_BROKER_URL"]

if not broker_url:
    raise RuntimeError("CELERY_BROKER_URL is required")
```

Grant workers only the queues and operations they require.

---

### Encrypting network connections

Use TLS for:

- Broker connections
- Result backends
- Databases
- APIs
- Object storage
- Monitoring dashboards

Verify server certificates. Do not disable TLS verification to work around certificate errors.

---

### Restricting task registration

Workers should register only known tasks.

```python name=restricted_tasks.py
ALLOWED_TASKS = {
    "send_email",
    "generate_report",
}


def validate_task_name(task_name: str) -> None:
    if task_name not in ALLOWED_TASKS:
        raise ValueError("Task type is not allowed")
```

Never accept arbitrary Python module names or function names from untrusted input.

---

### Validating task payloads

Validate type, length, range, and allowed values before processing.

```python name=payload_validation.py
from dataclasses import dataclass


@dataclass(frozen=True)
class ReportRequest:
    report_id: int

    def __post_init__(self) -> None:
        if not 1 <= self.report_id <= 1_000_000_000:
            raise ValueError("report_id is outside the allowed range")
```

Workers must validate payloads even when producers also validate them.

---

### Avoiding unsafe deserialization

Prefer JSON for broker messages:

```python name=safe_serialization.py
import json

payload = json.dumps({"report_id": 42})
data = json.loads(payload)

print(data["report_id"])
```

Avoid `pickle` for untrusted messages because deserialization can execute arbitrary code.

---

### Managing secrets securely

Store secrets in:

- A cloud secret manager
- A platform-managed secret store
- Protected environment variables
- Mounted secret files with restrictive permissions

Never place secrets in:

- Source code
- Task arguments
- Queue names
- Job IDs
- Logs
- Error messages

Rotate secrets and restrict who can retrieve them.

---

### Least-privilege worker accounts

Run workers using dedicated, non-administrator accounts with access only to:

- Required queues
- Required database operations
- Necessary directories
- Approved network destinations
- Required secret values

Do not run workers as `root` unless the platform strictly requires it.

---

### Resource and execution limits

Protect worker hosts with:

- Task timeouts
- Memory and CPU limits
- Maximum payload and file sizes
- Concurrency limits
- Network egress restrictions
- Read-only filesystems where possible
- Temporary isolated working directories
- Container or process isolation

Treat document conversion and user-supplied files as high-risk operations and isolate them from the main application.

## Quick Selection Guide

| Requirement | Suggested approach |
|---|---|
| Simple in-process scheduling | APScheduler |
| Distributed, feature-rich task processing | Celery |
| Simple Redis-backed job queue | RQ |
| I/O concurrency in one process | `asyncio` |
| CPU-heavy local parallel processing | `ProcessPoolExecutor` |
| Durable recurring distributed tasks | Celery Beat or a dedicated scheduler |
| Very large record processing | Chunked batch pipeline with checkpoints |

## Recommended Learning Order

1. Learn jobs, queues, workers, and task states.
2. Build a small APScheduler application.
3. Build an RQ producer and worker.
4. Learn Celery for distributed workflows.
5. Add retries, timeouts, idempotency, and dead-letter handling.
6. Add structured logs, metrics, health checks, and alerts.
7. Secure brokers, payloads, secrets, worker accounts, and execution environments.
