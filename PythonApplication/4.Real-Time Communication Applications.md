# 4. Real-Time Communication Applications

Real-time applications exchange information immediately or with very little delay. Examples include chat systems, live notifications, multiplayer games, monitoring dashboards, and IoT devices.

---

## 4.1 Real-Time Communication Fundamentals

### Persistent connections

A persistent connection remains open so clients do not need to reconnect for every message.

```python name=persistent_connection.py
import asyncio


async def handle(reader, writer):
    while data := await reader.readline():
        writer.write(b"Received: " + data)
        await writer.drain()

    writer.close()
    await writer.wait_closed()


asyncio.run(asyncio.start_server(handle, "127.0.0.1", 8000).serve_forever())
```

WebSockets and MQTT normally use persistent connections.

---

### Full-duplex communication

Full-duplex means the client and server can send messages independently at the same time.

```python name=full_duplex_concept.py
import asyncio


async def send_messages():
    while True:
        print("Sending message")
        await asyncio.sleep(2)


async def receive_messages():
    while True:
        print("Receiving message")
        await asyncio.sleep(1)


asyncio.run(asyncio.gather(send_messages(), receive_messages()))
```

In a real application, these tasks operate over the same WebSocket or network connection.

---

### Publish-subscribe architecture

Publishers send messages without knowing which subscribers receive them.

```python name=publish_subscribe.py
subscribers = {}


def subscribe(topic, handler):
    subscribers.setdefault(topic, []).append(handler)


def publish(topic, message):
    for handler in subscribers.get(topic, []):
        handler(message)


subscribe("weather", lambda message: print("Subscriber:", message))
publish("weather", {"temperature": 25})
```

This separates message producers from consumers.

---

### Events and messages

- **Event:** Something that happened, such as `order_created`.
- **Message:** The data sent to describe that event.

```python name=event_message.py
event = {
    "event": "order_created",
    "data": {"order_id": 101, "total": 49.99},
}

print(event["event"], event["data"])
```

Messages should usually include an event type, unique ID, timestamp, and payload.

---

### Topics and channels

Topics or channels organize messages.

Examples:

- `orders/created`
- `devices/sensor-10/temperature`
- `chat/room-42`

```python name=topics.py
topic = "orders/created"

if topic.startswith("orders/"):
    print("Process order event")
```

Use predictable names and avoid placing passwords or sensitive data in topic names.

---

### Presence and connection state

Presence indicates whether a user is online, offline, or temporarily disconnected.

```python name=presence.py
online_users = set()

online_users.add("alice")
print("Alice online:", "alice" in online_users)

online_users.discard("alice")
print("Alice online:", "alice" in online_users)
```

Production systems often store presence in Redis with an expiration time.

---

### Delivery guarantees

Common delivery guarantees are:

- **At-most-once:** The message may be lost but is not retried.
- **At-least-once:** Messages are retried but duplicates are possible.
- **Effectively-once:** Duplicates may arrive, but the application processes each logical message once.

```python name=delivery_guarantee.py
processed_ids = set()


def process(message):
    if message["id"] in processed_ids:
        return

    print("Processing:", message["data"])
    processed_ids.add(message["id"])
```

A durable database or cache should replace the in-memory set in production.

---

### Ordering and duplicate messages

Networks may delay, reorder, or redeliver messages. Sequence numbers help detect these conditions.

```python name=message_ordering.py
last_sequence = 2
message = {"id": "msg-3", "sequence": 3, "text": "Hello"}

if message["sequence"] == last_sequence + 1:
    print(message["text"])
    last_sequence = message["sequence"]
else:
    print("Missing or out-of-order message")
```

## 4.2 WebSocket Applications

WebSocket provides two-way communication over one persistent connection.

Install the example library:

`python -m pip install websockets`

### WebSocket connection lifecycle

Typical lifecycle:

1. Client requests a connection.
2. Server accepts or rejects it.
3. Both sides exchange messages.
4. Heartbeats check connection health.
5. Either side closes the connection.
6. Resources are cleaned up.

Always clean up presence, subscriptions, and other resources after disconnection.

---

### WebSocket server

```python name=websocket_server.py
import asyncio
from websockets.asyncio.server import serve


async def handle_connection(websocket):
    try:
        async for message in websocket:
            await websocket.send(f"Echo: {message}")
    except Exception:
        # Log safely in a real application.
        pass


async def main():
    async with serve(handle_connection, "localhost", 8765):
        await asyncio.Future()


asyncio.run(main())
```

---

### WebSocket client

```python name=websocket_client.py
import asyncio
from websockets.asyncio.client import connect


async def main():
    async with connect("ws://localhost:8765") as websocket:
        await websocket.send("Hello")
        print(await websocket.recv())


asyncio.run(main())
```

Use `wss://` rather than `ws://` across untrusted networks.

---

### Sending text and binary messages

```python name=websocket_messages.py
await websocket.send("Text message")
await websocket.send(b"\x01\x02\x03")
```

- Strings are sent as text frames.
- Bytes are sent as binary frames.
- Validate message type and size before processing.

---

### Connection authentication

Authenticate the connection before allowing access to protected resources.

```python name=websocket_authentication.py
async def authenticate(websocket):
    token = websocket.request.headers.get("Authorization")

    if token != "Bearer expected-token":
        await websocket.close(code=1008, reason="Unauthorized")
        return False

    return True
```

This comparison is only a learning example. In production:

- Validate a short-lived signed token.
- Use HTTPS/WSS.
- Verify expiration, issuer, and audience.
- Never hardcode tokens.
- Avoid putting secrets in URL query strings because URLs may be logged.

---

### Rooms, channels, and groups

A room contains multiple connected clients.

```python name=websocket_rooms.py
rooms = {}


def join_room(room_name, websocket):
    rooms.setdefault(room_name, set()).add(websocket)


def leave_room(room_name, websocket):
    rooms.get(room_name, set()).discard(websocket)
```

Authorize users before allowing them to join a room.

---

### Broadcasting

Broadcasting sends a message to multiple connected clients.

```python name=websocket_broadcast.py
async def broadcast(room, message):
    failed = []

    for connection in rooms.get(room, set()).copy():
        try:
            await connection.send(message)
        except Exception:
            failed.append(connection)

    for connection in failed:
        rooms[room].discard(connection)
```

A slow client should not block every other client. Production systems usually use queues and concurrent sending.

---

### Ping, pong, and heartbeats

Ping/pong frames detect broken or stale connections.

```python name=websocket_heartbeat.py
import asyncio


async def heartbeat(websocket):
    while True:
        pong = await websocket.ping()
        await asyncio.wait_for(pong, timeout=5)
        await asyncio.sleep(20)
```

Many WebSocket libraries provide automatic ping and timeout settings.

---

### Reconnection and session recovery

Clients should reconnect with increasing delays.

```python name=websocket_reconnection.py
import asyncio
from websockets.asyncio.client import connect


async def listen():
    delay = 1

    while True:
        try:
            async with connect("wss://example.com/events") as websocket:
                delay = 1
                async for message in websocket:
                    print(message)
        except Exception:
            await asyncio.sleep(delay)
            delay = min(delay * 2, 30)


asyncio.run(listen())
```

Add random jitter to delays in large systems so all clients do not reconnect simultaneously. Recover missed messages using a last-received event ID.

## 4.3 MQTT Applications

MQTT is a lightweight publish-subscribe protocol frequently used by IoT devices.

Install the Python client:

`python -m pip install paho-mqtt`

### MQTT brokers, clients, and topics

- **Broker:** Receives and routes messages.
- **Client:** Connects to a broker.
- **Topic:** Identifies a message category.

Example topic:

`building/room-1/temperature`

---

### Publishers and subscribers

Publisher:

```python name=mqtt_publisher.py
import paho.mqtt.publish as publish

publish.single(
    "building/room-1/temperature",
    payload="24.5",
    hostname="localhost",
    port=1883,
)
```

Subscriber:

```python name=mqtt_subscriber.py
import paho.mqtt.client as mqtt


def on_message(client, userdata, message):
    value = message.payload.decode("utf-8")
    print(message.topic, value)


client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2)
client.on_message = on_message
client.connect("localhost", 1883)
client.subscribe("building/room-1/temperature")
client.loop_forever()
```

The exact callback signature can depend on the installed Paho MQTT version.

---

### Topic naming and wildcards

MQTT supports two main wildcards:

- `+` matches one topic level.
- `#` matches any remaining levels.

Examples:

```text
building/+/temperature
building/#
```

`building/+/temperature` matches:

```text
building/room-1/temperature
building/room-2/temperature
```

Use narrow subscriptions. Avoid granting devices unrestricted access to `#`.

---

### Quality of Service levels

- **QoS 0:** Delivered at most once.
- **QoS 1:** Delivered at least once; duplicates are possible.
- **QoS 2:** Delivered exactly once at the MQTT protocol level; highest overhead.

```python name=mqtt_qos.py
client.publish(
    "devices/device-10/status",
    payload="online",
    qos=1,
)
```

QoS does not replace application-level validation or idempotency.

---

### Retained messages

A retained message stores the latest value for future subscribers.

```python name=mqtt_retained.py
client.publish(
    "devices/device-10/status",
    payload="online",
    qos=1,
    retain=True,
)
```

Retained messages are useful for state, but usually not for temporary events.

---

### Persistent sessions

Persistent sessions allow the broker to remember subscriptions and queued messages after disconnection.

```python name=mqtt_persistent_session.py
client = mqtt.Client(
    mqtt.CallbackAPIVersion.VERSION2,
    client_id="device-10",
    clean_session=False,
)
```

Use a stable and unique client identifier. Session configuration differs between MQTT protocol versions.

---

### Last Will and Testament messages

A broker publishes a client’s Last Will if that client disconnects unexpectedly.

```python name=mqtt_last_will.py
client.will_set(
    "devices/device-10/status",
    payload="offline",
    qos=1,
    retain=True,
)
```

Publish `online` after connecting successfully.

---

### Secure broker connections

Use TLS and broker authentication.

```python name=mqtt_secure_connection.py
import os
import ssl
import paho.mqtt.client as mqtt

username = os.environ["MQTT_USERNAME"]
password = os.environ["MQTT_PASSWORD"]

client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2)
client.username_pw_set(username, password)
client.tls_set(
    ca_certs="ca.crt",
    cert_reqs=ssl.CERT_REQUIRED,
)
client.connect("mqtt.example.com", 8883)
```

Do not disable certificate verification. Prefer per-device credentials with topic-level permissions.

---

### MQTT for devices and IoT communication

A sensor can publish measurements periodically.

```python name=temperature_sensor.py
import json
import time

while True:
    message = {
        "device_id": "sensor-10",
        "temperature": 24.5,
        "timestamp": time.time(),
    }

    client.publish(
        "devices/sensor-10/temperature",
        json.dumps(message),
        qos=1,
    )
    time.sleep(10)
```

Validate device identity, timestamp, measurement range, and payload size.

## 4.4 Real-Time Chat Systems

### One-to-one messaging

Use a private conversation ID rather than broadcasting to everyone.

```python name=direct_message.py
message = {
    "id": "msg-101",
    "sender_id": "alice",
    "recipient_id": "bob",
    "text": "Hello Bob",
}
```

Verify that the authenticated sender is allowed to access the conversation.

---

### Group chat

```python name=group_chat.py
groups = {"developers": {"alice", "bob"}}


def can_send(user_id, group_id):
    return user_id in groups.get(group_id, set())
```

Never trust a `sender_id` supplied by the client; obtain it from the authenticated session.

---

### User presence

```python name=user_presence.py
from datetime import datetime, timezone

presence = {
    "alice": {
        "status": "online",
        "last_seen": datetime.now(timezone.utc).isoformat(),
    }
}
```

Presence is often approximate because devices can disconnect without sending a close message.

### Typing indicators

Typing indicators are temporary events and normally do not need database storage.


### Message history


Production systems use database pagination instead of loading all messages.

---

### Read and delivery receipts

- **Sent:** Accepted by the sender’s service.
- **Delivered:** Reached the recipient’s device.
- **Read:** Opened or viewed by the recipient.

```python name=message_receipt.py
receipt = {
    "message_id": "msg-101",
    "user_id": "bob",
    "status": "read",
}
```

Receipts should be updated idempotently and must respect user privacy preferences.

---

### Attachments

Store large files in object storage, not directly inside WebSocket messages.

```python name=attachment_metadata.py
attachment = {
    "id": "file-10",
    "name": "report.pdf",
    "size": 204_800,
    "content_type": "application/pdf",
}
```

Validate file size and type, scan for malware, generate random storage names, and use short-lived authorized download links.

---

### Moderation and access controls

```python name=chat_authorization.py
def can_delete_message(user, message):
    return (
        user["id"] == message["sender_id"]
        or "moderator" in user["roles"]
    )
```

Common controls include blocking, muting, reporting, spam detection, and moderator audit logs.

---

### Offline message handling

Store undelivered messages and deliver them when the user reconnects.

```python name=offline_messages.py
offline_messages = {}


def queue_message(user_id, message):
    offline_messages.setdefault(user_id, []).append(message)


def retrieve_messages(user_id):
    return offline_messages.pop(user_id, [])
```

Use durable storage in production and remove messages only after acknowledgement.

## 4.6 Real-Time Message Processing

### Message producers and consumers

```python name=producer_consumer.py
import asyncio

queue = asyncio.Queue()


async def producer():
    await queue.put({"id": "msg-1", "value": 10})


async def consumer():
    message = await queue.get()
    try:
        print("Processing:", message)
    finally:
        queue.task_done()
```

---

### Message routing

```python name=message_routing.py
handlers = {
    "order_created": lambda data: print("Order:", data),
    "user_created": lambda data: print("User:", data),
}


def route(message):
    handler = handlers.get(message["type"])
    if handler:
        handler(message["data"])
```

Reject unsupported message types rather than executing arbitrary functions.

---

### Filtering and transformation

```python name=filter_transform.py
messages = [{"value": 5}, {"value": 20}]

result = [
    {"value": message["value"] * 2}
    for message in messages
    if message["value"] >= 10
]

print(result)
```

Filtering selects messages; transformation changes their structure or values.

---

### Message validation

```python name=message_validation.py
def validate_message(message):
    if not isinstance(message, dict):
        raise ValueError("Message must be an object")

    if message.get("type") not in {"created", "updated"}:
        raise ValueError("Unsupported message type")

    if not isinstance(message.get("data"), dict):
        raise ValueError("data must be an object")
```

Use a schema-validation library for larger applications.

---

### Deduplication

```python name=consumer_deduplication.py
processed = set()


def consume(message):
    message_id = message["id"]

    if message_id in processed:
        return

    print("Processed:", message_id)
    processed.add(message_id)
```

Store deduplication IDs durably and expire them after an appropriate period.

---

### Acknowledgements

An acknowledgement confirms successful processing.

```python name=acknowledgement.py
try:
    process(message)
    acknowledge(message["id"])
except Exception:
    retry_later(message)
```

Acknowledge only after required database work completes successfully.

---

### Dead-letter handling

Messages that repeatedly fail are moved to a dead-letter queue.

```python name=dead_letter.py
def handle_failure(message, error):
    if message["attempts"] >= 5:
        dead_letter_queue.append({
            "message": message,
            "error": type(error).__name__,
        })
```

Do not store secrets or unnecessary personal data in error details.

---

### Retry and backoff strategies

```python name=retry_backoff.py
import asyncio
import random


async def retry(operation, attempts=5):
    for attempt in range(attempts):
        try:
            return await operation()
        except Exception:
            if attempt == attempts - 1:
                raise

            delay = min(2 ** attempt, 30) + random.random()
            await asyncio.sleep(delay)
```

Retry only temporary failures. Invalid messages should normally be rejected or dead-lettered immediately.

## 4.7 Reliability and Scalability

### Reconnection strategies

Use exponential backoff with jitter:

`1s → 2s → 4s → 8s → maximum delay`

Reset the delay after a successful stable connection.

---

### Heartbeat and stale-connection detection

```python name=stale_connection.py
import time

last_heartbeat = time.monotonic()

if time.monotonic() - last_heartbeat > 30:
    print("Connection is stale")
```

Use monotonic time for elapsed-duration checks.

---

### Backpressure

Backpressure prevents fast producers from overwhelming slow consumers.

```python name=backpressure.py
import asyncio

queue = asyncio.Queue(maxsize=100)

# Waits when the queue is full.
await queue.put(message)
```

Possible policies include waiting, rejecting new messages, dropping low-priority events, or disconnecting slow clients.

---

### Connection limits

```python name=connection_limit.py
import asyncio

connection_limit = asyncio.Semaphore(1_000)


async def handle_connection(websocket):
    async with connection_limit:
        await serve_client(websocket)
```

Also set per-user and per-IP limits to reduce abuse.

---

### Horizontal scaling

Horizontal scaling runs multiple application instances behind a load balancer.

```text
Clients
   ↓
Load balancer
   ↓
App 1 ─┐
App 2 ─┼─ Shared broker/database
App 3 ─┘
```

A message broker is needed when clients connected to different instances must communicate.

---

### Shared state and message brokers

Do not rely only on an in-memory room dictionary when multiple servers are running.

Common shared components include:

- Redis Pub/Sub or Streams
- RabbitMQ
- Kafka
- MQTT brokers
- Durable databases

The correct choice depends on persistence, ordering, throughput, and delivery requirements.

---

### Message ordering

Global ordering is expensive. Prefer ordering within a smaller scope, such as:

- Per user
- Per conversation
- Per device
- Per account

Include a sequence number or ordered broker partition key.

---

### Processing guarantees

| Guarantee | Behavior | Main trade-off |
|---|---|---|
| At-most-once | No retry | Messages can be lost |
| At-least-once | Retry until acknowledged | Duplicates can occur |
| Effectively-once | Deduplicate at application level | More storage and complexity |

True end-to-end exactly-once delivery is difficult because brokers, databases, and external services can fail independently.

## 4.8 Real-Time Security

### Secure WebSocket and MQTT connections

Use encrypted protocols:

- WebSocket: `wss://`
- MQTT over TLS: commonly port `8883`

Verify server certificates and use current TLS settings. Do not silently fall back to an insecure connection.

---

### Connection-level authentication

Authenticate every connection using short-lived tokens, certificates, or secure sessions.

```python name=connection_auth.py
def authenticate(token):
    claims = verify_token(token)

    if claims["expired"]:
        raise PermissionError("Authentication expired")

    return claims["user_id"]
```

Regenerate session identifiers after login and securely revoke compromised credentials.

---

### Channel and topic authorization

Authentication answers “Who are you?” Authorization answers “May you access this channel?”

```python name=channel_authorization.py
def may_join(user_id, room):
    return user_id in room["members"]
```

Check authorization on the server for every join, publish, and sensitive read operation.

---

### Per-user permissions

```python name=permissions.py
def require_permission(user, permission):
    if permission not in user["permissions"]:
        raise PermissionError("Operation not permitted")


require_permission(user, "chat:send")
```

Use least privilege and deny access by default.

---

### Message validation

```python name=secure_message_validation.py
MAX_TEXT_LENGTH = 2_000


def validate_chat_message(message):
    text = message.get("text")

    if not isinstance(text, str):
        raise ValueError("text must be a string")

    if not 1 <= len(text) <= MAX_TEXT_LENGTH:
        raise ValueError("Invalid text length")
```

When displaying chat in a browser, use `textContent` or context-aware escaping rather than `innerHTML`.

---

### Rate and payload-size limits

```python name=payload_limit.py
MAX_MESSAGE_BYTES = 64 * 1024

if len(raw_message) > MAX_MESSAGE_BYTES:
    raise ValueError("Message is too large")
```

Apply connection, message-rate, subscription, and upload limits.

---

### Abuse prevention

Common protections include:

- Per-user and per-IP rate limiting
- Spam and repeated-message detection
- Account blocking and reporting
- Connection limits
- Temporary lockouts
- Audit logs
- Automated moderation with human review

Do not trust client-side abuse controls; enforce them on the server.

---

### Sensitive-data protection

- Encrypt network traffic with TLS.
- Encrypt sensitive stored data.
- Keep secrets in a secret manager.
- Avoid sending secrets through topic names or URLs.
- Redact tokens and personal data from logs.
- Apply retention and deletion policies.
- Restrict broker and database access.

End-to-end encryption may be necessary when the server must not read message content.

Real load tests should use dedicated tools and a non-production environment.

### Message-ordering tests

```python name=test_message_order.py
def test_messages_are_ordered():
    messages = [
        {"sequence": 1},

        {"sequence": 3},
```

### Duplicate-message tests

```python name=test_duplicate_message.py
def test_duplicate_is_processed_once():
    processed = set()

    message = {"id": "msg-1"}
    consume(message)
    consume(message)

    assert len(processed) == 1
```

Use an isolated deduplication store for each test.

### Broker failure tests

Test what happens when:

- The broker becomes unavailable.
- The connection is interrupted.
- A publish times out.
- An acknowledgement is lost.
- The broker restarts.
- Queues reach capacity.

The application should retry temporary failures without losing or endlessly duplicating messages.

### Load and latency testing

Important measurements include:

- Active connections
- Messages per second
- End-to-end latency
- Error rate
- Reconnection rate
- Queue size
- CPU and memory usage

```python name=latency_measurement.py
import time

started = time.perf_counter()
process_message()
latency_ms = (time.perf_counter() - started) * 1_000

print(f"Latency: {latency_ms:.2f} ms")
```

Measure percentiles such as p50, p95, and p99 rather than only the average.

## Quick Technology Guide

| Requirement | Common choice |
|---|---|
| Browser chat or live dashboard | WebSocket |
| IoT sensors and devices | MQTT |
| Internal task processing | Message queue |
| High-throughput event stream | Distributed event broker |
| Temporary cross-server broadcasts | Pub/Sub broker |
| Durable message history | Database or durable stream |

A practical learning sequence is:

1. Build a simple WebSocket echo server.
2. Add authentication and message validation.
3. Add rooms and broadcasting.
4. Store message history.
5. Add heartbeats and reconnection.
6. Add a shared broker for horizontal scaling.
7. Test duplicates, failures, concurrency, and latency.
8. Apply TLS, authorization, rate limits, and secure logging.
