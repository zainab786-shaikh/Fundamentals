
# Topic 6: Database Migrations with Alembic

Alembic tracks and applies database schema changes safely.

## 1. Install Alembic

```bash name=install.sh
pip install alembic
```

Alembic works with SQLAlchemy to manage schema versions.

---

## 2. Initialize Alembic

Run this command from the project root:

```bash name=initialize.sh
alembic init migrations
```

It creates:

- `alembic.ini`: Alembic configuration
- `migrations/env.py`: Migration environment
- `migrations/versions/`: Migration files

---

## 3. Configure the Database URL

Use the same environment-based URL as the application:

```python name=migrations/env.py
import os

from alembic import context
from sqlalchemy import engine_from_config, pool

from models.base import Base
from models.post import Post
from models.user import User

config = context.config

database_url = os.environ["DATABASE_URL"]
config.set_main_option("sqlalchemy.url", database_url)

target_metadata = Base.metadata


def run_migrations_offline() -> None:
    context.configure(
        url=database_url,
        target_metadata=target_metadata,
        literal_binds=True,
        compare_type=True,
    )

    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    connectable = engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )

    with connectable.connect() as connection:
        context.configure(
            connection=connection,
            target_metadata=target_metadata,
            compare_type=True,
        )

        with context.begin_transaction():
            context.run_migrations()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

Importing the models registers their tables in `Base.metadata`. The database password remains outside source control.

Example development configuration:

```text name=.env.example
DATABASE_URL=postgresql+psycopg://app_user:change_me@localhost:5432/app_db
```

Do not commit a real `.env` file.

## 4. Create the Initial Migration

```bash name=create-initial-migration.sh
alembic revision --autogenerate -m "create users and posts tables"
```

`--autogenerate` compares SQLAlchemy models with the current database schema and creates a migration.

Always review generated migrations before applying them.

---

## 5. Review a Migration

```python name=migrations/versions/001_create_users.py
from collections.abc import Sequence

import sqlalchemy as sa
from alembic import op

revision: str = "001"
down_revision: str | None = None
branch_labels: str | Sequence[str] | None = None
depends_on: str | Sequence[str] | None = None


def upgrade() -> None:
    op.create_table(
        "users",
        sa.Column("id", sa.Integer(), primary_key=True),
        sa.Column("name", sa.String(100), nullable=False),
        sa.Column("email", sa.String(255), nullable=False),
        sa.UniqueConstraint("email"),
    )
    op.create_index("ix_users_email", "users", ["email"])


def downgrade() -> None:
    op.drop_index("ix_users_email", table_name="users")
    op.drop_table("users")
```

- `upgrade()` applies the schema change.
- `downgrade()` reverses it.
- Constraints should exist in both ORM models and migrations.

## 6. Apply Migrations

```bash name=upgrade.sh
alembic upgrade head
```

`head` means the newest available migration.

Check the current version:

```bash name=current-version.sh
alembic current
```

## 7. Add a New Column

First, update the ORM model:

```python name=models/user.py
from sqlalchemy import Boolean, String
from sqlalchemy.orm import Mapped, mapped_column

from models.base import Base


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(100))
    email: Mapped[str] = mapped_column(String(255), unique=True, index=True)
    is_active: Mapped[bool] = mapped_column(
        Boolean,
        nullable=False,
        default=True,
        server_default="true",
    )
```

Then generate and apply the migration:

```bash name=add-column.sh
alembic revision --autogenerate -m "add is_active to users"
alembic upgrade head
```

`server_default` lets the database populate the column for existing and newly inserted rows.

## 8. Rename a Column Safely

Autogeneration may interpret a rename as deleting one column and creating another. Write the rename explicitly:

```python name=migrations/versions/002_rename_name.py
from alembic import op


def upgrade() -> None:
    op.alter_column(
        "users",
        "name",
        new_column_name="display_name",
    )


def downgrade() -> None:
    op.alter_column(
        "users",
        "display_name",
        new_column_name="name",
    )
```

An explicit rename preserves existing data.

---

## 9. Revert a Migration

Revert the most recently applied migration:

```bash name=downgrade.sh
alembic downgrade -1
```

Revert to a specific revision:

```bash name=downgrade-specific.sh
alembic downgrade 001
```

Back up production data before downgrading because some reversals can destroy data.

---

## 10. View Migration History

```bash name=history.sh
alembic history --verbose
```

This displays migration revisions and their order.

---

## 11. Production Migration Practices

```bash name=production-migration.sh
alembic current
alembic upgrade head
```

Before production migration:

1. Back up the database.
2. Review the generated SQL.
3. Test the migration against a staging database.
4. Avoid destructive changes in the same release.
5. Prepare a rollback or recovery plan.
6. Run migrations once, not from every application instance.

Generate SQL for review without applying it:

```bash name=preview-migration.sh
alembic upgrade head --sql
```
