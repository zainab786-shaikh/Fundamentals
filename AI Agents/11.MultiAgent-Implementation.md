## Practical Project: Customer Support Ticket Triage

We’ll build a **simple multi-agent system** for a small online store.

**Goal:** When a customer submits a support ticket, the system decides:
1. What the customer needs
2. How urgent it is
3. Which team should handle it
4. What response to send

Example ticket:

> “My order was marked delivered, but I did not receive it.”

We’ll cover **one topic per response**. Today: **1. Foundational Concepts**.

---

## 1. Foundational Concepts

A **multi-agent system** is a team of small AI agents. Each agent has a focused responsibility, rather than asking one large agent to do everything.

### Single-agent approach

One agent reads the ticket and performs every task:

```text
Ticket → One AI agent → Category, priority, assignment, response
```

This is simple, but the agent has many responsibilities at once.

### Multi-agent approach

Several specialized agents collaborate:

```text
Ticket
  ↓
Ticket Analyzer Agent
  ├─→ Priority Agent
  ├─→ Routing Agent
  └─→ Response Agent
  ↓
Final Support Decision
```

### Agents in our example

| Agent | Responsibility | Example output |
|---|---|---|
| **Ticket Analyzer** | Understand the customer’s request | `delivery problem` |
| **Priority Agent** | Determine urgency | `high` |
| **Routing Agent** | Choose the responsible team | `shipping support` |
| **Response Agent** | Draft a safe, helpful reply | “We’re sorry—our shipping team will investigate.” |

### Why use multiple agents?

Each agent has a narrow goal, so its instructions are easier to understand, test, and improve.

For example:

- The **Priority Agent** should not write customer emails.
- The **Response Agent** should not decide refunds unless policy explicitly permits it.
- The **Routing Agent** should only choose from approved teams.

This follows **least privilege**: each agent receives only the permissions and data it actually needs. It reduces mistakes such as an AI accidentally issuing refunds or exposing customer data.

### Simple end-to-end example

**Input:**

```text
Customer: “My order was marked delivered, but I did not receive it.”
Order ID: ORD-1042
```

**Agent collaboration:**

```text
Ticket Analyzer → category: delivery_not_received
Priority Agent → priority: high
Routing Agent → destination: shipping_support
Response Agent → draft response: acknowledge issue and explain next step
```

**Final result:**

```text
Category: Delivery not received
Priority: High
Assigned team: Shipping Support
Customer reply: “I’m sorry your order has not arrived. Our shipping team will
investigate the delivery status and update you shortly.”
```

### Key takeaway

A multi-agent system is not necessarily complicated. It can simply be:

> **One task → several focused agents → one combined result**

Next: **2. Coordination Architectures / Topologies** — we’ll decide how these four agents should be connected and who controls the workflow.

---

## 2. Coordination Architectures / Topologies

A **topology** is simply the structure of communication between agents: **who talks to whom and in what order**.

For our support-ticket project, we’ll use a **centralized coordinator** pattern because it is the easiest to understand and control.

```text
Customer Ticket
      ↓
Coordinator Agent
      ↓
Ticket Analyzer
      ↓
Priority Agent
      ↓
Routing Agent
      ↓
Response Agent
      ↓
Coordinator Agent
      ↓
Final Support Decision
```

### What does the Coordinator do?

The **Coordinator Agent** does not need to solve the ticket itself. Its job is to:

1. Send the ticket to the right specialist agent.
2. Collect each agent’s result.
3. Check that required information is present.
4. Produce one final, structured result.

Think of it as a team lead coordinating specialists.

### Example workflow

**Customer ticket:**

> “My order was marked delivered, but I did not receive it.”

| Step | Agent | Result |
|---|---|---|
| 1 | Ticket Analyzer | `category: delivery_not_received` |
| 2 | Priority Agent | `priority: high` |
| 3 | Routing Agent | `team: shipping_support` |
| 4 | Response Agent | Drafts a polite response |
| 5 | Coordinator | Combines and validates the result |

**Final output:**

```json
{
  "category": "delivery_not_received",
  "priority": "high",
  "assignedTeam": "shipping_support",
  "customerResponse": "I’m sorry your order has not arrived. Our shipping team will investigate the delivery status and update you shortly."
}
```

### Why choose centralized coordination?

| Benefit | Why it helps |
|---|---|
| **Easy to follow** | One agent controls the sequence. |
| **Easy to test** | Each step has a clear input and output. |
| **Safer** | The coordinator can reject incomplete or invalid results. |
| **Good for beginners** | No complex agent-to-agent discussions. |

### Alternative: agents communicate directly

In a decentralized system, agents might message each other directly:

```text
Ticket Analyzer ↔ Priority Agent ↔ Routing Agent ↔ Response Agent
```

This can be useful for complex, collaborative work, but it is harder to debug. An agent may send incomplete information, repeat work, or create circular conversations.

For this simple project, **centralized orchestration is the better choice**.

### Security rule

The coordinator should enforce an approved output format and permitted routing values:

```text
Allowed teams:
- shipping_support
- billing_support
- technical_support
```

If an agent returns an unknown team, such as `executive_team`, the coordinator should reject it and route the ticket for human review. This prevents unsafe or unexpected automated actions.

**Next:** **3. Agent Roles & Specialization** — we’ll define exactly what each agent can do, what it cannot do, and the information it receives.

---

## 3. Agent Roles & Specialization

Each agent should have **one clear responsibility**. This makes the system easier to understand, test, and secure.

For our customer-support ticket system, we use five roles.

| Agent | Main responsibility | Must not do |
|---|---|---|
| **Coordinator** | Runs the workflow and validates final output | Invent policies or directly issue refunds |
| **Ticket Analyzer** | Classifies the customer’s issue | Set priority or write the final reply |
| **Priority Agent** | Determines ticket urgency | Access payment or customer-address details |
| **Routing Agent** | Selects an approved support team | Create new teams or contact customers |
| **Response Agent** | Drafts a customer-friendly response | Promise refunds, credits, or delivery dates |

---

### 1. Coordinator Agent

The coordinator is the **workflow manager**.

It sends information to each specialist, verifies their outputs, and creates the final result.

```text
Input: Customer ticket
Output: Validated final support decision
```

It should only accept known categories, priorities, and teams.

```text
Allowed priorities: low, medium, high
Allowed teams: shipping_support, billing_support, technical_support
```

If a result does not match the approved list, the coordinator should stop automation and send the ticket to a human.

---

### 2. Ticket Analyzer Agent

This agent reads the ticket and assigns a category.

```text
Input:
“My order was marked delivered, but I did not receive it.”

Output:
delivery_not_received
```

Possible categories:

```text
delivery_not_received
damaged_item
refund_request
payment_problem
technical_problem
other
```

It does **not** decide urgency or the support team. Its only job is to understand the problem.

---

### 3. Priority Agent

This agent decides how quickly the ticket needs attention.

Example rules:

| Situation | Priority |
|---|---|
| Customer cannot access their account | High |
| Order is missing or wrongly delivered | High |
| Customer asks where to find a feature | Low |
| Customer reports a minor website issue | Medium |

For our ticket:

```text
Category: delivery_not_received
Priority: high
```

To protect privacy, this agent should receive only the category and minimal context—not the customer’s full address, payment details, or unnecessary personal information.

---

### 4. Routing Agent

This agent assigns the ticket to one of the approved teams.

```text
Input:
category: delivery_not_received

Output:
shipping_support
```

Simple routing rules:

```text
delivery_not_received → shipping_support
damaged_item          → shipping_support
refund_request        → billing_support
payment_problem       → billing_support
technical_problem     → technical_support
```

The agent must choose only from the allow-listed teams. If the category is unknown, use:

```text
human_review
```

---

### 5. Response Agent

This agent writes a short, polite reply using the validated results.

```text
Input:
Category: delivery_not_received
Priority: high

Output:
“I’m sorry your order has not arrived. Our shipping team will investigate the
delivery status and update you shortly.”
```

Important safety rule: it should not promise outcomes it cannot guarantee.

**Avoid:**

> “We will refund you today.”

**Prefer:**

> “Our team will review the delivery status and let you know the available next steps.”

---

### Key takeaway

Specialization means each agent has:

- A **small, specific job**
- Only the **data it needs**
- Limited permissions
- Clear rules for when to send work to a **human**

This reduces errors and makes the overall system safer.

**Next:** **4. Communication Protocols** — we’ll define the structured messages agents send to one another.

---

## 4. Communication Protocols

A **communication protocol** defines how agents exchange information.

For a simple system, use **structured JSON messages**. This is safer and easier to validate than letting agents send free-form text to each other.

```text
Coordinator → Agent → Structured result → Coordinator
```

---

### Why structured messages?

Without a clear format, one agent might return:

> “This seems urgent and should probably go to shipping.”

That is understandable to a person, but difficult for software to process reliably.

Instead, require a predictable response:

```json
{
  "category": "delivery_not_received",
  "confidence": 0.95
}
```

The coordinator can validate every field before continuing.

---

## Message 1: Coordinator to Ticket Analyzer

The coordinator sends only the information needed to classify the ticket.

```json
{
  "ticketId": "TICKET-1001",
  "message": "My order was marked delivered, but I did not receive it."
}
```

The Ticket Analyzer responds:

```json
{
  "ticketId": "TICKET-1001",
  "category": "delivery_not_received",
  "confidence": 0.95
}
```

### Validation rules

The coordinator checks:

- `ticketId` is present.
- `category` is from the approved list.
- `confidence` is a number between `0` and `1`.

If confidence is too low—for example, below `0.70`—the system should use `human_review`.

---

## Message 2: Coordinator to Priority Agent

The Priority Agent does not need the entire customer message. It receives the classified category.

```json
{
  "ticketId": "TICKET-1001",
  "category": "delivery_not_received"
}
```

Response:

```json
{
  "ticketId": "TICKET-1001",
  "priority": "high",
  "reason": "A marked-delivered but missing order may require prompt investigation."
}
```

The `reason` is useful for logs and human review, but it should not contain sensitive customer information.

---

## Message 3: Coordinator to Routing Agent

```json
{
  "ticketId": "TICKET-1001",
  "category": "delivery_not_received",
  "priority": "high"
}
```

Response:

```json
{
  "ticketId": "TICKET-1001",
  "assignedTeam": "shipping_support"
}
```

The coordinator validates that `assignedTeam` is allow-listed:

```text
shipping_support
billing_support
technical_support
human_review
```

---

## Message 4: Coordinator to Response Agent

The Response Agent receives only the validated data required to draft a reply.

```json
{
  "ticketId": "TICKET-1001",
  "category": "delivery_not_received",
  "priority": "high",
  "assignedTeam": "shipping_support"
}
```

Response:

```json
{
  "ticketId": "TICKET-1001",
  "customerResponse": "I’m sorry your order has not arrived. Our shipping team will investigate the delivery status and update you shortly."
}
```

---

## Handling failures

Every response should include the same ticket ID, so results cannot accidentally be connected to the wrong customer.

If an agent fails or returns invalid data:

```json
{
  "ticketId": "TICKET-1001",
  "status": "needs_human_review",
  "reason": "The routing result was not an approved team."
}
```

Do not guess, retry indefinitely, or take customer-impacting actions automatically.

---

### Key takeaway

A good communication protocol uses:

- **Structured data**, such as JSON
- **Required fields** and allow-listed values
- A shared correlation ID, such as `ticketId`
- **Validation** at every step
- A safe fallback: `human_review`

**Next:** **5. Task Allocation & Planning** — we’ll decide which agent works first, which tasks can run at the same time, and when the workflow should stop.

---

## 5. Task Allocation & Planning

**Task allocation** means deciding which agent handles each piece of work.  
**Planning** means deciding the order in which those tasks run.

For our simple ticket-triage system, we use a fixed plan.

```text
1. Analyze the ticket
2. Decide priority
3. Route to a team
4. Draft a response
5. Validate and return the result
```

---

### Which agent does each task?

| Step | Task | Agent | Depends on |
|---|---|---|---|
| 1 | Identify the issue category | Ticket Analyzer | Customer message |
| 2 | Choose urgency | Priority Agent | Category |
| 3 | Choose support team | Routing Agent | Category |
| 4 | Draft customer response | Response Agent | Validated category, priority, and team |
| 5 | Validate and combine results | Coordinator | All prior results |

---

## Sequential and parallel work

Some tasks must wait for earlier results. Others can run at the same time.

### Step 1 must run first

The Ticket Analyzer creates the category:

```text
Customer message → Ticket Analyzer → delivery_not_received
```

The other agents need that category, so they wait.

### Steps 2 and 3 can run in parallel

Once the category is available, the coordinator can ask both agents at the same time:

```text
                         ┌→ Priority Agent → high
Category ────────────────┤
                         └→ Routing Agent  → shipping_support
```

This makes the workflow faster without adding much complexity.

### Step 4 waits for validation

The Response Agent should run only after priority and routing outputs are valid:

```text
Validated category + priority + team → Response Agent → customer reply
```

This prevents it from mentioning an incorrect team or making unsupported promises.

---

## Simple workflow plan

```text
START
  ↓
Classify ticket
  ↓
Is the category valid and confidence ≥ 0.70?
  ├─ No → Human review → END
  └─ Yes
       ↓
  Run priority and routing in parallel
       ↓
  Are both results valid?
  ├─ No → Human review → END
  └─ Yes
       ↓
  Draft response
       ↓
  Validate final response
       ↓
END
```

---

## Example

**Input:**

> “My order was marked delivered, but I did not receive it.”

**Plan execution:**

```text
1. Ticket Analyzer
   → category: delivery_not_received
   → confidence: 0.95

2. Priority Agent and Routing Agent, in parallel
   → priority: high
   → assignedTeam: shipping_support

3. Response Agent
   → “I’m sorry your order has not arrived. Our shipping team will
      investigate the delivery status and update you shortly.”
```

---

## Safe stopping rules

The coordinator should stop automated processing and use `human_review` when:

- The category is missing or not allow-listed.
- Classification confidence is below `0.70`.
- An agent response is malformed or has a mismatched `ticketId`.
- The assigned team is not approved.
- A response includes prohibited promises, such as guaranteed refunds.
- An agent times out or fails after a limited retry.

Use a small retry limit—for example, **one retry** for transient failures—then hand off to a human. This avoids infinite loops and protects the customer experience.

---

### Key takeaway

A plan makes the team predictable:

- **Classify first**
- **Run independent tasks in parallel**
- **Validate before the next step**
- **Stop safely when information is uncertain**

**Next:** **6. Shared State & Memory** — we’ll show where the agents store the ticket’s progress and what information each agent is allowed to read.

---

## 6. Shared State & Memory

**Shared state** is the current, structured record of one ticket as it moves through the agent workflow.

**Memory** is information the system keeps for later—such as previous ticket history or approved support policies.

For this beginner project, keep them separate:

- **Shared state:** short-lived data for the current ticket.
- **Memory:** carefully controlled long-term information.

---

## Shared state: one ticket record

The coordinator owns the ticket record and updates it after each validated agent result.

```text
Ticket received
  ↓
Coordinator creates ticket state
  ↓
Agents read only the fields needed for their job
  ↓
Coordinator validates and saves their result
```

Example state:

```json
{
  "ticketId": "TICKET-1001",
  "status": "in_progress",
  "customerMessage": "My order was marked delivered, but I did not receive it.",
  "category": "delivery_not_received",
  "classificationConfidence": 0.95,
  "priority": "high",
  "assignedTeam": "shipping_support",
  "customerResponse": null,
  "requiresHumanReview": false
}
```

As the system progresses, the coordinator fills in fields one at a time.

---

## Who can read what?

Agents should receive only the information required for their task.

| Agent | Can receive | Should not receive unless necessary |
|---|---|---|
| Ticket Analyzer | Ticket message | Payment details, full customer profile |
| Priority Agent | Category and minimal context | Customer address or payment data |
| Routing Agent | Category and priority | Customer identity |
| Response Agent | Validated category, priority, and team | Internal-only notes or sensitive data |
| Coordinator | Validated workflow state | Unrestricted access by default |

This is called **data minimization**. It reduces privacy risk and limits damage if an agent makes a mistake.

---

## Short-term memory

Short-term memory exists only while the ticket is being handled.

For example, the system remembers:

```text
Ticket ID: TICKET-1001
Category: delivery_not_received
Priority: high
Assigned team: shipping_support
```

When the ticket is complete, keep only the records required for customer support, auditing, and legal retention rules. Do not retain unnecessary raw AI prompts or sensitive content indefinitely.

---

## Long-term memory

Long-term memory can help with future tickets, but it must be controlled.

Useful long-term information includes:

- Approved issue categories
- Routing rules
- Support response templates
- Refund and delivery policies
- Anonymized trends, such as frequently reported delivery issues

Example policy memory:

```text
Policy:
For “delivery_not_received” tickets:
- Route to shipping_support.
- Do not promise a refund.
- Ask the shipping team to investigate.
- Escalate to a human if order details conflict.
```

The Response Agent can use this policy, but it should not freely access every past customer conversation.

---

## Avoid unsafe memory

Do **not** let the system automatically learn and reuse everything customers say.

For example, this is unsafe:

```text
Customer ticket → save permanently → reuse in future AI prompts
```

It may expose personal information to unrelated tickets.

Instead:

```text
Customer ticket → process with limited access
                 → retain only approved support records
                 → store anonymized lessons separately
```

---

## Example: state updates

```text
1. Coordinator creates:
   status: in_progress

2. Ticket Analyzer returns:
   category: delivery_not_received
   confidence: 0.95

3. Coordinator validates and saves the result.

4. Priority and Routing Agents return:
   priority: high
   assignedTeam: shipping_support

5. Coordinator validates and saves both results.

6. Response Agent returns:
   customerResponse: “I’m sorry your order has not arrived...”

7. Coordinator marks:
   status: ready_for_support_team
```

---

### Key takeaway

Shared state gives every agent a reliable view of the current ticket, while memory provides carefully selected information for future work.

Keep it safe by:

- Letting the **coordinator** control updates
- Giving agents only the fields they need
- Validating every change
- Separating current ticket data from long-term knowledge
- Avoiding unnecessary storage of customer information

**Next:** **7. Control Flow & Orchestration** — we’ll look at how the coordinator controls decisions, retries, human escalation, and completion.

---

## 7. Control Flow & Orchestration

**Control flow** is the set of rules that determines what happens next.

**Orchestration** is the coordinator managing those rules across all agents.

In our project, the Coordinator Agent controls the workflow. Specialist agents provide results, but they do not decide the overall process.

```text
Customer Ticket
      ↓
Coordinator starts workflow
      ↓
Ticket Analyzer
      ↓
Validate result
      ↓
Priority + Routing Agents
      ↓
Validate results
      ↓
Response Agent
      ↓
Final validation and handoff
```

---

## The coordinator’s decisions

The coordinator decides whether to:

- Continue to the next agent
- Retry a failed agent once
- Send the ticket for human review
- Mark the ticket ready for a support team

### Simple decision flow

```text
START
  ↓
Analyze ticket
  ↓
Is category valid and confidence ≥ 0.70?
  ├─ No → Send to human review → END
  └─ Yes
       ↓
   Get priority and routing results
       ↓
   Are both results valid?
  ├─ No → Send to human review → END
  └─ Yes
       ↓
   Draft customer response
       ↓
   Is the response safe and non-promissory?
  ├─ No → Send to human review → END
  └─ Yes
       ↓
   Assign ticket and save response
       ↓
END
```

---

## Example: successful ticket

**Customer message:**

> “My order was marked delivered, but I did not receive it.”

```text
1. Coordinator → Ticket Analyzer
   Result: delivery_not_received, confidence 0.95

2. Coordinator validates result.
   Result is valid, so continue.

3. Coordinator → Priority Agent and Routing Agent
   Results:
   - priority: high
   - team: shipping_support

4. Coordinator validates both results.
   Results are valid, so continue.

5. Coordinator → Response Agent
   Result:
   “I’m sorry your order has not arrived. Our shipping team will investigate
   the delivery status and update you shortly.”

6. Coordinator checks the response:
   - Does not promise a refund
   - Does not expose internal details
   - Uses the correct team name

7. Ticket is assigned to shipping support.
```

---

## Example: uncertain ticket

**Customer message:**

> “Something is wrong with my recent purchase.”

The Ticket Analyzer returns:

```json
{
  "ticketId": "TICKET-1002",
  "category": "other",
  "confidence": 0.42
}
```

Because confidence is below `0.70`, the coordinator should not guess.

```json
{
  "ticketId": "TICKET-1002",
  "status": "needs_human_review",
  "reason": "Ticket category could not be determined with sufficient confidence."
}
```

This is safer than sending the customer to the wrong team.

---

## Retry rule

Agents can sometimes fail because of temporary problems, such as a network timeout.

Use a strict retry policy:

```text
Agent fails
  ↓
Retry once
  ↓
Still fails?
  ↓
Human review
```

Do not retry forever. Repeated retries can delay support and increase cost.

---

## Final states

Each ticket should end in a clear state.

| State | Meaning |
|---|---|
| `ready_for_support_team` | Valid result; assigned to an approved team |
| `needs_human_review` | The system is uncertain, invalid, or failed |
| `completed` | A support agent resolved the ticket |
| `failed` | A technical failure requires investigation |

---

### Key takeaway

The Coordinator Agent is the system’s traffic controller:

- It decides the sequence of work.
- It validates every result.
- It limits retries.
- It stops unsafe automation.
- It escalates uncertain cases to people.

**Next:** **8. Consensus, Conflict & Collaboration** — we’ll handle cases where agents disagree, such as one agent choosing `high` priority while another result suggests the ticket is low urgency.

---

## 8. Consensus, Conflict & Collaboration

In a multi-agent system, agents may sometimes produce results that do not fit together.

For example:

```text
Ticket Analyzer → category: delivery_not_received
Priority Agent → priority: low
```

A missing order is usually urgent enough to need prompt attention, so the Coordinator should recognize that this combination may be inconsistent.

---

## What is consensus?

**Consensus** means reaching a trusted final decision from multiple agent results.

For this simple project, agents do **not** debate each other. Instead, the Coordinator uses clear rules to resolve disagreements.

```text
Specialist results
      ↓
Coordinator checks for conflicts
      ↓
Apply approved policy
      ↓
Use final result or send to human review
```

This is easier to test and safer than allowing unlimited agent conversations.

---

## Common conflicts

| Conflict | Example | Safe response |
|---|---|---|
| Category and priority disagree | Missing delivery classified as `low` priority | Apply policy or escalate |
| Category and assigned team disagree | `payment_problem` sent to `shipping_support` | Correct using routing rules |
| Two classifications disagree | One agent says `damaged_item`, another says `refund_request` | Ask for human review |
| Response contradicts policy | Reply promises an automatic refund | Reject and regenerate once or escalate |
| Agent result is invalid | Unknown team or missing ticket ID | Reject and use human review |

---

## Conflict example 1: priority does not match policy

**Customer message:**

> “My order was marked delivered, but I did not receive it.”

Results:

```json
{
  "category": "delivery_not_received",
  "priority": "low",
  "assignedTeam": "shipping_support"
}
```

The Coordinator checks the approved policy:

```text
delivery_not_received → priority must be high
```

It can safely correct the priority only when the rule is explicit:

```json
{
  "category": "delivery_not_received",
  "priority": "high",
  "assignedTeam": "shipping_support",
  "resolution": "Priority set by approved policy."
}
```

### Important rule

Use deterministic policy rules for known cases. Do **not** let an agent override policy without authorization.

---

## Conflict example 2: routing does not match the category

Results:

```json
{
  "category": "payment_problem",
  "priority": "high",
  "assignedTeam": "shipping_support"
}
```

Approved routing policy:

```text
payment_problem → billing_support
```

The Coordinator rejects the incorrect routing result and uses the allow-listed rule:

```json
{
  "category": "payment_problem",
  "priority": "high",
  "assignedTeam": "billing_support",
  "resolution": "Team set by approved routing policy."
}
```

---

## Conflict example 3: uncertainty requires a person

**Customer message:**

> “I was charged twice, and my package also arrived damaged.”

This ticket contains two valid problems:

```text
payment_problem
damaged_item
```

A simple system may not support multiple categories. The Coordinator should not choose one and ignore the other.

```json
{
  "ticketId": "TICKET-1003",
  "status": "needs_human_review",
  "reason": "The ticket contains multiple issues requiring billing and shipping support."
}
```

Later, a more advanced system could split this into two linked tasks. For now, human review is clearer and safer.

---

## Collaboration rules

For a beginner-friendly system, use these rules:

1. **Agents provide recommendations, not final authority.**
2. **The Coordinator validates every result.**
3. **Approved policies win over agent guesses.**
4. **Conflicting or uncertain results go to human review.**
5. **Log the decision and reason** for auditing and troubleshooting.
6. **Never allow agents to issue refunds, modify orders, or access payment details** unless a separate, authorized workflow permits it.

---

## Simple resolution order

```text
1. Is the agent output valid?
   No → Human review

2. Does it match an explicit policy?
   Yes → Apply the policy

3. Do agents disagree or is the request multi-part?
   Yes → Human review

4. Otherwise:
   Continue the workflow
```

---

### Key takeaway

Collaboration does not mean agents need long conversations. For simple systems, it means:

- Specialists provide focused results.
- The Coordinator compares them.
- Clear policies resolve known conflicts.
- Humans handle unclear or high-impact cases.

## 9. Multi-Agent Frameworks: LangChain and LangGraph

For our simple support-ticket example, we will focus on:

- **LangChain** — helps connect AI models, prompts, tools, and structured outputs.
- **LangGraph** — helps control multi-step and multi-agent workflows.

They work well together:

```text
LangChain = builds individual agents
LangGraph = controls how agents move through the workflow
```

---

## LangChain

LangChain is useful for creating each specialist agent.

For example, we could create:

- A Ticket Analyzer agent
- A Priority agent
- A Routing agent
- A Response agent

Each agent receives a prompt, processes input, and returns structured data.

```text
Ticket Analyzer
Input: customer message
Output: category + confidence
```

Conceptually:

```text
Customer message
      ↓
LangChain agent
      ↓
Structured JSON result
```

Example agent output:

```json
{
  "category": "delivery_not_received",
  "confidence": 0.95
}
```

### Best use of LangChain in this project

Use LangChain for:

- Calling the AI model
- Defining each agent’s instructions
- Enforcing structured output
- Connecting agents to approved tools or knowledge sources
- Validating basic input and output formats

Do **not** give every agent unrestricted access to databases, email, refunds, or order updates. Each agent should get only the tools and data it needs.

---

## LangGraph

LangGraph is useful for defining the workflow between agents.

It represents the process as a graph:

```text
Nodes = steps or agents
Edges = paths between those steps
```

For our system:

```text
START
  ↓
Ticket Analyzer
  ↓
Validate Category
  ├─ Invalid / uncertain → Human Review → END
  └─ Valid
       ↓
  Priority Agent + Routing Agent
       ↓
  Validate Results
  ├─ Invalid → Human Review → END
  └─ Valid
       ↓
  Response Agent
       ↓
  Final Validation
       ↓
END
```

Each agent becomes a **node** in the graph.

| LangGraph node | Responsibility |
|---|---|
| `analyzeTicket` | Classify the issue |
| `validateCategory` | Check category and confidence |
| `determinePriority` | Choose urgency |
| `routeTicket` | Select an approved team |
| `draftResponse` | Create a customer reply |
| `humanReview` | Stop automation and escalate |
| `finalizeTicket` | Save the validated result |

---

## Why LangGraph fits multi-agent systems

LangGraph is helpful when a workflow needs:

- Clear agent order
- Conditional decisions
- Shared state
- Parallel tasks
- Retry limits
- Human approval steps

Our earlier workflow maps directly to this.

```text
Category available
      ↓
Priority Agent ─┐
                ├─→ Coordinator validates both results
Routing Agent ──┘
```

The priority and routing steps can run in parallel after classification.

---

## Shared state in LangGraph

LangGraph keeps a shared state object that moves through the graph.

Example:

```json
{
  "ticketId": "TICKET-1001",
  "customerMessage": "My order was marked delivered, but I did not receive it.",
  "category": "delivery_not_received",
  "classificationConfidence": 0.95,
  "priority": "high",
  "assignedTeam": "shipping_support",
  "customerResponse": null,
  "status": "in_progress",
  "requiresHumanReview": false
}
```

Each node should update only its assigned fields.

| Node | Permitted state updates |
|---|---|
| Ticket Analyzer | `category`, `classificationConfidence` |
| Priority Agent | `priority` |
| Routing Agent | `assignedTeam` |
| Response Agent | `customerResponse` |
| Coordinator / validation nodes | `status`, `requiresHumanReview`, audit fields |

This prevents one agent from changing unrelated data.

---

## Simple comparison

| Feature | LangChain | LangGraph |
|---|---|---|
| Main purpose | Build AI-powered agent steps | Orchestrate the overall workflow |
| Best for | Prompts, models, tools, structured output | Agent order, branching, state, retries |
| In this project | Build each specialist | Connect and control the specialists |
| Can be used alone? | Yes, for simple linear tasks | Yes, but commonly used with LangChain components |

---

## Recommended approach

For this project:

```text
LangChain:
- Create the four specialist agents.
- Require validated JSON outputs.

LangGraph:
- Coordinate the agent workflow.
- Run priority and routing in parallel.
- Validate every result.
- Send uncertain or unsafe tickets to human review.
```

### Key takeaway

Use **LangChain** to create what each agent does.

Use **LangGraph** to control when agents run, what information they receive, and when the system must stop and involve a human.

This gives you a simple, secure multi-agent design:

```text
LangChain agents + LangGraph orchestration + policy validation + human review
```
