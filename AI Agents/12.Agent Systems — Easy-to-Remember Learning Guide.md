# Agent Systems — Easy-to-Remember Learning Guide

> ## **An Agent = Brain + Hands + Memory + Control**
>
> - **Brain** — thinks and plans  
> - **Hands** — uses tools and takes actions  
> - **Memory** — remembers useful information  
> - **Control** — works safely with the right level of freedom  

Use this pattern for every topic:

> **Why → Core Idea → Remember It As → Example → Leads To**

---

# 1. Control — What Makes an Agent Safe and Useful?

## 1.1 Plain LLM vs. Agent

**Why:** A plain LLM cannot verify live information or perform actions.

**Core idea:** A plain LLM answers from its provided context; an agent can use tools, inspect results, and then respond.

**Remember it as:**  
> **LLM = Brain only**  
> **Agent = Brain + Hands**

**Example:**  
“What's Delhi’s weather now?”  
- Plain LLM: cannot reliably know  
- Agent: calls weather service → reads result → answers

**Leads to:** If agents can act, how much freedom should they have?

---

## 1.2 Autonomy Spectrum

**Why:** Full independence can be risky; approval for every small action is inefficient.

**Core idea:** Give agents different levels of authority based on risk.

**Remember it as:**  
> **Suggest → Ask → Act**

| Level | Agent behavior | Example |
|---|---|---|
| **Assistant** | Suggests only | Drafts an email |
| **Co-pilot** | Acts after approval | Drafts email and asks before sending |
| **Autonomous agent** | Acts within approved boundaries | Handles routine support tickets |

**Example:**  
An expense agent may summarize expenses automatically but must ask before submitting reimbursement claims.

**Leads to:** How does an agent repeatedly decide what to do?

---

## 1.3 PRAO Agent Loop

**Why:** Real tasks require several actions, checks, and corrections.

**Core idea:** Agents work in a loop: **Perceive → Reason → Act → Observe**.

**Remember it as:**  
> **See → Think → Do → Check**

**Example:** Find a cheap flight:
1. **See:** User wants Delhi to Mumbai tomorrow  
2. **Think:** Flight data is needed  
3. **Do:** Search flights  
4. **Check:** Compare returned prices  
5. Repeat if needed, then answer  

**Leads to:** Should every workflow use dynamic decision-making?

---

## 1.4 Agentic vs. Non-Agentic Workflows

**Why:** Dynamic agents are unnecessary for simple, predictable jobs.

**Core idea:** Use fixed pipelines for stable tasks and agents for uncertain tasks.

**Remember it as:**  
> **Pipeline = recipe**  
> **Agent = detective**

**Example:**  
- Pipeline: PDF → extract text → summarize → save  
- Agent: Investigate why sales dropped → choose which data to inspect next  

**Leads to:** What behaviors make something truly agent-like?

---

## 1.5 Four Agent Properties

**Why:** Calling every LLM workflow an “agent” makes the term unclear.

**Core idea:** Agent-like systems are goal-directed, reactive, proactive, and persistent.

**Remember it as:**  
> **Goal, React, Initiate, Remember**  
> **G-R-I-R**

| Property | Meaning | Inbox-agent example |
|---|---|---|
| **Goal-directed** | Works toward an objective | Keeps important mail handled |
| **Reactive** | Responds to changes | Categorizes a new email |
| **Proactive** | Takes useful initiative | Flags an unanswered client email |
| **Persistent** | Tracks state over time | Remembers pending follow-ups |

**Leads to:** Now that we know what an agent does, how does it think?

---

# 2. Brain — How an Agent Reasons and Plans

## 2.1 Chain-of-Thought (CoT)

**Why:** Complex questions are easier to solve when broken into intermediate steps.

**Core idea:** The model uses stepwise reasoning instead of jumping directly to an answer. For users, provide only the concise explanation needed to verify the result.

**Remember it as:**  
> **Don’t jump; climb steps.**

**Example:**  
23 apples − 8 sold = 15  
15 + 15 delivered = **30 apples**

**Leads to:** Reasoning is useful, but how does the agent check real-world facts?

---

## 2.2 ReAct

**Why:** Thinking alone cannot search, calculate, query a database, or verify live facts.

**Core idea:** ReAct alternates reasoning with tool use.

**Remember it as:**  
> **Think → Do → Learn → Repeat**

**Example:**  
“What is the population of France’s capital?”
1. Find France’s capital → Paris  
2. Look up Paris population  
3. Return the verified result  

**Leads to:** What if the first path of reasoning is wrong?

---

## 2.3 Tree-of-Thought (ToT)

**Why:** A single reasoning path can lead to a dead end.

**Core idea:** Generate several possible paths, evaluate them, and continue with the strongest one.

**Remember it as:**  
> **A maze, not a straight road.**

**Example:**  
Riddle: “I have branches but no trunk or leaves.”
- Tree → poor fit  
- River → possible  
- Bank → best fit  

Answer: **A bank**

**Leads to:** How can the agent improve after making a mistake?

---

## 2.4 Reflexion

**Why:** An agent can produce an answer or action that looks correct but fails testing.

**Core idea:** Review the result, identify the failure, improve the approach, and retry within a limit.

**Remember it as:**  
> **Do → Review → Improve**

**Example:**  
An agent writes code to reverse a string:
1. Runs a test  
2. Test fails  
3. Finds an off-by-one error  
4. Fixes and retests  

**Leads to:** How can larger tasks avoid rethinking every tiny action?

---

## 2.5 Plan-and-Execute

**Why:** Re-deciding the entire strategy after every action is slow and costly.

**Core idea:** Make a high-level plan first, execute it, and re-plan only when necessary.

**Remember it as:**  
> **Plan once, work many times.**

**Example:** Plan a Goa trip:
1. Search flights  
2. Search hotels  
3. Build itinerary  
4. Re-plan only if a step fails, such as no available flights  

**Leads to:** How can an agent reveal the smaller questions inside a large question?

---

## 2.6 Self-Ask

**Why:** Some questions look simple but depend on multiple facts.

**Core idea:** Break the main question into smaller follow-up questions.

**Remember it as:**  
> **Ask the hidden questions first.**

**Example:**  
“Who was US president when the first iPhone launched?”
1. When did the first iPhone launch? → 2007  
2. Who was president in 2007? → George W. Bush  
3. Answer → **George W. Bush**

**Leads to:** What if multiple sub-questions connect and combine?

---

## 2.7 Graph-of-Thought (GoT)

**Why:** Some tasks need ideas from several paths merged together.

**Core idea:** Reasoning can branch, reconnect, reuse findings, and merge results.

**Remember it as:**  
> **A web of ideas, not a family tree.**

**Example:** Write about remote work:
- Gather advantages  
- Gather disadvantages  
- Gather productivity data  
- Merge all findings into a balanced report  

**Leads to:** How can agents reduce repeated model calls for many tools?

---

## 2.8 ReWOO

**Why:** ReAct can be expensive when each tool result causes another model call.

**Core idea:** Plan required tool calls first, execute them, then combine their results once.

**Remember it as:**  
> **Plan → Gather → Solve**

**Example:** Compare France, Germany, and Italy:
1. Plan population and area lookups  
2. Run all lookups  
3. Generate one comparison table  

**Leads to:** How do we break a vague goal into work items?

---

## 2.9 Task Decomposition

**Why:** Big goals are too vague to execute directly.

**Core idea:** Divide a large goal into smaller, manageable tasks.

**Remember it as:**  
> **Big goal → small jobs**

**Example:** Plan a birthday party:
- Venue  
- Guest list  
- Food  
- Entertainment  
- Invitations  

**Leads to:** How should those tasks be organized when there are many levels?

---

## 2.10 Hierarchical Planning

**Why:** A single long task list becomes difficult to track and repair.

**Core idea:** Organize work from high-level goals down to executable actions.

**Remember it as:**  
> **Goal → Sub-goal → Action**

**Example:**  
Organize a company offsite:
- Book venue  
  - Search venues  
  - Compare prices  
  - Request approval  
  - Confirm booking  
- Arrange transport  
- Plan activities  

**Leads to:** Once the agent knows what to do, how does it take action?

---

# 3. Hands — How an Agent Uses Tools

## 3.1 Function Calling Fundamentals

**Why:** An LLM produces text, but software needs predictable structured inputs.

**Core idea:** Give the model a tool schema so it can request a function call with valid arguments.

**Remember it as:**  
> **A form, not free-form text.**

**Example:**  
Tool definition: `get_weather(city, unit)`  
Agent requests:

```json name=weather-tool-call.json
{
  "name": "get_weather",
  "arguments": {
    "city": "Delhi",
    "unit": "celsius"
  }
}
```

**Leads to:** How do major LLM providers implement this pattern?

---

## 3.2 Native Tool-Calling APIs

**Why:** Parsing tool requests from ordinary language is unreliable.

**Core idea:** Providers return structured tool-call objects instead of requiring fragile text parsing.

**Remember it as:**  
> **Schema in → tool call out**

**Example:**  
Your app sends:
- User message  
- Available tool schemas  

The model returns:
- A normal answer, or  
- A structured request to call a tool  

**Leads to:** How does the agent choose the right tool?

---

## 3.3 Tool Selection

**Why:** Too many available tools increase cost and cause wrong tool choices.

**Core idea:** Route the request to the smallest useful set of tools.

**Remember it as:**  
> **Right tool, right job.**

**Example:**  
- “What is 25 × 17?” → calculator  
- “Find a flight and add it to my calendar” → flight search + calendar  

**Security note:** Only expose tools the agent is authorized to use; use deny-by-default permissions.

**Leads to:** What happens when the chosen tool fails?

---

## 3.4 Tool Result Parsing and Error Handling

**Why:** APIs can fail, time out, return invalid data, or reject inputs.

**Core idea:** Validate tool results before using them; retry safely or ask the user when needed.

**Remember it as:**  
> **Trust, but verify.**

**Example:**  
`get_weather("Dehli")` returns `City not found`.
- Do not invent weather data  
- Suggest “Delhi” or ask for clarification  
- Retry only with safe limits  

**Leads to:** How do agents work with hundreds of tools?

---

## 3.5 Dynamic Tool Discovery

**Why:** Loading every tool into every prompt is expensive and confusing.

**Core idea:** Search a tool catalog and load only relevant tool schemas.

**Remember it as:**  
> **Search the toolbox before picking a tool.**

**Example:**  
Request: “Check inventory for product X.”  
The registry returns:
- `get_product_details`  
- `check_inventory`  

**Leads to:** How can tool integrations work consistently across systems?

---

## 3.6 Model Context Protocol (MCP)

**Why:** Custom integrations for every agent, service, and model are hard to maintain.

**Core idea:** MCP provides a standard way for agents to discover and use tools and context sources.

**Remember it as:**  
> **USB for AI tools.**

**Example:**  
An MCP-compatible client can connect to approved GitHub, database, and Slack MCP servers through a common protocol.

**Security note:** Treat every MCP server as a privileged integration; restrict access, validate tool inputs, and use least-privilege credentials.

**Leads to:** What if no existing tool can perform the needed calculation?

---

## 3.7 Sandboxed Code Execution

**Why:** Fixed tools cannot cover every custom calculation or data transformation.

**Core idea:** Let agents run generated code in a tightly isolated environment.

**Remember it as:**  
> **A safe workshop, not unrestricted server access.**

**Example:**  
An agent writes a small script to calculate compound interest and returns the computed result.

**Security requirements:**
- No production credentials  
- Restricted temporary filesystem  
- Network blocked by default  
- CPU, memory, and execution-time limits  
- Approved package allow-list  

**Leads to:** How are complex real-world APIs simplified for agents?

---

## 3.8 API Wrappers

**Why:** Raw APIs expose unnecessary complexity, credentials, pagination, and inconsistent responses.

**Core idea:** Build small, focused tool wrappers that provide only the capability the agent needs.

**Remember it as:**  
> **Steering wheel, not engine parts.**

**Example:**  
Instead of exposing a complete weather API, provide:

`get_weather(city)` → `{ temperature, condition }`

**Security note:** Keep API keys in secrets management, validate inputs, allow-list destinations, and never expose credentials to the model.

**Leads to:** How do tools recover from temporary failures?

---

## 3.9 Retries and Fallbacks

**Why:** Network services can fail temporarily.

**Core idea:** Retry limited times with backoff, then use a pre-approved fallback or report failure.

**Remember it as:**  
> **Try carefully, then switch safely.**

**Example:**  
1. Weather API times out  
2. Retry after 2 seconds  
3. Retry after 4 seconds  
4. Use a backup provider  
5. If all attempts fail, clearly explain the limitation  

**Security note:** Never retry destructive actions blindly; use idempotency keys and confirmation checks.

**Leads to:** How does an agent retain useful information over time?

---

# 4. Memory — How an Agent Remembers

## 4.1 Short-Term Memory

**Why:** Long conversations can exceed context limits and become expensive or confusing.

**Core idea:** Keep recent relevant content and summarize older content.

**Remember it as:**  
> **A limited whiteboard.**

**Example:**  
Keep recent messages in full, plus a concise summary of the earlier conversation.

**Leads to:** How does the agent remember beyond one chat session?

---

## 4.2 Long-Term Memory

**Why:** Models do not automatically remember information after a session ends.

**Core idea:** Store approved useful information externally and retrieve it only when relevant.

**Remember it as:**  
> **A filing cabinet outside the brain.**

**Example:**  
Store: “User prefers vegetarian restaurants.”  
Later, use that preference for restaurant suggestions.

**Security note:** Obtain consent, minimize stored data, encrypt sensitive records, and provide deletion controls.

**Leads to:** What kinds of information should be stored?

---

## 4.3 Episodic Memory

**Why:** Agents may need to remember past events and actions.

**Core idea:** Store what happened, when it happened, and the outcome.

**Remember it as:**  
> **The agent’s diary.**

**Example:**  
“On March 3, the user reported a checkout bug. Ticket #452 was created.”

**Leads to:** How are stable facts stored separately from events?

---

## 4.4 Semantic Memory

**Why:** General facts should not be buried inside past conversation logs.

**Core idea:** Store stable facts in structured, easy-to-retrieve form.

**Remember it as:**  
> **The agent’s fact sheet.**

**Example:**  
`preferred_language = "Hindi"`

**Security note:** Track source and update time, because facts can become outdated.

**Leads to:** How does an agent remember successful ways of doing work?

---

## 4.5 Procedural Memory

**Why:** Agents should not rediscover the same successful process repeatedly.

**Core idea:** Save validated workflows and playbooks for reuse.

**Remember it as:**  
> **The agent’s recipe book.**

**Example:**  
Deployment incident procedure:
1. Check service health  
2. Inspect logs  
3. Verify configuration  
4. Escalate or restart only with authorization  
5. Confirm recovery  

**Leads to:** How can the agent find relevant information among thousands of memories?

---

## 4.6 Vector-Based Retrieval

**Why:** Exact keyword search misses memories expressed using different words.

**Core idea:** Use embeddings to retrieve memories based on meaning.

**Remember it as:**  
> **Search by meaning, not spelling.**

**Example:**  
Question: “Is there a shipping problem?”  
Retrieved memory: “Package delayed because of a courier strike.”

**Security note:** Apply user and tenant access filters before similarity search results reach the model.

**Leads to:** How can memory stores remain efficient as they grow?

---

## 4.7 Memory Summarization

**Why:** Storing every message forever creates clutter and raises cost.

**Core idea:** Compress older conversations into short, useful summaries.

**Remember it as:**  
> **Keep the lesson, discard the transcript.**

**Example:**  
Instead of 20 billing-support messages, save:  
“January 2026 billing dispute resolved with a ₹500 refund.”

**Leads to:** What should happen to outdated or irrelevant memories?

---

## 4.8 Memory Pruning

**Why:** Old or incorrect memories can lead to bad decisions.

**Core idea:** Delete, expire, deprioritize, or replace memories based on age, importance, and contradiction.

**Remember it as:**  
> **Memory needs spring cleaning.**

**Example:**  
Old fact: “User lives in Mumbai.”  
New fact: “User moved to Bengaluru.”  
Replace the old fact with the new verified one.

**Leads to:** How does the agent track information during one active task?

---

## 4.9 Working Memory / Scratchpad

**Why:** Multi-step work can become inconsistent if the agent loses track of progress.

**Core idea:** Keep a temporary, structured record of task state.

**Remember it as:**  
> **The agent’s sticky note.**

**Example:**

```text name=trip-task-state.txt
Flights: Cheapest option found — ₹4,500
Hotels: Searching
Itinerary: Not started
```

**Security note:** Treat scratchpads as potentially sensitive temporary data; restrict access and clear them after the task according to retention policy.

**Leads to:** Combine Brain, Hands, Memory, and Control to build a complete agent.

# Final One-Minute Summary

> ## **An Agent = Brain + Hands + Memory + Control**

| Part | Question it answers | Key concepts |
|---|---|---|
| **Control** | How freely and safely can it act? | Autonomy, permissions, PRAO |
| **Brain** | How does it decide? | CoT, ReAct, ToT, planning |
| **Hands** | How does it do things? | Tools, APIs, MCP, sandboxes |
| **Memory** | How does it remember? | Context, retrieval, summaries, pruning |

## The Complete Agent Cycle

> **Control sets boundaries**  
> → **Brain makes a plan**  
> → **Hands take safe actions**  
> → **Memory stores useful outcomes**  
> → **Brain uses those outcomes next time**
